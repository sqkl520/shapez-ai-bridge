## 1. 设计依据（为什么是这些坐标）

### 1.1 带子的方向语义（已用源码 + 实机双重确认）

`recon/upstream-full/src/js/game/systems/belt_path.js:246`
——下游带子接受来料的条件是 **`ejectSlotWsDirection === targetStaticComp.localDirectionToWorld(top)`**，
即"上游的喷射方向 == 下游带子的行进方向"。所以：

```
带子 B 从格 T 收货  ⟺  T 是 B 的相邻格，且 (T→B) 的方向 == B 的行进方向
```

等价地：**带子只从它"来向"的那一格收货，永远只往行进方向吐。** 没有侧向输入。

### 1.2 `(r, rotationVariant)` → (入口侧, 出口方向)

由 `components/belt.js:102-118`（`transformBeltToLocalSpace`）与 `buildings/belt.js` 的
`arrayBeltVariantToRotation = [top, left, right]` 推出，并用实机 161 条带子的 140 对相邻关系回归验证：

| r | rv | code | 入口侧 | 出口方向 |
|---|---|---|---|---|
| 0 | 0 | 1 | 南 | 北 |
| 0 | 1 | 2 | 南 | 西 |
| 0 | 2 | 3 | 南 | 东 |
| 90 | 0 | 1 | 西 | 东 |
| 90 | 1 | 2 | 西 | 北 |
| 90 | 2 | 3 | 西 | 南 |
| 180 | 0 | 1 | 北 | 南 |
| 180 | 1 | 2 | 北 | 东 |
| 180 | 2 | 3 | 北 | 西 |
| 270 | 0 | 1 | 东 | 西 |
| 270 | 1 | 2 | 东 | 南 |
| 270 | 2 | 3 | 东 | 北 |

**回归证据**：对 `debug_items` 返回的 18 条 beltPath 逐对相邻格做一致性检查，
140 对全部"恰好单向连通、0 对矛盾"。表与实机完全吻合。

### 1.3 拐角带子必须"下游先放"（硬约束）

`buildings/belt.js:160-245` 的 `computeOptimalDirectionAndRotationVariantAtTile` 会在每次放置后
被 `BeltSystem.updateSurroundingBeltPlacement` 对所有邻居重算一次。它的优先级是：

1. 下方有 ejector → 直行
2. 侧向有 ejector（左右各异）→ 朝该侧转弯
3. 上方没有 acceptor 时，侧向有 acceptor → 朝该侧转弯
4. 否则直行

**关键实测结论**（用上述算法对 4 种 pass-r 逐一枚举）：

> 想要得到"侧进上出/上进侧出"的拐角，**传进去的 `r` 必须等于来料方向**，
> 而且**下游那一格必须已经存在**（否则规则 3 看不到 acceptor，退化成直行）。

所以本文所有坐标清单都是**按"下游 → 上游"的顺序排列**的，照抄顺序执行即可，
不要重排。第 5 节给出每格的 `pass r`（放置时传的 r）与最终 `(r, rv)`，
两者不同时说明该格被自动定向成了拐角——这是预期行为，不是错误。

### 1.4 机器几何

- **矿机** `buildings/miner.js:82`：1×1，ejector 在 `(0,0)` 朝 `top` → 只向上吐。
- **切割机** `buildings/cutter.js:98-119`：2×1，占 `(x,y)`+`(x+1,y)`；
  acceptor 在 `(0,0)` 方向 `bottom`（**唯一输入**，从下方进）；
  两个 ejector 在 `(0,0)` 和 `(1,0)` 都朝 `top`（向上出）。
- **切割机槽位映射**（`systems/item_processor.js:367`，`ops-semantics-VERIFIED.md §7` 实机验证）：
  - 槽 0 = `(x, y-1)` → `----RuRu`（**废料**）
  - 槽 1 = `(x+1, y-1)` → `RuRu----`（**目标**）
- **trash** `buildings/trash.js`：1×1，四边全收，无需方向。
- **hub** `buildings/hub.js:63-82`：4×4 占 `(-2..1, -2..1)`；
  顶排 `(-2..1,-2)` 接受从上方来的（需带子朝下 S），
  底排 `(-2..1, 1)` 接受从下方来的（需带子朝上 N）。

### 1.5 产能

- `config.js:151`：`minerSpeedItemsPerSecond = beltSpeedItemsPerSecond / 5` = **0.4/s**（miner 升级 0 级）
- `hub_goals.js:552`：cutter 速度 = `2 × (1/4) × processors(1.0)` = **0.5/s** → 不是瓶颈
- 带子 2/s → 远不是瓶颈
- 切割后**只有一半**产物是 `RuRu----` → 进 hub 速率 = **0.4/s**
- 70 个 ÷ 0.4/s = **175 s ≈ 2 分 55 秒**

| **B-R1** | `(4,-7)` 与 `(5,-7)` 紧贴现有矿机 `uid 10081@(4,-8)`、`uid 10082@(5,-8)` 的**正上方一格** | 这是 B 比 A 多出来的主要风险。矿机朝 N 吐，出口正是 `(4,-7)`/`(5,-7)` —— **如果只贴了带子而没先确认这两台矿机的去向，它们会往我的 S 形输入段里灌 `RuRuRuRu`**，与我的矿机产物汇流。虽然两者都是 `RuRuRuRu`（同种物品，汇流不产生错误产物），但会让输入变 3 路、并把 B 的"独立产线"属性破坏掉 |
| **B-R2** | 同上 | 现有 `(4,-8)`/`(5,-8)` 两台矿机的产物当前**已经**被 `uid 10138@(4,-9)`/`uid 10145@(5,-9)` 接走（朝 N 的带子）。只要那两条带子在，矿机出口就已被占用，不会往 `(4,-7)` 吐。**贴前必须用 `debug_items` 确认 `(4,-7)`/`(5,-7)` 在现有 path 里没有出现** |
| B-R3 | `(6,-7)` 是拐角 W→N，需要 `(6,-8)` 切割机**先存在** | 按表中顺序（#2 先放 cutter）即可 |
| B-R4 | 输入段有 2 个拐角（A 只有 0 个），多 2 个失效点 | 顺序错一步就断 |

> 结论：B 能用，但收益为零（产能同为 0.4/s）而风险显著更高。**推荐 A。**

## 7. 回滚清单

**统一原则**：只删自己贴的格子，一格不多。所有坐标都取自 §3.2 / §4.2 的表，不含任何现有实体。

### 7.1 精确回滚：方案 A（43 个）

`delete` 是**按格删**（`opDelete` 用 `getLayerContentXY` 取那一格的实体），
所以下面每一行删掉的就是那一格上的东西。

**第 1 批 — 6 个非带子实体 + 输入段的 2 条带子（先删，避免断链报错刷屏）**
```
(6,-6)   miner
(6,-8)   cutter
(6,-10)  trash
(6,-9)   belt
(6,-7)   belt
(1,2)    belt
```

**第 2 批 — `y=2` 横向 10 格**
```
(2,2) (3,2) (4,2) (5,2) (6,2) (7,2) (8,2) (9,2) (10,2) (11,2)
```

**第 3 批 — `x=12` 纵向 17 格**
```
(12,-14) (12,-13) (12,-12) (12,-11) (12,-10) (12,-9) (12,-8) (12,-7) (12,-6)
(12,-5) (12,-4) (12,-3) (12,-2) (12,-1) (12,0) (12,1) (12,2)
```

**第 4 批 — `y=-14` 横向 5 格 + `x=7` 纵向 5 格**
```
(11,-14) (10,-14) (9,-14) (8,-14) (7,-14)
(7,-13) (7,-12) (7,-11) (7,-10) (7,-9)
```

合计 6 + 10 + 17 + 10 = **43 格 = 43 个实体**，与 §0 的实体总数一致（1 miner + 1 cutter + 1 trash + 40 belts）。

**更简单的做法**：按 4 个矩形做 `bulk_delete`，但**只会删这些格子上的东西**：
```
[2,2,11,2]      → 10 格
[12,-14,12,2]   → 17 格
[7,-14,11,-14]  → 5 格
[7,-13,7,-9]    → 5 格
[6,-10,6,-6]    → 5 格（miner/belt/cutter/belt/trash 共 5 格，x=6,y=-10..-6）
[1,2,1,2]       → 1 格
```
**注意**：`[12,-14,12,2]` 这一列在 `y=-10` 处与现有平衡器 `uid 10187@(10,-9)/(11,-9)` **不重叠**
（平衡器占 `x=10,11`，本设计用 `x=12`）。
但 `[7,-13,7,-9]` 的 `(7,-9)` 与平衡器 `uid 10186@(8,-9)` 相邻不重叠。✅

**回滚后自检**：
```

debug_items region[0,-12,13,3] → pathCount 应回到 18
hub 底排 (-2..1,2) → 应仍无 path 末格
```

### 7.2 精确回滚：方案 B（45 个）

同 §7.1，但把第 1 批与末批换成：

```
(4,-6)   miner          ← 换掉 (6,-6)
```

### 7.3 半截回滚（贴到一半失败）

按 §3.2 的表**倒序**逐条 `delete` 即可（表本身就是下游→上游的顺序，

或者：

先 `dry_run` 看会删掉几个。**注意这个矩形会覆盖 `x=1..5` 的现有钌线**
（`1,-16..-3`、`2..5,-16..-8`），**不能直接执行** —— 只能用来诊断。
