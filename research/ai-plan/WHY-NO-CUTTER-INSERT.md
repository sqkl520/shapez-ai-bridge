# 为什么不能直接往现有线上插切割机

## 结论

**当前实现下，切割机只能装在"流向向上（y 减小）"的产线上。**
钌线主干是向下的（y 增大），所以插不进去。这不是编译器 bug，
是 `v1 加工机器朝向恒 r=0` 这条限制的直接后果。

## 推导（用受控实验验证过，不是推测）

### 坐标系

```js
DIRV = { top: [0,-1], right: [1,0], bottom: [0,1], left: [-1,0] }
ORDER = ["top", "right", "bottom", "left"]
angleToDir(r) = ORDER[r/90]
```

- `r=0`   → `top`    → y 减小
- `r=180` → `bottom` → y 增大

### 切割机的槽位

```js
inputs:  [slot([0,0], "bottom")]           // 输入格 = 本格 + [0,1] = (x, y+1)
outputs: [slot([0,0], "top"), slot([1,0], "top")]  // 输出格 = (x, y-1) 与 (x+1, y-1)
```

**输入格在 `(x, y+1)`，输出格在 `(x, y-1)` 附近。**

### 两条线的实际流向

**钌线主干**（`x=1`，从 `(1,-34)` 到 `(1,-3)`）：`r=180` = `bottom` = **y 增大**。
即物品从 y=-34 流向 y=-3，再进 hub（hub 在 y=-2）。

要在 `(1,-6)` 插切割机，它的输入格是 `(1,-5)` —— 那是**下游**。
物品还堵在 `(1,-7)`，根本到不了 `(1,-5)`。

**受控实验**（新存档，不是用户存档）确认了正确的配置：

```
矿机 (-10,6) r=0     ← 输出向上到 (-10,5)
带子 (-10,5) r=0     ← 向上到 (-10,4)
带子 (-10,4) r=0     ← 向上到 (-10,3)
切割机 (-10,3) r=0   ← 输入格 = (-10,3)+(0,1) = (-10,4) ✓ 正是上游
```

结果：`ejectors` 显示切割机两个槽都在产出 `----CuCu` 和 `CuCu----`。

**所以：切割机要求"输入格在上游"，而输入格恒在 y+1。
因此只有当产线流向是 y 减小时，y+1 才落在上游。**

## 我犯的错

我在用户存档的 `(1,-6)` 放了切割机，以为它会吃掉 `(1,-7)` 来的货。
实际它的输入格是 `(1,-5)`，那是下游 —— 于是：

1. 切割机永远收不到货
2. 主干 `(1,-7)` 堆满（23 个物品），`boundAcceptor=null`
3. 4 台钌矿机全部停摆（`progress=1`）
4. `produced` 里钌完全消失

**已完全回滚**：删切割机和垃圾桶，恢复 `(1,-6)`、`(1,-7)` 两条 `r=180` 带子。
验证：`RuRuRuRu` 恢复产出。

## 更深的问题

不只是位置问题。就算找对位置，**`r=0` 的切割机在这条向下的线上仍然装不进去**——
因为它的输入永远在 y+1，而这条线的上游永远在 y-1。

真正要解决，必须支持**旋转机器**（`r=180` 的切割机，输入在 y-1）。
而这是 `op-templates.mjs` 里 H3 明确排除的：

> H3 v1 加工机器朝向恒 r=0（GEOMETRY 表1 的槽位只在 r=0 定义，
> static_map_entity.js 旋转时 origin 位移未实机验证）。

`rotateSlot()` 已经实现了并有单测，但从没在实机上验证过。

## 下一步该做什么

1. **实机验证 `rotateSlot`** —— 已做，结论是**旋转机器目前在实机上不可用**。

   受控实验（独立存档 `8f007207`，已删除）：

   ```
   矿机 (-10,6) r=180
   带子 (-10,7) r=180
   带子 (-10,8) r=180
   切割机 (-10,9) r=180     ← 期望输入格 (-10,8)
   ```

   结果：`produced = {}`，`ejectors = []`。**完全没有产出。**
   又逐个探测了四侧（y+1 / y-1 / x-1 / x+1），四个方向的带子都拿不到
   `boundAcceptor`，说明 `r=180` 的切割机在游戏里根本不收任何一侧的货。

   对照实验（同存档、同位置、只把 `r` 换成 0、链换成向上）：

   ```
   矿机 (-10,6) r=0
   带子 (-10,5) r=0
   带子 (-10,4) r=0
   切割机 (-10,3) r=0       ← 输入格 (-10,4)
   ```

   结果：`ejectors` 显示切割机两个槽都在产出 `----CuCu` / `CuCu----`。**正常工作。**

   **所以：`rotateSlot` 的理论映射（单测里是对的）与游戏实机不一致。
   `r≠0` 的加工机器在 1.5.6 里不能收货。**

   这与 `op-templates.mjs` 的 H3 判断一致（"旋转时 origin 位移未实机验证"），
   但现在有了明确答案：**不是"未验证"，是"验证失败"**。

2. 因此 H3 不能放宽。要让机器支持 4 向，得先弄清游戏内部
   `static_map_entity` 旋转时 origin 到底怎么移 —— 需要读源码 + 更多实机探测。

3. **在此之前，L4 的正确做法是新建一条线**，而不是改造现有产线。
   新建线的矿机与带子都朝 `r=0`（向上），天然可用。

## 教训

我这次是**在用户真实的存档上试错**，而且是在没有先做受控实验的情况下。
虽然回滚了，但这是不应该的 —— 用户的存档不是试验场。

正确顺序应该是：先在独立存档做最小复现 → 确认机制 → 再动真实存档。
