## 3. 失败模式分类（这是本次实验最有价值的部分）

### 3.1 模型**从不删东西**（5/5）

五次尝试，**没有一次**想到要 `remove_run` 或 `replace_run` 删掉那三条带子。
它一致地选择 `insert_machine`——"在某个位置插一台机器"。

**为什么**：模型把 L4 理解成"加一台切割机"，而不是"把这段带子改造成切割机"。
从 `obs` 看，`(4,-13)` 已经有一条带子；模型倾向于**在旁边加**，而不是**就地改**。

**这是提示词的问题**：prompt 里没有一句话说明"改造既有带子"是允许且常见的。
`replace_run` 在候选宏里，但模型没有理由优先选它。

### 3.2 模型选的位置有系统性偏差（4/5）

| # | 选的位置 | 与正解的距离 |
|---|---|---|
| 2 | B84 | 不是目标三条 |
| 3 | B85 | 不是目标三条 |
| 4 | B112 | 是目标的上游（M3 矿机链） |
| 5 | B135 | hub 入口那一圈 |

**#4 最接近**：它选了 M3 矿机链的头部（B112），说明它**理解了"要从矿机那头改"**，
但选的是链头而不是中段的目标位置。

**#5 的推理是错的但可理解**：它说"hub 已经有供料带但没交货，所以问题在入口"——
从 `obs` 看，hub 环上确实有 3 条带子（B135/B136/B137），且 delivered=0。
它推断"货到了 hub 却没进来"，所以想改入口。**实际原因是那三条带子不在通往 hub 的路径上。**

### 3.3 机器名拼错（1/5）

`"machine":"rotator"` —— 正确是 `"rotater"`。宏正确地拒绝了（`unsupported_building`）。
**这类错误 prompt 完全可以防**：宏卡片里应该列出合法的 machine 值。

### 3.4 `LLM_NARRATION` 造成真实损失（1/5）

第 5 次 `say` 写了 349 字符（上限 280），整轮被拒。
但它的动作 `insert_machine(at=B135, cutter)` 是**结构合法**的——
被拒的理由纯粹是叙述太长。

这是 C agent 在实现时质疑过、红队也批评过的那条规则：
> 「拿正确性给格式买单」

**实测证实了这个批评**。`LLM_NARRATION` 应该降级为警告，不该整轮作废。

但**核心指标没动**。

### 新的失败模式：位置选择的系统性偏差

5 次里 **4 次**选中 hub 入口那一圈 `B135/B136/B137`：

> "The goal is a cut half-shape; convert the hub-feed belts in place into a cutter plus trash"
> （#1，`replace_run` on B135/B136/B137 → `out_of_scope`）

**模型的推理链条是正确的**：
1. goal 要 `RuRu----`（半个形状）
2. hub 的 delivered = 0
3. 所以肯定要切割
4. 哪条带子在往 hub 送？→ B135/B136/B137（hub 环上仅有的三条）
5. 那就把这三条改成切割机

**它错在事实层面**：那三条带子尽管紧贴 hub，**其实不在通往 hub 的有效路径上**
（`pathCount` 里它们的 `boundAcceptor` 是 null 或指向别处）。
而真正的产品链是从 M3 矿机出来的那两条（B63…B69/B81 与 B64…B70/B82）。

**prompt 没有提供判断这一点的信息**：
- BELTS 段只写「上游=X 下游=Y 货=N」，没写「这条链是否真的接进了 hub」
- 没有写「这条链在造什么形状」
- 模型只能靠"离 hub 近"这个启发式猜，而它猜错了

### #5 选中了正解，但 region 给得太大

> `replace_run {region: $bbox_of[B112,B105,B97,B90,B81,B69,B63], building: "belt"}`

它把**整条上游链**（从矿机 M3 到目标）都框进去了，而不只是要改的 3 格。
这是 `$bbox_of` 的语义问题：给一组句柄 → 覆盖它们的**最小外接矩形**，
而 `replace_run` 需要的是"恰好那几格"。两者不匹配。

## 11. 修正后的结论

**核心赌注仍未达成（0/5）**，但失败原因已经从"看不见"精确到**两个可定位的缺口**：

| 缺口 | 性质 | 修法 | 估计 |
|---|---|---|---|
| 模型不知道哪条链接进了 hub | **信息缺失** | BELTS 段标注每条链的 `boundAcceptor` 是否非 null（是否真接入） | 半天 |
| 模型不知道哪条链在造什么 | **信息缺失** | 标注链的产出形状（需从 production 或矿机类型推） | 1 天 |
| `$bbox_of` 的 bbox 与 `replace_run` 的 region 语义不匹配 | **算子语义缺口** | 需要 `$path_of`（沿链取格）或让 `$bbox_of` 支持"紧凑子集" | 1 天 |

**注意**：这三条都不是"宏层"的问题。宏层在对照组里已经证明能一条调用解出正解。
问题全在 **prompt 提供的信息量** 与 **句柄算子的表达力** 上。

这实际上**强化**了 DIRECTION-FINAL 的原始判断：
> 「LLM 是改稿人，不是设计者，也不是算数的人。」

它现在证明：**改稿人也需要看到稿子**。当前 prompt 给它的是一张缺了关键标注的图。

## 12. 决定性发现：**模型的误选是合理的**

用 `src/agent/probe-hub-reach.mjs` 实测「哪条带子真的能走到 hub」：

```
hub @ (-2,-2) · 能到 hub 的带子 58/163

模型常选的 hub 环 B135/B136/B137  → 真能到 hub：3/3
正解三条      B81/B82/B69        → 真能到 hub：0/3
```

**这是本轮最重要的发现。**

模型没有乱猜。它观察到「hub 的 delivered = 0」，于是去找「哪些带子在往 hub 送货」，
选中了真正连通 hub 的那三条。**在它掌握的信息下，这是最合理的推理。**

错的是我们的前提：**L4 的正解要改造的那三条带子，本身并不通往 hub**。
它们是从 M3 矿机出来的上游链，改造后才会产生 `RuRu----` 并接进 balancer → hub。

也就是说：**模型需要的不是"哪条离 hub 近"，而是"哪条链在造什么形状、以及 goal 要求什么形状"。**
这个信息 prompt 里完全没有。

### 这改变了「失败」的性质

| 之前的判断 | 修正后的判断 |
|---|---|
| 模型选错了位置 | **模型选对了它唯一能判断的位置** |
| 需要更好的提示词措辞 | **需要更多的世界知识（形状归属）** |
| 是 LLM 能力问题 | **是信息供给问题，且我们知道缺哪一条** |

## 15. 第三轮实验：修完验收三处后重跑（2026-10-28T19:34）

修完第二轮验收指出的三处（loop 要 resources / 候选宏加 replace_run / 实验口径）后重跑 5 次。

| 指标 | 第二轮 | **第三轮** | 变化 |
|---|---|---|---|
| prompt 看到正解 | 5/5 | 5/5 | — |
| **选中 ≥2 条** | 1/5 | **4/5** | **↑↑** |
| **选中全部 3 条** | 1/5 | **2/5** | ↑ |
| 走到 plan | 1/5 | 0/5 | ↓ |
| 精确匹配 | 0/5 | 0/5 | — |

### 模型的行为发生了质的变化

**第二轮**：4/5 盯着 hub 入口 `B135/B136/B137`（"货没进来，改入口"）。
**第三轮**：4/5 正确地指向了 **M3 矿机链**（`B97/B90/B81`、`B98/B91/B82` 等），
推理是「两条矿机线汇入 L3，把整条就地改成 cutter+trash」。

模型现在**理解了问题的真实结构**。这一步是 §12 那个"决定性发现"的直接修复效果：
给了 resources 之后，它能算出"哪条链在装什么原料"，于是不再靠"离 hub 近"猜。

### 但它现在卡在几何执行，不在选择

| # | 选中 | 失败码 | 含义 |
|---|---|---|---|
| 1 | 2/3 | `occupied` | region 覆盖了不该动的格子 |
| 2 | 2/3 | `out_of_scope` | 目标机器 r≠0 |
| 3 | 3/3 | `not_a_run` | region 里有非带子 |
| 4 | 0/3 | `precondition_failed` | 位置错 |
| 5 | 3/3 | `precondition_failed` | **选中 3/3 且给了 cutter+trash，但 region 太大** |

**#5 是最接近成功的一次**：它同时选中了 x=4 与 x=5 两条链，
给了正确的 `[cutter, trash(left)]`，只差 region 只能包住要改的那三格。

### 结论修正

上一轮我写"模型需要的是哪条链在造什么形状"。**给了这个信息后它确实变好了**（1/5 → 4/5）。
现在剩下的瓶颈是**另一个**：

> **`$bbox_of` 给的是「覆盖所有句柄的最小外接矩形」，而 `replace_run` 要的是「恰好那几格」。**

模型想改 `B97/B90/B81`（同一条链上连续三格），`$bbox_of` 会给出一个矩形 ——
但那条链在空间上可能拐弯或与别的链并行，矩形会**顺带框进不该动的格子**。
#1 的 `occupied`、#3 的 `not_a_run`、#5 的 `precondition_failed` 全是这个原因。

**这是纯算子表达力问题，与模型能力无关。**

修法：需要一个"沿链取格"的算子（`$path_of`），或让 `replace_run` 接受
"这段链的连续三格"而不是一个矩形 region。

### 15.1 复现五条失败时的实测修正（`$path_of` 落地时重跑）

落地 `$path_of` 时把上面五条**按 JSON 里的原始计划逐条重放**，发现两处与本文的叙述不符。
两条都影响"修哪个算子"的判断，所以记在这里：

**① 失败原因不是"矩形多框了格子"，而是 `region` 只有 1 格宽。**

| # | 原文 | 重放得到 |
|---|---|---|
| 1 | `occupied` = region 覆盖了不该动的格子 | region `[4,-13,4,-11]` **恰好 3 格、无空洞**；`occupied` 的真因是 **1 格宽装不下 2×1 的 cutter** |
| 5 | `precondition_failed` = region 太大 | 7 格是**一条直线**，`contiguous:true`，与 `$bbox_of` **逐位相等**；`precondition_failed` 的真因是 `cutter` 的废料口只能是 `right`，模型写了 `left` |

也就是说：这两条的真实瓶颈是"**宽度**（2×1 机器的摆向）"与"**枚举值**"，`$path_of`
前后给出的 region 完全一样 —— **它不会救活这两条**。原文把它们归到"矩形框太大"是错的。

**② `$bbox_of` 真正危险的形态是「成功但换了对象」，而不是「宏拒绝」。**

用 L4 的真实数据（见 `src/agent/loop_pipeline.test.mjs` 的 ⑥b）：

```
$bbox_of(["B69","B81","B82"])  → region [4,-14,5,-13]（2×2，含没被点名的 (5,-14)）
replace_run(...trash:right)    → ok:true，删掉的 uid = [10149, 10150, 10209]
                                  ↑ 10150 = B70 @(5,-14) 没被点名；而被点名的 B69(10143) 没动
```

宏**接受了**它，没有任何拒绝信号，模型"以为自己改的是 B69/B81/B82"。这比 `occupied` 更糟：
`occupied` 至少会被 `verify` 抓到，而这一支会以一个**看起来成功**的 tx 落盘。

**结论**：`$path_of` 修的是 **①的叙述错误之外的真实一类** —— "选区在空间上拐弯/并排，
矩形必然多框"；判据是 `contiguous`（格集是否填满自己的外接矩形）。它**不修**宽度与枚举值。
`$path_of(["B97","B90","B81"])` 这种直线段上与 `$bbox_of` 完全等价 —— 这正是它诚实的边界。

## 16. 第四轮实验：`$path_of` 之后（2026-10-28T20:29）

加了 `$path_of`、修正了 `replace_run` 示例的 `port`、加了 R13 闸之后重跑：

| 指标 | 第三轮 | **第四轮** |
|---|---|---|
| 看到正解 | 5/5 | 5/5 |
| 选中 ≥2 条 | 4/5 | **1/5** |
| 选中全部 3 条 | 2/5 | 0/5 |
| 走到 plan | 0/5 | 2/5 |
| 精确匹配 | 0/5 | 0/5 |

**变差了。** `$path_of` 确实被用上了（#1 写了 `{"region":{"$path_of":[...]}}`），
但没有带来提升。原因是**另一个问题浮现出来**。

### 新浮现的问题：模型对形状代数的理解是错的

5 次里有 **4 次**认为需要一个 `rotater`：

> "Goal RuRu---- is a rotated half-shape: the factory has a cutter but no rotater at all,
> so add one on the cutter's left output belt so the half gets turned into the goal."
> （#5）

> "Convert the cutter's left output belt into a rotater so its half-shape becomes the goal's top-row shape."
> （#3）

**这个推理是错的。** `RuRu----` = `RuRuRuRu` 切一刀（取左半），**不需要旋转**。
模型把"半形状"理解成"需要旋转的形状"。

而它在 #3/#5 里的观察其实是对的——"工厂有 cutter 但没有 rotater"——
只是从"没有 rotater"推出了错误的结论（"所以需要 rotater"），
而正确答案是"不需要 rotater，需要的是让 cutter 对着正确的那条链"。

### 为什么这是新问题

前三轮的失败都是**空间定位**问题（选哪里）。这一轮 `$path_of` 解决了表达问题之后，
暴露出的是**语义理解**问题（这个形状要怎么造）。

这需要的信息是**形状代数**：`RuRu----` 由什么操作从什么原料得到。
而这恰恰是 `src/ai/compiler/` 已经做过的事（`solver` / `shape-ops`），
但那个能力**从来没有接进 prompt**。

### 四轮实验的失败原因迁移

| 轮次 | 主要失败原因 | 性质 |
|---|---|---|
| 1 | 看不到目标（163 条里选 12 条） | 信息量 |
| 2 | 选 hub 入口（"货没进来改入口"） | 信息量（缺矿图） |
| 3 | 选对了链，但 region 表达不了 | 算子表达力 |
| 4 | **不知道目标形状要怎么造（要 rotater 吗）** | **形状代数** |

每一轮修完，下一层问题就露出来。这不是原地打转——问题在**向更难、也更有价值的方向**移动。

### 形状代数**已经存在**，只是没接进 prompt

验证（用仓库里现成的 `research/ai-player/proto/shape-ops.mjs`）：

```js
const src = S.parse('RuRuRuRu');
const h = S.cutHalf(src);
// h[0] === 'RuRu----'  ← 目标的正确造法
// 旋转 ≠ 目标           ← 确认不需要 rotater
```

`src/ai/compiler/compile.mjs:568` 早就用它做规划了（`SHAPE_OPS.cutHalf(parentShapes[0])`）。

**所以这不是"需要新能力"，而是"已有的能力没接上"。**
prompt 里应该告诉模型的是一句可以机器生成的话：

> `RuRu----` = `cutHalf(RuRuRuRu)` 取左半。不需要旋转。

这类句子完全可以从 solver 自动生成，不需要手写。

## 17. 第五轮实验：形状代数接进 prompt 之后（2026-10-28T22:33）

把 `proto/solver.mjs` 的配方接进 prompt（新增 `src/agent/loop/recipe.mjs`）后重跑。

### 最直接的证据：`rotater` 从 4/5 变成 **0/5**

第四轮：5 次里 4 次坚持要 rotater。
第五轮：**一次都没提过 rotater**（grep 全文 0 命中）。

而且模型开始**引用配方**：

> "**The recipe needs** the mined four-quadrant shape cut in half, so I convert a segment
> of the miner-to-balancer belt runs in place into a cutter with the waste half..."
> （#3）

> "No fault is flagged yet, so **I follow the recipe**: cut the mined RuRuRuRu in the
> miner output line that feeds the balancer, sending the waste half to trash."
> （#4）

**配方确实被读了、被用了。** 这是五轮实验里第一次看到模型主动引用外部知识。

### 指标汇总（五轮）

| 轮次 | 关键改动 | 看到 | 选中全 3 | 精确 | rotater 误判 |
|---|---|---|---|---|---|
| 1 | — | 5/5 | 0/5 | 0/5 | — |
| 2 | 修夹具+引导 | 5/5 | 1/5 | 0/5 | — |
| 3 | 给矿图 | 5/5 | 2/5 | 0/5 | — |
| 4 | `$path_of` | 5/5 | 0/5 | 0/5 | **4/5** |
| **5** | **形状代数** | 5/5 | 1/5 | 0/5 | **0/5** ✅ |

### 剩下的失败：几何，不是语义

第五轮 5 次的失败码：

| # | 选中 | 结果 | 模型在做什么 |
|---|---|---|---|
| 1 | 0/3 | plan ok | 想给 cutter 供料（"给它一台矿机"） |
| 2 | 0/3 | `unsupported_macro:connect` | 想用 connect（实验脚本没接这个宏） |
| 3 | **3/3** | `occupied` | **正确引用配方**，选了 x=4/x=5 两条链，但 region 太宽 |
| 4 | 1/3 | `occupied` | 按配方选对了链，region 覆盖过多 |
| 5 | 0/3 | plan ok | 想加矿机 + 切割机 |

**#3 是最接近的一次**：三句都对——配方引用对、选的链对、机器对（cutter+trash/right）。
只差 `region` 覆盖了整段 6 格而不是要改的 3 格。

→ `occupied` 的原因是：链上有 balancer/机器，`replace_run` 的 region 不能跨过它们。

### 结论

**形状代数这一环成功了**（rotater 误判 4/5 → 0/5，模型开始引用配方）。

现在剩下的**全部**是几何表达问题：`$path_of` 给出的是一段连续带子的**全部格子**，
而 `replace_run` 需要的是一个**能放下 cutter 且不被 balancer 挡住的窗口**。
这需要"沿链取一个长度恰好合适的窗口"的能力，而不是"整段"。

这是一个**比前面几轮都更窄、更具体**的缺口。
