# 「静态经验文本」vs「动态观察面」—— 外部文献与项目内已有工作

> 2026-11-02。文献检索 agent。
> 触发问题：CAPACITY 段（现算产能数据）把「处理瓶颈」从 0/26 拉到 16/25（p=2.85e-07）。
> 那「加静态经验」会不会有类似效果？还是说 LLM 真正需要的是**当前具体数据**而非**一般性经验**？
>
> 标注：**【一手】**= 我读到了论文正文/表格的原文数字；**【二手】**= 只有检索摘要有数字，未核原表；
> **【空】**= 明确没找到。

## 1. 一句话结论

**外部证据支持「加经验」，但支持的是「检索具体的、已验证的成功片段」，不支持「手写的一般性心得」；
而且最强的效应都出现在「模型有一个知识缺口/错误先验」的场景，不是「模型已经知道但没被授权」的场景。**

三个能把结论钉住的数字（全部【一手】，来源见 §3）：

| 形态 | 效应量 | 出处 |
|---|---|---|
| 人工策划的 **procedural skill**（任务类级别、结构化、带代码） | **+16.2pp** | SkillsBench |
| **模型从成功/失败对比中自己提炼**的自然语言 insight | **+11pp**（HotpotQA 28→39） | ExpeL |
| **人手工写的** insight（最接近「手写玩法心得」） | **+4pp**（28→32） | ExpeL |
| **模型自己凭空生成** skill（不给经验素材） | **−1.3pp**（负） | SkillsBench |
| 「全面详尽」长度的经验文本 | **−2.9pp**（负） | SkillsBench |
| 一次给 4 条以上 skill | **+5.9pp**（vs 2–3 条的 +18.6pp） | SkillsBench |

⇒ **不是「经验有用 / 没用」，是「哪一种经验」。** 手写一般性心得是这张表里效应量最小、且最容易变负的那一档。

而且外部**没有**任何一篇做过「同等 token 预算下，静态经验 vs 动态现算数据」的正面 A/B（§6.4）。
这个对比是空白，只能我们自己做 —— 但做之前有 4 个来自文献的设计陷阱必须避开（§7）。

## 3. 外部关键研究（每条只写「对我们有什么用」）

### 3.1 ExpeL —— 最直接回答「经验是什么形态」

**ExpeL: LLM Agents Are Experiential Learners**（Zhao et al., arXiv:2308.10144）
https://arxiv.org/abs/2308.10144 ｜【一手】读了 Table 1、Table 2、§5.2

从成功/失败轨迹的**对比**中提炼自然语言 insight，测试时检索复用。关键消融（HotpotQA SR %）：

| 配置 | HotpotQA | ALFWorld |
|---|---|---|
| ReAct（无经验） | 28.0 ±1.4 | 40.0 ±0.3 |
| **人手工写的 insight** | **32.0** ±1.1 | — |
| 只给「经验检索」（具体轨迹） | 31.0 | 55.0 |
| 只给 insight（抽象规则） | 36.0 | 50.0 |
| ExpeL 全量 | **39.0** ±1.7 | **59.0** ±0.3 |
| insight 里再加「反思」 | **29.0** ±0.4（比不加还差） | — |
| 用 gpt-3.5 提炼 insight | 32.0 ±0.4 | — |

**对我们的三个用处**：

1. **手写经验 ≈ 半价经验。** 人写的 +4pp，模型自己从成败对比里提炼的 +11pp。
   差在「人写的是他觉得重要的，模型提炼的是它实际错过的」。
2. **抽象规则 vs 具体轨迹是任务相关的，不能一概而论。**
   HotpotQA（靠解读维基文本）insight 更好（36 vs 31）；ALFWorld（靠具体动作序列）轨迹更好（55 vs 50）。
   ⇒ 我们这种「靠具体几何动作」的场景，**应该更接近 ALFWorld，即具体案例优于抽象心得**。
   这个判断可以直接当实验假设。
3. **在 insight 提取里加「反思」是负收益**（29 < 39）—— 作者归因于反思产生幻觉污染了提炼。
   ⇒ 形态 (c)「模型自己复盘」如果做成自由反思，外部证据是**变差**。

**场景像不像我们**：中。ExpeL 是文本问答/文字游戏，我们是空间改造。但它的任务结构
（有明确成功判据、可反复试、错误可归因）和我们最像。

### 3.2 SkillsBench —— 给出了「经验文本」的剂量-反应曲线

**SkillsBench: Benchmarking How Well Agent Skills Work Across Diverse Tasks**（arXiv:2602.12670）
https://arxiv.org/abs/2602.12670 ｜【一手】读了 Finding 3/5/6/7 与 Table 4/6

87 任务，18 种模型-框架配对，配对评测。这是唯一一组**按「经验文本的长度/数量/来源」分层**的数据：

| 变量 | 结果 |
|---|---|
| 人工策划的 skill（含代码） vs 无 | **+16.2pp**（33.9% → 50.5%） |
| **模型自己生成** skill（不给素材） | **−1.3pp**（只有 Opus 4.6 +1.4，Codex+GPT-5.2 **−5.6**） |
| 一次给 2–3 条 skill | **+18.6pp** |
| 一次给 4 条以上 | **+5.9pp** |
| 「Detailed」长度 | +18.8pp |
| 「Compact」长度 | +17.1pp |
| **「Comprehensive」（详尽）长度** | **−2.9pp** |

**对我们的用处**：

- **长度有明确的负区间。** 「详尽」不是更好，是负的。作者归因：模型从长文本里提不出可执行的动作，
  且经验文本吃掉了上下文预算。我们已有同向的实测（`REDTEAM-EXPERIENCE-AB.md §4.2`：
  加 490 字经验正好把 CAPACITY 的 options 两行挤掉）。**两边的机制是同一个。**
- **数量拐点在 2–3 条。** 我们打算写多少条？`01-shapez-mastery.md` 有 10 条 —— 按这张表在悬崖外。
- **「模型自己生成经验」是负的**，且失败模式是「说得对但不可执行」（"用 pandas 处理数据" 级别的空话）。
  这正是 `REDTEAM-EXPERIENCE-AB.md §8.2` 猜的东西，外部证据支持那个猜想。

**场景像不像我们**：高（就「经验文本怎么设计」这一层）。它是软件/文档任务，但变量定义
（procedural / task-class / 结构化 / 可移植）比我们目前的设计更严。

### 3.3 GITM —— 游戏里「静态知识 + 静态记忆」的效应量（最大的一组）

**Ghost in the Minecraft**（Zhu et al., arXiv:2305.17144）https://arxiv.org/abs/2305.17144
【一手】读了 Table 3（40 局/配置）与 §4.3

累加式消融，ObtainDiamond 各里程碑成功率（%）：

| Goal Decomp | Feedback | **External Info** | **Memory** | 工作台 | 木镐 | 石镐 | 铁镐 | **钻石** |
|---|---|---|---|---|---|---|---|---|
| | | | | 57.5 | 32.5 | 5.0 | 0.0 | 0.0 |
| ✓ | | | | 90.0 | 90.0 | 67.5 | 2.5 | 0.0 |
| ✓ | ✓ | | | 97.5 | 95.0 | 77.5 | 20.0 | 5.0 |
| ✓ | ✓ | ✓ | | 100 | 100 | 100 | **57.5** | **35.0** |
| ✓ | ✓ | ✓ | ✓ | 100 | 100 | 100 | **95.0** | **67.5** |

- **External Info**（静态知识库：配方、"钻石在高程 Y 更常见"这类）= 铁镐 20→57.5（**+37.5pp**）、钻石 5→35（+30pp）。
- **Memory**（静态文本，存的是每个目标的历史成功 plan）= 铁镐 57.5→95（**+37.5pp**）、钻石 35→67.5（+32.5pp）。
- **Feedback**（动态观察：智能体状态 + 动作执行结果）= 工作台 57.5→90（+32.5pp），但**钻石 0→5**（几乎无效）。

这是文献里**唯一一组让我相信「游戏里的静态文本经验能给出 30–40pp」的数据**。但必须同时看清两件事：

1. **它填的是知识缺口。** 钻石在哪一层是 Minecraft 的**隐藏事实**，模型不知道就只能瞎挖。
   shapez 没有这类隐藏事实 —— 我们的速率、配方、槽位全在 `rules.mjs` / `op-templates.mjs` 里，
   而且 CAPACITY 段已经现算。**这是最关键的「像不像」判断：不像。**
2. **它是累加阶梯，不是头对头。** 后加的一环拿到的增益里含前面几环的底。而且
   Feedback（动态）与 Knowledge/Memory（静态）**作用在不同时间尺度**：动态管短程纠错，
   静态管长程路线。这个分工对我们有参考价值（见 §6.3）。

### 3.4 AWM —— 「文本形式的记忆」和「代码形式的记忆」差别很小

**Agent Workflow Memory**（Wang et al., arXiv:2409.07429）https://arxiv.org/abs/2409.07429
【一手】读了 Table 3/4/7/8/9

从历史轨迹归纳可复用 workflow 注入记忆。Mind2Web（GPT-4）：

| 配置 | Elem Acc | Step SR | Task SR |
|---|---|---|---|
| MindAct（无记忆） | 41.6 | 36.2 | 2.0 |
| AWM 离线 | 50.6 | **45.1** | **4.8** |
| **AWM，workflow 写成自然语言文本** | 51.2 | 45.4 | **3.6** |
| AWM，把 workflow 当成可调用宏（扩动作空间） | 51.8 | 46.4 | **3.6** |

**对我们最有用的一条**：**把 workflow 从「代码」改写成「自然语言」几乎不掉分**
（step SR 45.1 → 45.4，task SR 4.8 → 3.6）。作者原话：「do not find substantial performance variance
between workflows represented in text and code formats」。

⇒ **「经验必须是代码」这个担心可以放下。** 文本形态本身不是瓶颈，**内容（是否抽象、是否可执行）才是**。

另一条负结果（Table 8）：状态描述用「自然语言 + 过滤后 HTML」两套一起给，比只给自然语言**更差**
（step SR 34.6 → 32.9）。作者归因：上下文变长 + HTML 里 47% 情况没有正确元素，自相矛盾。
**这正是 REDTEAM 说的「补充上下文引入了错误的解释空间」的独立复现。**

### 3.5 Dynamic Cheatsheet / ACE —— 「静态 vs 演化」的关键区别

- **Dynamic Cheatsheet**（Suzgun et al., arXiv:2504.07952）https://arxiv.org/abs/2504.07952 【一手·摘要】
  一个持久、自我整编的记忆：Claude 3.5 Sonnet 在 AIME 上**准确率翻倍以上**；GPT-4o 在 Game of 24 上
  **10% → 99%**（因为它发现并复用了一段 Python 解法）；GPQA-Diamond +9%、MMLU-Pro +8%。
  但作者同时观察到：**错误启发式一旦进入记忆会被同样放大**，需要主动剪枝。
- **ACE**（arXiv:2510.04618）https://arxiv.org/abs/2510.04618 【一手·Table 3】
  把上下文当「可演化 playbook」，用**增量 delta** 更新而非整体重写。AppWorld 上比 ReAct +17.0pp；
  若去掉增量、改成整体重写则退化。作者命名了两个失败模式：
  **brevity bias**（越总结越丢细节）与 **context collapse**（反复改写侵蚀内容）。

**对我们的用处**：这是「静态经验」内部的第二个轴。同样是静态文本，
**「一次写死」和「每轮增量修订」是两种东西**，后者明显更强。
如果我们只做「写死一段经验」，等于选了弱的那一半。

### 3.6 「经验会被错误放大」—— 记忆管理的实证

**How Memory Management Impacts LLM Agents**（Xiong et al., arXiv:2505.16067）
https://arxiv.org/abs/2505.16067 【一手】读了 Table 1、§4.2、§5.3

三个领域（EHRAgents / AgentDriver / CIC-IoT），比较记忆的「加」和「删」策略：

| 策略 | EHRAgents ACC | AgentDriver SR |
|---|---|---|
| 固定记忆（不学） | 16.89 | 40.53 |
| **全加（add-all）** | **13.04**（比不学还差） | **32.48**（比不学还差） |
| 粗筛 | 31.35 | 37.03 |
| 严格筛 | **38.86** | **50.94** |

**全加记忆比不加记忆更差**。作者命名机制 `experience-following`：智能体会模仿检索到的旧轨迹，
于是**错误也被原样传播**；并按「删掉的记录」分析出 `misaligned experience replay`
（输入相似但输出不相似的记录会把模型带偏）。

**对我们的用处**：`REDTEAM-EXPERIENCE-AB.md §8.2` 猜「模型自复盘最可能负收益，因为本仓库宏失败率 14/16」。
**外部证据支持这个猜想，并给出了机制名称。** 所以 (c) 形态（自复盘）不该做成「把失败轨迹存下来」，
除非有产出相似度的筛选。

## 4. Voyager 的专门分析（最接近的类比，必须拆细）

**Voyager**（Wang et al., arXiv:2305.16291）https://arxiv.org/abs/2305.16291
【一手】读了 §2.2、§3.4、Table 1、Table 2、附录 A.4.3、附录 B.3

### 4.1 skill 是什么形态？—— **可执行 JavaScript 代码**，不是文本

论文原话（§2.2）：*"we represent each skill with **executable code** that scaffolds temporally
extended actions"*。附录 A.4.3 的实例是真实的 `async function craftWoodenPlanks(bot) { ... }`，
调用 `craftItem` / `mineWoodLog` 等下层函数，用 `bot.inventory.count(...)` 检查背包。

技能在库里存的是三元组（图 4）：**嵌入向量为 key（由 GPT-3.5 生成的程序描述算），程序本身为 value**。
检索时用 top-5。也就是说 —— **检索用的是自然语言描述，注入进 prompt 的是代码。**

| 维度 | Voyager | 我们要做的「文本经验」 |
|---|---|---|
| 注入物 | 可直接执行的函数体 | 自然语言句子 |
| 谁保证正确 | Minecraft 解释器：跑不通就报错 | 无。文本错了也照样被读进去 |
| 抽象层级 | 参数化的行为 | 断言/建议 |
| 复用机制 | 新技能**调用**旧技能（组合） | 无组合，只有拼进 prompt |
| 写入条件 | 必须**执行成功 + 自验证通过** | 无门槛 |

⇒ **不能直接类比。** Voyager 的 3.3× 是「一个可执行、已验证、可组合的行为库」对
「无行为库」的比值，不是「一段经验文本」对「无经验文本」。把这两件事混为一谈，
是这条文献里最常见的误读（我们自己的 `RESEARCH-A-PARADIGMS.md` 就犯了，见 §4.4）。

### 4.2 消融到底报了什么？—— **技能库那一项没有数字**

§3.4 原文（逐字）：

> • *Automatic curriculum* … The discovered item count **drops by 93%** if the curriculum is replaced with a random one.
> • *Voyager w/o skill library* exhibits **a tendency to plateau in the later stages**. This underscores the pivotal
>   role that the skill library plays…
> • *Self-verification* … Removing the module leads to a significant drop (**−73%**) in the discovered item count.
> • *GPT-4* … obtains **5.7×** more unique items.

**注意：课程学习有 −93%，自验证有 −73%，技能库只有一句「后期趋于平台」，没有任何数字。**
消融图（Fig. 9）是曲线图，正文没有给端点值。

唯一能给技能库定量的表是 **Table 1（科技树解锁所需提示轮数，3 次试验，越少越好）**：

| 配置 | 木 | 石 | 铁 | 钻 |
|---|---|---|---|---|
| **w/o Skill Library** | 7±2 (3/3) | **9±4** (3/3) | 29±11 (3/3) | **0/3** |
| Voyager 完整 | **6±2** (3/3) | 11±2 (3/3) | **21±7** (3/3) | **1/3** |

以及 **Table 2（零样本迁移到新世界，50 轮上限，轮数越少越好）**：

| 配置 | 钻石镐 | 金剑 | 岩浆桶 | 指南针 |
|---|---|---|---|---|
| w/o Skill Library | 36 (2/3) | 30±9 (3/3) | **27±9** (3/3) | **26±3** (3/3) |
| Voyager 完整 | **19±3** (3/3) | **18±7** (3/3) | 21±5 (3/3) | 18±2 (3/3) |

**读法（这才是诚实的读法）**：

1. 前三档科技树**互有胜负**（木 6 vs 7、石 11 vs 9）。真正的差距只在钻石档。
2. 钻石档是 **1/3 vs 0/3**。**n=3**。
3. 迁移表里「无技能库」在 2 个任务上**更快**（岩浆桶 27 vs 21、指南针 26 vs 18）。

⇒ 技能库的效应量在它自己的数据上只支持一条弱结论：**「对最长期的目标有用」**，
不支持「没有技能库就做不了」。这与我们 `03-agent-architecture.md §5.3` 的读法一致，
但与 `RESEARCH-A-PARADIGMS.md §2`「ablation 逐一拿掉，性能分别掉」的表述**不一致**——
后者过度归纳了。

### 4.3 Voyager 唯一确定的机制：**组合**，不是「经验」

论文给技能库的辩护是「**new skills built upon older ones**」——即木镐调木板、木板调原木，
层层复用，把长链条的搜索空间压扁。这是**程序组合**，不是「告诉模型一条心得」。

⇒ 如果我们要借 Voyager，借的应该是**「宏能调用宏」**那一半（`DIRECTION-FINAL.md` 阶段 1 已经在做），
而不是「往 prompt 里塞一段经验」那一半。

## 5. 反方向证据：prompt 变长的代价

### 5.1 长度本身就有代价（Chroma，18 个模型 / ~194k 次调用）

**Context Rot: How Increasing Input Tokens Impacts LLM Performance**（Hong, Troynikov, Huber, 2025-07）
https://research.trychroma.com/context-rot ｜【一手】读了全文

- 18 个前沿模型（GPT-4.1 / Claude 4 / Gemini 2.5 / Qwen3 等），**全部**随输入变长而退化，
  且退化**不是均匀的**。
- 关键设计：他们区分了「focused input（只给相关片段）」与「full input（相关 + 无关）」。
  模型在 focused 上几乎都做得对，在 full 上**一致退化**。
  作者定义机制：**「加无关上下文 = 给模型增加了『先检索再推理』这个额外任务」**。
- 干扰项的影响**随长度放大**，且不同干扰项之间差异很大。
- 结论原话：*"Whether relevant information is present in a model's context is not all that matters;
  **what matters more is how that information is presented**."*

**对我们的用处**：这条正好解释我们两轮 A/B 的反差。断点场景里，诊断的 `handles B34` 就是
focused input；再补 BELTS 段细节 = 把它变成 full input（`AB-PROMPT-RESULT.md` 里 A 臂 9/10、
B/C/D/E 臂掉到 40–70%，且模型开始把 B34 误读成「该扔掉的死端」）。
**这不是「模型不行」，是「我们给它加了检索任务」。**

### 5.2 位置比长度更阴险（Lost in the Middle）

**Lost in the Middle**（Liu et al., arXiv:2307.03172, TACL 2023）https://arxiv.org/abs/2307.03172
【一手】读了 §3.3

- U 形曲线：相关信息在**开头或结尾**最好，在**中间**最差。
- GPT-3.5-Turbo 多文档 QA 在 20 文档设置下最低 **52.9%**，**低于闭卷基线 56.1%**；掉幅 >20%。
- **扩展上下文版（16K）在 fits 的情况下与 4K 版几乎重合** ⇒ 窗口变大不等于更会用。

**对我们的用处**：经验段插在 prompt 的哪里，可能比写什么更重要。
`AB-PROMPT-RESULT.md` 里 B 臂的 CAPACITY 是插在 MACHINES 与 BELTS 之间的（**中间**），
如果按这条文献，插到 USER 段末尾（`## YOUR TURN` 之前）可能更好 —— 这是一个便宜的可测变量。

### 5.3 「更多例子」会让 prompt 更脆（GSM-IC，这条最反直觉）

**Large Language Models Can Be Easily Distracted by Irrelevant Context**（Shi et al., arXiv:2302.00093）
https://arxiv.org/abs/2302.00093 ｜【一手】读了 Table 3、Table 6、§5.4

- 基础集（100 题）上 CoT 微准确率 **95.0%**；加了**一句**无关信息之后，
  **macro 准确率只有 6.0%**（macro = 「不管加哪种干扰句都能稳定解出」的题目比例）。
  作者原话：**「fewer than 30% of the base problems are consistently solved after adding distractors」**
  （公认口径下最好的 LtM 也只有 18.0%）。
- **§5.4 的 Table 6 直接测了「加更多静态示例」**：

| 提示 | 示例数 | GSM8K（干净） | GSM-IC 2 步 | **GSM-IC >2 步** |
|---|---|---|---|---|
| CoT | 1 | 60.3 | 73.6 | **70.8** |
| CoT | 4 | **66.3** | **78.0** | **69.4** |
| CoT + 指令 | 1 | 58.8 | 79.0 | **76.0** |
| CoT + 指令 | 4 | **66.5** | 79.2 | **70.6** |

**读法**：4 条示例在**干净**基准上明显更好（60.3→66.3），但在**需要多步推理且含干扰**的子集上
**更差**（76.0 → 70.6，−5.4pp）。作者归因：「adding more exemplars can make the prompt **less robust**
as it leads to some overfitting」。

⇒ **这是「加静态示例」在受控条件下被证明「净负」的唯一一组数据，而且它测的正是我们关心的事**
（静态示例 vs 抗干扰能力）。我们的场景（181 实体、7 条诊断、0/163 带子可见）**永远处在含干扰状态**。

### 5.4 指令密度（IFScale）

**How Many Instructions Can LLMs Follow at Once?**（Jaroslawicz et al., arXiv:2507.11538）
https://arxiv.org/abs/2507.11538 ｜【一手·摘要】

500 条同时生效的指令，20 个模型。**最好的前沿模型在 500 条时只有 68% 准确率**，
且表现出「偏向靠前指令」的偏置。

**对我们的用处**：`SYSTEM_PROMPT` 已有 12 条规则，`01-shapez-mastery.md` 有 10 条候选。
按这条，规则/经验的**条数**本身就是自变量，不是「加得越多越好」。

## 6. 回答四个具体问题

### 6.1 有实证支持「静态经验文本能提升 LLM 游戏决策」吗？效应量多大？

**有，但强证据全部集中在「补知识缺口 / 可执行 procedure」，不在「一般性心得」。**

| 证据 | 形态 | 效应量 | 强度 |
|---|---|---|---|
| GITM 静态知识库（游戏） | 领域事实（配方、矿层） | 铁镐 **+37.5pp**、钻石 **+30pp** | 强【一手】，n=40 |
| GITM 静态记忆（游戏） | 每个目标的成功 plan 文本 | 铁镐 **+37.5pp**、钻石 **+32.5pp** | 强【一手】，n=40 |
| SkillsBench 人工 skill | 结构化 procedure + 代码 | **+16.2pp** | 强【一手】 |
| ExpeL 学到的 insight | 模型自己从成败对比提炼 | **+11pp** | 中【一手】 |
| ExpeL 只给具体轨迹 | 具体案例 | +3pp（HotpotQA）/ **+15pp**（ALFWorld） | 中【一手】 |
| **ExpeL 人写的 insight** | **一般性心得** | **+4pp** | 中【一手】 |
| SkillsBench 自生成 skill | 模型凭空写 | **−1.3pp** | 强【一手】 |
| SkillsBench「详尽」长度 | 长文本 | **−2.9pp** | 强【一手】 |
| Voyager 技能库 | **可执行代码** | 钻石档 1/3 vs 0/3，**无效应量** | 弱（n=3）【一手】 |

**结论**：如果我们的「静态经验」= 手写玩法心得（形态 b），外部预期效应量在 **+4pp 量级，
且很容易变负**。作为对照，我们的 CAPACITY 段是 0/26 → 16/25（**+64pp**）。
**这两者不是一个量级的东西，不该放在同一个 A/B 里比「哪个更有效」，因为它们测的不是同一件事。**

### 6.2 Voyager 的 skill 是什么形态？

**可执行 JavaScript 代码**（不是自然语言描述）。存进向量库的 key 是「描述文本的嵌入」，
value 是「程序本身」；检索 top-5 后**把代码原文拼进 prompt**。技能可组合（新技能调用旧技能）。

**和我们的「文本经验」是不是一回事？不是。** 差在四处（§4.1 表）：

1. **有解释器当裁判**：跑不通就报错，坏技能进不了库。
2. **参数化**：一个函数覆盖一类任务，不是一个断言覆盖一个观察。
3. **可组合**：技能能调技能，文本经验不能。
4. **有准入门槛**：必须执行成功 + 自验证通过才写入。文本经验**没有任何门槛**。

⇒ **Voyager 不能为「加一段经验文本」背书。** 它能背书的是「宏技能库 + 组合」，
那是 `DIRECTION-FINAL.md` 阶段 1 的事，与本问题无关。
另外 AWM 的 Table 7 显示：把 workflow 从代码改写成自然语言，**几乎不掉分**
（step SR 45.1 → 45.4）—— 所以「必须写成代码」这个担心是多余的，**内容对不对才是**。

### 6.3 有证据表明 prompt 变长会降低性能吗？阈值在哪？

**有，而且很硬。但「阈值」不是一个 token 数，是三个可操作的条件：**

| 条件 | 证据 | 具体数字 |
|---|---|---|
| **只要上下文里含无关内容，就会出现「先检索再推理」的额外任务** | Chroma（18 模型） | 全部模型在 focused → full 时一致退化 |
| **相关信息在中间时最差，可以差到低于「什么都不给」** | Lost in the Middle | GPT-3.5 20 文档最低 52.9% < 闭卷 56.1% |
| **静态示例变多 → 干净基准变好，抗干扰变差** | GSM-IC Table 6 | >2 步：76.0 → 70.6 |
| **经验文本长度有负区间** | SkillsBench Table 6 | 「comprehensive」= **−2.9pp** |
| **数量拐点在 2–3 条** | SkillsBench Finding 5 | 2–3 条 +18.6pp；≥4 条 +5.9pp |

**我们自己的实测阈值（比任何文献都更相关）**：
`REDTEAM-EXPERIENCE-AB.md §4.3` —— 真实存档 `L4-obs.json`（181 实体 / 163 带子 / 7 诊断）：

```
baseline chars 10217  /  targetChars 9800   ⇒ 已 over_token_budget
belts_shown = 0/163
CAPACITY   = 不存在（dropped-for-budget）
再加 1778 字符 ⇒ buildPrompt 抛 PROMPT_OVER_BUDGET（loop 直接 halt）
```

⇒ **在我们当前的真实存档上，「加经验」这个动作的预算是 0，甚至是负的。**
这不是理论风险，`prompt.mjs:1570` 抛的是异常而不是降级。

### 6.4 「经验 vs 观察面」有没有直接对比的研究？

## 7. 结论：我们的实验设计该改吗？

**该改，而且改动主要不在「加不加经验」，在「对照臂和判据」。**

### 7.1 外部证据直接支持的三条现成结论

1. **形态优先级**：具体案例（ExpeL 只给轨迹：ALFWorld +15pp）> 抽象心得（+10pp）> 人写心得（+4pp）
   > 模型凭空生成（SkillsBench −1.3pp）。
   ⇒ 用户列的四种里，**(a) 案例库 > (b) 手写心得 > (c) 自复盘**，而 (c) 有实测负收益的先例。
2. **长度/数量有明确的负区间**：≥4 条从 +18.6 掉到 +5.9；「详尽」长度 −2.9。
   ⇒ 经验段**硬上限 3 条、每条约一句话**。这不是美学，是有曲线的。
3. **位置比长度更阴险**：Lost in the Middle。⇒ 经验段放 USER 段末尾，别放中间。

### 7.2 必须改的（不做则实验结果无效）

沿用 `REDTEAM-EXPERIENCE-AB.md §7` 的四条，我在此基础上按文献**加两条**：

| # | 改动 | 依据 |
|---|---|---|
| 1 | **主判据从 utilization 换成真实产出增量** | 红队实测：utilization 从 27.8% 刷到 55.6% 而真产出归零 |
| 2 | **判据必须真的过宏**（`resolveRefs` + 逐条 `ok:true`） | 红队实测：B2 的 23 条可解析样本里只有 2 条能跑通，且这 2 条都是错的 |
| 3 | **对照臂换成 `B2 vs B2+经验`**，不是 `A2 vs A2+经验` | 红队 §1.3；Chroma「focused vs full」——否则测的是「加无关内容」 |
| 4 | **先修 RECIPE 与 CAPACITY 的冲突** | 否则两段互相抵消，效应量被吃掉 |
| **5（新增）** | **经验段必须先解决预算**：真实存档已是 0/163 带子、加 1778 字抛异常 | SkillsBench「comprehensive −2.9pp」；Chroma；我们自己的 `§4.3` |
| **6（新增）** | **每臂 n ≥ 20**，且用同一批固定场景 | `AB-PROMPT-RESULT.md` 的 EXCEPTION 段 p=0.0449 在 n=20 时未复现 |

### 7.3 我认为实验设计**最该改的一处**（文献 + 内部证据的交点）

**把「经验」的定义从「一般性心得」改成「纠错型断言」，并且专门针对 `BALANCER-PRIOR-FINDING.md`。**

三个理由叠在一起：

1. **内部**：48/48 条 thinking 都假设「balancer 会分流」，而源码证明是「先填满左槽」。
   这是一个**可确证、可一句话表达、且已经在产生错误动作**的错误先验。
2. **外部**：ExpeL 的 `hand-crafted` 只 +4pp，而它的机制正是「人觉得重要的」；
   `BALANCER-PRIOR-FINDING.md` 已经论证了「纠错型」不是「人觉得重要」，是「模型确实错了」。
   两个方向一致：**只有当经验瞄准一个真实存在的错误先验时，它才有 ExpeL 那 +11pp 的机制**
   （从成败对比里提炼的东西之所以更强，就是因为它必然是「模型错过的东西」）。
3. **可测性**：这条经验是**外部给定**的（源码出处 `balancer.js:179-200` / `item_ejector.js:117-125`），
   不是模型自生成，也不是我们的猜测 —— 正好落在 SkillsBench「人工策划 +16.2pp」那一档，
   而不是「自生成 −1.3pp」那一档。

**可执行的检验（两条，分开跑）**：

- **H1（纠错效应）**：`B2` vs `B2 + 一句 balancer 更正`。判据：A2 臂里那 14/26 次
  「给 balancer 空 secondary 接垃圾桶」的动作消失率。如果消失 ⇒ 那 14 次是**知识问题**不是能力问题。
- **H2（技巧 vs 纠错）**：`B2 + 纠错型经验` vs `B2 + 技巧型经验`（同等字数）。
  如果纠错型显著更大 ⇒ 经验库的设计原则改成**「先找模型错在哪，再写更正」，而不是「先攒技巧」**。
  这条直接决定 (a)/(c) 该攒什么。

### 7.4 我认为**不该**做的事

1. **不该把「静态经验 vs 动态观察面」做成头对头 A/B。**
   文献里没有先例（§6.4），而且两者作用的时间尺度不同（GITM：动态管短程、静态管长程）。
   把它们放进一个 A/B，测出来的差异会被「场景选的是短程还是长程」混淆。
   **应该做的是「在 B2 之上加经验还能不能再加」，而不是「经验 vs CAPACITY 谁强」。**
2. **不该做形态 (c)「模型自由复盘」。** ExpeL（+反思 → 29 < 39）、SkillsBench（自生成 −1.3pp）、
   记忆管理（add-all 13.04 < fixed 16.89）**三篇独立**都指向负收益。要做也只能做成
   「带产出相似度筛选的严格筛选」（38.86 vs 13.04），那是另一个工程量。
3. **不该引用 Voyager 的 3.3× 来论证「经验有用」。** 那是代码技能库对无技能库、
   且技能库那一项的消融**原文没给数字**（§4.2）。
4. **不该超过 3 条经验。** SkillsBench 的拐点在 2–3 条，我们已有的 12 条规则 + 3 条经验 = 15 条，
   IFScale 说这是自变量。

## 8. 如果我是错的，最可能是哪里错

1. **GITM 的 +30~37pp 可能不可迁移。** 它填的是 Minecraft 的隐藏知识（钻石在哪一层）；
   shapez 没有隐藏知识，配方/速率全在 `rules.mjs`，产能已经现算。
   我用它来支持「静态经验能到 30pp」，**这是全篇最大的外推**。
2. **SkillsBench 的 +16.2pp 是软件/文档任务。** 它的 skill 里含可执行脚本；
   纯文本 skill 的效应量没单独报。我把它归到「procedural」档，可能高估。
3. **「手写心得 +4pp」来自 ExpeL 一个环境（HotpotQA）的一组消融**，n 未报。
   我把它当成基准线，可能低（或高）估。
4. **Voyager 的读法。** 我说「技能库只对最长期目标有用、无效应量」——
