## 1. P0 — 补完已验证但未落地的部分

### P0-1 隧道实机验证 ✅ 已完成（2026-10-26）

隧道以前是"源码 + 存档 + 桩测试"三件套，没有一次实机运货。现在有了。

| 命题 | 证据 |
|---|---|
| 物品穿过隧道 | arm A 送达 **+8**，中间 3 格全空（带子无法跨越） |
| 送达不是装置自产的 | arm C 同装置无隧道，送达 **0** |
| 粘贴不毁隧道下的带子 | arm D 贴完 **3/3** 存活 |
| 该检查能变红 | arm E 走未保护路径，**3/3 被删**（C4 复现） |

arm E 是关键：没有它，arm D 的绿是假的。完整记录见
[`tmp/TUNNEL-VERIFIED.md`](tmp/TUNNEL-VERIFIED.md)，脚本
`live/exp-tunnel-transport.mjs` + `live/exp-tunnel-falsify.mjs`，
原始数据 `live/results/tunnel-transport.json`、`tunnel-falsify.json`。

**同时确认**：code 22/23 与 rv 0/1 的对应是一手观测；sender 与 receiver 的 `rotation`
**相同**，方向靠 code 区分。

**§1.1 实测暴露的新缺陷（转入 P1-4）**：用真实存档种子（60908）编译 `CgScScCg` 失败，
`planMinerColumns` 把 5 台矿机的相对偏移硬定死（-12/-8/-4/0/+4），真实地图不可能满足。
`--range 256` 结论不变，是几何硬约束而非搜索范围。离线用的 seed 43391 恰好满足，所以一直是绿的。

### P0-2 `--tunnels` 默认策略

现在隧道是 opt-in（默认关），因为要保证既有目标逐字节不变。但既然隧道已经证明安全：

- **问题**：该不该默认开？
- **权衡**：默认开会改变 7 个目标里某些的布局（能用隧道的地方会用），破坏已记录的基线数字；默认关则用户必须知道有这个参数。
- **建议**：先保持 opt-in，但在 README 和目标表里写清楚"哪些目标需要 `--tunnels`"。等 P1 做完再重新评估。

### P1-3 矿机落点必须逐台独立

**这是 P0-1 实测发现的缺陷，优先级高于 P1-1/P1-2**——它让"能编译"直接变成"不能编译"。

**现状**：`planMinerColumns` 先把所有矿机的相对偏移钉死成一条等距直线
（`CgScScCg` 是 rel -12/-8/-4/0/+4），然后只做**整体平移**去匹配资源图。

**这是几何硬约束，不是搜索范围问题**：用真实存档种子 60908 编译 `CgScScCg` 直接
`ok:false, no-resource-in-range`；扩大到 `--range 256`（每种矿都有上千格可选）结论不变。

真实地图的矿簇是随机散布的，不可能恰好满足"五种矿相对某锚点呈等距排列"。

**为什么一直没暴露**：离线测试固定用 seed 43391，而 43391 恰好满足了这个关系。
这是"离线样本单一"的典型代价——绿的次数多不代表覆盖广。

**要做**：
1. `planMinerColumns` 逐台矿机独立选矿，放弃刚性相对偏移
2. 多台矿机的馈线各自独立走通道（这本来就是路由层该处理的事）
3. 加入至少 3 个不同种子的回归测试，防止再次退化成"只有一个种子能跑"

**完成判据**：`CgScScCg` 在 seed 43391 与 60908 上都能 `ok:true`。

## 2. P1 — 让编译器真正可用

### P1-1 一次编译覆盖多个目标

**现状**：`compilePlan` 一次一个 goal，每次都要重新选址、重新布局。真实玩家会想要"同时生产 CrCrCrCr 和 CpCpCpCp"。

**为什么值得一提**：这是"能不能真的当玩家用"的分水岭。单个目标的编译器是 demo，能同时跑几个才是工具。

**难点**：两个目标共享矿机会打起来；hub 的 16 个入口要分配；布局要互不重叠。

**建议起点**：同一个 DAG 的多个终局形状（比如 `CuCuCuCu` 和 `--CuCu--` 共用 Cu 矿），先做这个子集。

### P1-2 吞吐量真正达标

**现状**：`stats.estThroughputPerSec` 取的是 `min(节点速率)`，没有考虑：
- 一条带子要喂多台机器时的分流
- 拐角按 0.78 折算（已记但没进代价函数）
- stacker 0.25/s 意味着一台满带要 8 台 stacker

**要做的**：V7 从"报告 min 速率"升级为"验证这条链真的能输出那么多"。这需要**布局级**的吞吐计算，不只是节点级。

**完成判据**：构造一个目标，让 V7 说"能出 X/s"，实机跑一段时间，测出的产量与 X 误差 < 10%。

### P1-4 增量对接

**现状**：`v1 只支持全新址`。真实玩家的存档里已经有工厂，新布局必须能接进去。

**为什么难**：要读现有世界的连通关系、找到可用的空位、避免切断既有物流。这是 `--hub` 那套东西的自然延伸。

## 3. P2 — 扩展可解范围

### P2-1 多层目标

`out-of-scope:multilayer` 是当前最大的能力缺口。多层需要：
- 垂直堆叠的编码（蓝图里层怎么表示）
- 跨层的物流（隧道只能同层）
- 布局算法从 2D 变 3D

**建议**：先调研游戏里多层是怎么实现的（`recon/` 有源码），确认可行性再动手。

### P2-2 更多机器变体

现在只出 `rv=0` 的机器。`cutQuad`（4 路切割）、`painterDouble` 等变体能大幅简化布局，但它们的 rv 编码没有实机凭据。

**先决条件**：需要一次针对性的实机实验——在游戏里放这些变体，读存档看 code。这与隧道那次实验是同一个套路。

## 5. 工作纪律（来自本轮的教训）

### 必须做的

1. **"green ≠ true"**：任何"能跑"的结论都要有实机凭据或可证伪的对照实验
2. **先量后改**：本轮 `CgScScCg` 卡了很久，真正解决是先用探针量清"挡几格"，而不是瞎调参数
3. **改动要有反证**：每次加测试，都要验证"去掉这个修改，测试会红"
4. **实机实验用专用存档**：不要每次 `new_game`（本轮造了 19 个 level-1 存档）

### 不应该做的

1. **不要用 `sed`/正则改源码**：本轮两次把文件改坏。用 Read + Edit
2. **不要假设"负坐标不合法"之类的隐式前提**：本轮这个假设出现了三次，每次都导致下游错位
3. **不要在测试桩里省略真实约束**：`pasteStubRoot` 缺少 `performImmutableOperation` 分支，导致 `else` 分支的 bug 没被发现

### 关于 Agent 的使用

本轮派了 9 个子 Agent，经验：

- **写代码的 Agent 要给出精确的文件归属**，否则会互相覆盖
- **规划 Agent 很有价值**（`PLAN-CGC.md` 推翻了我的两个错误假设），但要给它**先验门**（"先跑探针验证可行，再写方案"）
- **Agent 会做 `git stash` 这类破坏性操作**，必须在任务书里禁止
- **Agent 完成不等于交付**：`Plan` 类型不写文件，结论留在 transcript 里

## 6. 建议的下一步顺序

### 6.0 总方向：**目标是像真人一样玩游戏**

这是用户 2026-10-26 给出的总方针，优先于下面所有条目：

> 先开一个存档用一个角色玩到底，**根据当前存档、等级要求、矿物资分配去规划**，
> 包含造哪些设施、如何接线。后续任务基于它来规划。

这条改变了两件事：

1. **不再执着于"把所有目标都编译通"**。真正的成功判据是：从 level 1 开始，
   在真实世界里一关一关往下打，每关都靠"看懂当前局面"来决定造什么。
2. **规划必须以存档状态为输入**。现在 `compilePlan` 只吃 `{goal, seed, hub}`；
   要做成真玩家，它得吃"当前有什么、缺什么、hub 要什么、下一步解锁什么"。

由此暴露的现状差距：

| 能力 | 现在 | 要做成"玩得下去"需要 |
|---|---|---|
| 关卡推进 | ❌ 无 | 读到 goal → 规划 → 建 → 等交付 → 下一关 |
| 已有工厂复用 | ❌ v1 只支持全新址 | 在现有布局旁接新产线（P1-4） |
| 多目标并存 | ❌ 一次一个 | 同时维持几种形状的产线（P1-1） |
| 解锁门控 | ⚠️ 只报告不阻断 | 按当前解锁决定能造什么（`--enforce-unlocks`） |

**第一个里程碑**：在专用测试存档（`7c93b3dd`，当前 level 2）上，
用 agent 把 level 2 → level 3 走通，全程不手工干预。

```
P1-3 矿机落点独立      ← 实测暴露的硬缺陷，让"能编译"变成"不能编译"
  ↓
P0-3 仓库卫生          ← 便宜，顺手做
  ↓
P1-5 关卡循环（新）     ← 按 §6.0 的总方向：读局面 → 规划 → 建 → 推进
  ↓
P1-1 多目标编译        ← 价值最高的能力扩展
  ↓
P1-2 吞吐量真实验证    ← 让"能跑"变成"能产出"
  ↓
P1-4 增量对接          ← 让它能用在真实存档上
  ↓
P2 / P3                ← 视需求推进
```

**如果只做一件事**：P1-3。隧道已经证明能用，但真实种子上 `planMinerColumns` 的刚性
偏移让 `CgScScCg` 根本编译不出来——修好之前，隧道在真实世界里没有上场机会。
