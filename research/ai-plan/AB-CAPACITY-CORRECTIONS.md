## 过计 1：n 里混进了重跑记录

`results-v2.json` 有 51 条，但只有 **46 个不同的 `arm#rep`**：

```
A2#3  {parse_ok:false, stop:'max_tokens'} + {parse_ok:true}   ← 同一次试验
B2#4  同上
A2#9  {err:'fetch failed'}                + {parse_ok:true}
B2#16 同上
A2#16 同上
```

`runner-v2.mjs:53` 的 `done` 集合跳过**已成功**的 `arm#rep`，
所以失败后重跑会产生两条记录，**属于同一次试验，不是独立样本**。

| 口径 | A2 | B2 |
|---|---|---|
| 上一轮报告（记录条数） | 26 | 25 |
| **独立样本（正确）** | **23** | **23** |

p 值影响：`0/26 vs 16/25` → p=2.85e-07；`0/23 vs 16/23` → p=4.95e-07。
**结论方向不变**（都远低于 1e-5），但 n 必须更正。

## 过计 2：7 条命中把 cutter 插在了**产品段**上

复核者按 `belt-rules.mjs` 从 `obs` 实测了整条拓扑（37 条带子全部验证闭合），
这个场景有三段：

|---|---|

| **产品段** | `C1.right → B11 → B35 → B12..B14 → B36 → B15..B30 → H1` |
| **废料段** | `C1.left → B37 → T1` |

B2 的 16 条命中落在哪：

| 落点 | 条数 |
|---|---|
| 纯原料段 | **9** |
| **纯产品段** | **7** ← 问题在这里 |
| 横跨两段 | 1 |

产品段上的货是 `RuRu----`（已经切好的半片）。再切一刀得到 `----RuRu`，

⇒ **模型在「加 cutter」这件事上做对了，但在「加在哪」上错了 44%。**

```

```

**仍然显著（p≈1.5e-3），但比 2.85e-07 弱 4 个数量级。**

## 顺带发现的两个实现缺陷

### 缺陷 1：`arms.mjs:judge()` 无法处理嵌套的 machine 参数（低危）

```js
const m = String(a.machine || "");   // machine:{kind:"cutter"} → "[object Object]"
```

合法形态 `{"machine":{"kind":"cutter"}}` 会被漏判。
本例里被 `says_add_cutter` 兜住了（`B2#21`），但**如果模型只写结构化参数不写 `say`，就会漏判**。

**修复**：改用 `JSON.stringify(a.machine)` 或递归取 `kind`。
（`v3.mjs` 的 `judge()` 已经这么做了 —— 见 `.tmpverify/ab-correction/v3.mjs`。）

### 缺陷 2：夹具里还有一处自相矛盾（V2 声称已修，实际没修干净）

```json
window_seconds: 60,
delivered_slices: [{"RuRu----":30}, {"RuRu----":30}],   ← 共 60
delivered_per_sec: {"RuRu----": 0.5}                     ← 60/60 = 1.0，不是 0.5
```

`src/mod/shapez-ai-bridge.js:644` 明确 `slice_seconds = 10`，
`delivered_per_sec = deliveredSum / (wantSlices × sliceSecs)`。自洽的读法：

- 2 片 × 10s = 20s ⇒ **3.0/s**
- 按 `window_seconds: 60` ⇒ **1.0/s**

**两种读法都不是 0.5。** `v2.mjs` 只补了 `produced_total`，没动 `delivered_slices`。

这不影响 A2/B2 的对照（两臂吃同一份数据），**但意味着「V2 场景已自洽」不成立**，
而且 CAPACITY 段说的 0.5/s 与 PRODUCTION 段仍然打架 ——
和上一轮那个「假信号」是同一类问题，只是换了位置。

## 这些更正**改变**的

1. **效应量**：从「64% 处理瓶颈」降到「39% 改对了」
2. **n**：从 26/25 降到 23/23
3. **模型的能力判断**：它不是「知道该加 cutter」，是**「知道该加 cutter，但有一半加错了位置」** ——
   这是**空间推理**问题，不是知识问题。对 C 实验的设计影响很大：
   如果经验形态只教「瓶颈了要加机器」，不教「加在瓶颈机器**之前**」，
   那它只能改善 39%→？，改善不了「加错位置」这一半。
4. **`v3.mjs` 的判据必须同时看 `handledBottleneck` 和「加在哪」** —— 我在纠错实验里
   只判了前者，这是个已知缺口（见 `EXPERIENCE-AB-RESULT.md` 的诚实边界）。
