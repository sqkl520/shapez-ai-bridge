# P11 —— 关卡变更检测：让「目标换了」变成系统看得见的事

日期：2026-11-04
前置：P8（度量）、P9（回滚）、P10（跨 run 记忆）。这一轮补上「世界升级」这条线。

---

## 0. 起点

用户贴图那次的直接成因：世界从 level 5（`Cu----Cu`）升到 level 6（`Cu------`），
旧产线**没有拆**，变成 41% 到不了 hub 的死带子，模型还在修那条造着上一个 level 形状的线。

系统里**没有任何东西注意到「目标变了」**。更糟的是，即使注意到了，`GOAL_MISMATCH`
那条检查也会直接 halt —— 等于「赢一局就死机」，还会丢掉本次 run 已经收集到的全部经验。

---

## 1. 关键设计：两种情况必须分开

两者都是 `obsGoal !== goal`，但含义完全相反：

| 情况 | 判据 | 处置 |
|---|---|---|
| 调用方传错 goal（runner 硬编码） | 记忆里的上次目标 != 调用方传的 goal | **halt**（配置错误，继续跑会用错误诊断改世界） |
| 世界自己升级了 | 记忆里的上次目标 == 调用方传的 goal | **继续**，采纳新目标 |

```
① rememberedGoal === goal（调用方没变）
② goal !== obsGoal（世界变了）
两者同时成立 ⇒ 世界升级
```

记忆读不到 / 这个世界第一次跑 ⇒ 退化为 halt。
「没见过这个目标」与「调用方给错了」无法区分，而误判成升级会让 loop
在**错误目标**上继续改世界 —— 那更危险。

### ⚠️ 这里踩过一个条件恒假的坑

初版写成 `remembered.last_goal === obsGoal`（记忆里的目标 == 世界现在的目标）。

**那个条件恒为假** —— 如果记忆里已经是 `obsGoal`，就根本进不了这个分支
（前提是 `goal !== obsGoal`）。于是升级检测形同不存在，而且**不报任何错**。

正确的对照物是**调用方传的 `goal`**，不是世界的当前目标。
这个 bug 是加临时探针打印实际值才发现的（`selfMoved: false`）。

---

## 2. 升级时要做的三件事

1. **配方作废重算**（`st.recipe = null`）。旧配方是旧目标的解法，
   拿它判 `PROCESSOR_REQUIRED` 会给出**错误的机器建议**。
2. **`curGoal` 切换到新目标**。`opts.goal` 不改（那是「这次 run 想解决什么」），
   但所有下游（diagnose / prompt / 记忆落盘 / verify）都改用 `curGoal`。
3. **记一条 `GOAL_CHANGED`**（通告，不是阻塞诊断）。

## 3. 残线识别：`OBSOLETE_LINE`

### 为什么不能用带子拓扑认

实测两张**正常存档**：

```
L4: 到 hub 140/163 = 86%，死 23
L5: 到 hub 133/160 = 83%，死 27
```

死带子比例都在 14–17%。拿比例当判据会把正常世界判成病态。

### ★ 60 秒窗口的死角（交叉评审指出，已实测确认）★

第一版只用 `production.produced_total`。它是**最近 60 秒**的窗口量
（`shapez-ai-bridge.js:738-759`，`slices:6 × sliceSecs:10`）。

而残线的**典型终局恰恰是「旧线已经停了」**——用户贴图那次的现场是
「40 条入口带子 0 条有货、带上货 0」。实测：

```
produced_total = {}                 → 一条都不报   ← 真实场景
produced_total = {"Cu----Cu": 0}    → 一条都不报
produced_total = {"Cu----Cu": 25}   → 报（但这时它还在跑，不算最严重）
```

**它只在旧线还没死时有效，而那时它并不算问题。** 这是证据源选错，不是阈值没调好。

### 两路证据，互补

| 函数 | 证据 | 覆盖的场景 |
|---|---|---|
| `findObsoleteLines` | 60 秒产出窗口 | 旧线**还活着** —— 唯一能及时拦住它的时刻 |
| `findStoredObsolete` | `hub.stored_shapes` 累计账本 | 旧线**已经停了** —— 窗口归零后的唯一证据 |

账本法有个陷阱：`stored_shapes` 混着**配方的中间产物**。

```
L4（目标 RuRu----）stored = {CuCuCuCu:46, ----CuCu:47376, RuRuRuRu:112866}
L5（目标 Cu----Cu）stored = {CuCuCuCu:46, ----CuCu:87446, RuRuRuRu:177830, RuRu----:31204}
```

拿「stored 里有非目标形状」当判据，会把**任何**正常存档判成残线。
所以要求：这个形状**不在当前配方闭包内**（`recipe.steps[].hash` 全部排除）。

### 判据

| # | 条件 | 理由 |
|---|---|---|
| 1 | `produced_total[shape] > 0` 且 `shape !== goal` | 它在**产**东西，不是死线 |
| 2 | `delivered_total[shape]` 为 0 或缺失 | 一件都没进 hub |
| 3 | 占全部产出 ≥ 5% 且 ≥ 10 件 | 一两次调试残渣不是「一条线」 |

目标读不到时**不报** —— 「不知道目标是什么」不等于「造的东西是错的」。

实测（用户贴图那次的真实数字）：

```
Cu----Cu ×25 (89% of all output) but 0 of it ever reached the hub — Cu----Cu is not the goal (Cu------)
```

### 与 `NO_PRODUCTION` 的分工

- `NO_PRODUCTION` 说「**整体**没有产线在造目标」⇒ 让模型去**建**
- `OBSOLETE_LINE` 说「有这么一条线在造**别的**东西、而且零交付」⇒ 让模型先**拆**

动作方向相反的两件事合成一条，模型会在「先建」和「先拆」之间摇摆 ——
这正是它每轮追不同诊断、不收敛的原因之一。

### ★ 只在换关那一轮报 ★

第一版每轮都报。残线在拆掉之前每轮都存在，每轮一条诊断会吃掉预算，
还会稀释真正重要的那几条。改成只在 `st.goalChanged` 那一轮报 ——
那正是「最容易继续在旧线上修」的时刻。

## 3b. ★ 授权拆除：系统叫它拆的，不许反过来撤销它 ★

这是整轮里最重要的一条，也是**实测确认过的反向激励**：

```
1. OBSOLETE_LINE 说「这条线是残线，拆掉它」
2. 模型照做 → 删掉几条能到 hub 的带子
3. classifyNetEffect 判 regressive（必然 —— 它拆的就是那些带子）
4. 连续第二次 regressive → decideRollback 判 rolling_back → 系统撤销拆除
```

实测验证过第 3、4 步：拆两条活线 → `regressive` → 连续第二次 `rollback: true`。

**结果是「照着系统的话做，系统再把你的动作撤销」，比不提示更糟。**
它会让模型学到「拆线会被惩罚」，从而彻底不动手。

旁证（真实的调用分布，1405 次）：

```
connect 373 | trash_unused 229 | replace_run 118 | insert_machine 6 | remove_run 2
```

模型本来就不愿拆（2 / 1405）。再撤销它的拆除，等于把这条路彻底封死。

修法：`decideRollback` 新增 `sanctionedTeardown`，返回第五档 `sanctioned`（不撤）。

判据（`isSanctionedTeardown`，**四条**同时成立）：

1. 本次 tx **确有删除**；
2. 被删的**都**是带子/隧道（拆机器不算 —— 机器可能正在被复用）；
3. 存在残线证据；
4. **本次 run 确实换过关**（`levelChanged === true`）。

第 2 条用「都」而不是「有」：既拆带子又放机器是**施工**，
施工有自己的 `converging` 豁免，不该走这条。

### ⚠️ 第 4 条是血的教训（关机前那次全量回归抓到的）

最初只有前三条。结果：`stored_shapes` 里存着**所有更早关卡**的遗留物 ——
L4 上就有 `CuCuCuCu:46` / `----CuCu:47376`。于是**每个世界**都能算出残线证据
⇒ 授权拆除恒成立 ⇒ **回滚永不触发**。

一次全量回归把它暴露出来：`E11（撤销之后 prompt 必须说 reverted）`
因为「前提：这次 run 必须真的撤销过」不成立而变红 ——
也就是说，我为了修一个反向激励，把 P9 的整个安全网废掉了。

修法：账本法与授权拆除**都**强制要求 `levelChanged === true`。
默认 `false`，宁可少报，不许误报。

实测对照（L4 夹具）：

```
未换关: findStoredObsolete(...) → []                     ← 正常
换关了: findStoredObsolete(...) → [----CuCu, CuCuCuCu]   ← 有旧目标遗留
```

教训写在这里不是为了记流水账：**这类「为了不误伤 A 而让 B 永远不生效」的
开关，只有端到端用例能抓到。** 单元测试里两种输入都各自正确。

## 4. ★ 指纹必须排除环境性诊断 ★

`NO_PROGRESS_3X` 的判据是「同一指纹第 3 次 ⇒ halt」。它要抓的是
「模型反复撞同一个墙」，所以指纹只能含**模型能改变**的东西。

`OBSOLETE_LINE` / `GOAL_CHANGED` 不是：

- 残线在拆掉之前**每轮都存在** ⇒ 进了指纹，第 3 轮必然 halt，
  而那时模型可能刚开始动手拆 —— 等于在它来得及行动前判死。
- `GOAL_CHANGED` 描述的是**世界自己**做的事（升级），算进「模型没进展」是错的。

所以：

```js
const ENV_CODES = new Set(["OBSOLETE_LINE", "GOAL_CHANGED"]);
const fpDiags = diagnoses.filter(d => d && !ENV_CODES.has(d.code));
const fpNow = fingerprintOf(fpDiags.length ? fpDiags : diagnoses);
```

**两处都要用过滤后的列表** —— `countFingerprint` 内部自己调 `fingerprintOf`，
只在上游算 `fpNow` 时过滤、却把全量传给 `countFingerprint`，那次过滤就白做了。
（这类「算了但没用上」的 bug 在本项目出现过，所以代码里显式写了注释。）

全是环境码时退回全量：空列表的指纹是常量，那会让第 3 轮必然 halt。

## 5. ★ 两个静默丢字段的真 bug ★

加 `worlds` 字段时发现的：

1. `loadMemory` 返回 `{version, goals}` —— 任何**其它**顶层字段被丢掉。
2. `mergeMemory` 返回 `{version, goals}` —— 同一类 bug 的第二处。

后果：`worlds` 这一轮刚写、下一轮就被自己的 merge 抹掉，**而且不报错**。
换关检测于是永远读到 `undefined`，功能形同不存在。

两处都改成了显式带上 `worlds`，并各写了一条测试钉住（V22 / V23）。
**加顶层字段时一定要回到这两行。**

## 6. 世界 key 必须一次定死

`readWorldKey` 最初读闭包里的 `st.lastObs` —— 那个引用在循环里每轮都被换掉，
读到的是「当下的世界」而不是「算 key 那一刻的世界」。

而退化的 key（`hubuid:<uid>|L<level>`）**含关卡号**：升级之后 key 就变了，
`worlds` 里那条记录永远匹配不上 ⇒ 换关检测失效。

修法：`obs` 显式作为参数传入，key 在首轮 observe 之后**只算一次**。

## 7b. 交叉评审改掉的三处（值得记下来）

这一轮的 5 个 Agent 里只有红队/批判那个跑出了结果（其它 6 个输出始终 0 字节）。
它给出的三条批评我逐条实测核实，**全部成立**：

1. **窗口证据有死角**（见 §3）—— 我实测 `produced_total={}` 一条不报，确认。
2. **反向激励**（见 §3b）—— 我实测拆活线 → regressive → 连续第二次 rollback，确认。
3. **`worldUpdate` 只在 finally 写** —— 全新 runDir 时中途升级会退化 halt。
   修法：首轮 observe 之后立即写一次，同 run 内可自证。加了 G13/G14 两条测试。

它另外几条我核实后**没有采纳**：

- 「删掉 `OBSOLETE_LINE` 诊断码，只留 `GOAL CHANGED` 段」—— 两路证据的场景不同
  （窗口 vs 账本），删掉诊断码会让「线还活着」这个唯一能及时拦住的时刻失去候选卡片。
  改成**只在换关那一轮报**，既省预算又保留能力。
- 「`produced_total` 换成 `stored_shapes`」—— 单独用账本会把中间产物误判成残线
  （实测：`CuCuCuCu`/`----CuCu` 每次挖矿都进 hub）。改成两路并用 + 闭包排除。
