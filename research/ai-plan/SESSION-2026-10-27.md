# 2026-10-27：L4 端到端打通 + 三个假绿修复

## 主结果

**level 4 → level 5。** `RuRu----` 从 0 交付到 70（实际入库 597），关卡推进。

做法只有 **+2 个实体**：在现有钌线的向上段插一台切割机。

```
删 (4,-13) 删 (5,-13) 删 (4,-14)
放 (4,-13) cutter r=0
放 (4,-14) trash  r=0
```

一条 `paste_blueprint`，`applied: 2`，`failed: []`，约 190 游戏秒达成。

## 打通之前卡在哪

三轮失败（含两次在用户存档上试错）之后，这一轮找到的四个真障碍：

### 1. 地图种子是错的（最根因）

`world.mjs` 的 `DEFAULT_SEED = 43391` 是 **level-11 存档**的值。
这个 L4 存档的真实种子是 **55013**。

后果：编译器在空气上放矿机，**并且报 ok:true**。

验证（三条独立路径）：

```
world_info RPC            → seed: 55013
存档解码 dump.map.seed     → 55013
484 矿格 + 83 空格暴力反解 → 唯一解 55013
```

### 2. `--world` 从没进过 siteStage

CLI 的 `--world` 填 `input.worldEntities`，但 `siteStage` 读 `input.world`。
两条入口不通，于是：

```
带 181 实体 world 编译 CuCuCuCu → 仍是 no-resource-in-range
（若 siteStage 真收到 world → 会是 no-site-large-enough"世界不干净"）
```

**"世界不干净就拒绝"那道闸在 README 让人走的唯一路径上从来没执行过。**

### 3. `place()` 的两段式布局自己堵自己

收集带先铺，trash 候选生成只看几何不看占用，9 个候选全落在刚铺好的收集带上。
所以 `no-site-large-enough` 不是"地方不够"，是"自己占了"。

### 4. `place` 放不出指定 rv 的转角

带子的弯道变体由邻居派生，邻居来路不明确时游戏只给 code=1。
精确转角必须用 `paste_blueprint`（它携带 code = 1 + rv）。

实测：`place (10,-11) r=0` → code 1；`paste code=2` → 真正的左进上出转角。

## 为什么这次能插进现有产线

`WHY-NO-CUTTER-INSERT.md` 的结论「插不进去」**只对了一半**：

- 它试的是 `x=1` 那条 **r=180（向下）** 的主干 —— 方向确实不匹配
- 但 `x=2..5` 从 `y=-9` 到 `y=-15/-20` 是 **r=0（向上）** 的
- 切割机 `r=0` 的输入恒在 `(x, y+1)`（南侧），**向上流的产线天然满足**

整条钌线是 **U 形回绕**：矿机向上 → 到 y=-34 横移 → x=1 向下进 hub。
只看进 hub 的那一段，确实插不进；回绕段可以。

## 三个假绿

### 假绿 1：`--world`

见上。修法：两条入口在调用点合流（`entitiesToWorld`）。

### 假绿 2：默认种子

不显式给 `--seed` 时，在非 level-11 存档上矿位是错的，但报 ok:true。
修法：输出里警告，指向 `world_info` RPC。**不改编译行为**，基线逐字节不变。

### 假绿 3：`load_save` / `new_game`

原实现 `moveToState` 后无条件 `return ok:true`。实测连续三次"成功"，
而游戏一直停在 `MainMenuState`（`moveToState` 被状态机静默忽略）。

修法：等状态机真的进 `InGameState` 才回 ok，否则 2003。

## M3 闸的红队结论（未修，已立项）

红队对 `gates.mjs` 做了变异测试：**26 个变异体里 17 个存活**。

核心发现：**5 道闸里 4 道对 2026-10-26 的 L4 事故假绿。**

根因不是判据写错，是**期望值来自编译器自己**：
`gates.mjs` 全文从不读 `intent.blueprint`，也从不读 `rotationVariant` / `inDir` / `outDir`。

具体的测试缺陷（全部有行号）：

| # | 问题 |
|---|---|
| 1 | `goodAfter` 与 `cutterOriginOnly` 是同一份夹具，逐字相同 |
| 2 | 共享夹具所有实体 `rot`/`rv` 都是 0，「G4 读 intent.rot」从没被测过 |
| 3 | 朝向反例只有 cutter，而 L4 事故发生在 **belt** 上 |
| 4 | `boundAcceptor` 缺失的夹具只覆盖 1 格，红在 `uncovered` 不是 dead-end |
| 5 | **`runGates` 零覆盖** —— 三条流程变异体全存活 |
| 6 | G3 的三条判据里两条零覆盖 |
| 7 | G6 的绝对阈值分支是死代码 |
| 8 | `mkSlices` 每片计数相同，测不出"排除最后一片" |
| 9 | `expectedRateOf` 零覆盖 |
| 10 | 几何断言只数个数，不查坐标 |
| 11 | `before.truncated` 分支零覆盖 |

新增三道闸的设计（已有 13 个实跑用例）：

- **G2' 同源自洽**（贴前）：`intent.entities` 与 `intent.blueprint` 逐格相等，
  且 belt 的 `(rv, rot)` 反推方向 == 声明的 `inDir/outDir`
- **G7 逐格流向**（贴后）：用 `path.cells` 的邻接关系验每格实际进出去向
- **G8 链划分**（贴后）：蓝图推出的链 vs 游戏实际 path 逐格同序比对
  —— **唯一能在"intent 与 blueprint 都自洽但都错"时变红的闸**

## 环境事故

派了 3 个 agent 同时碰同一个游戏实例，它们的 `new_game` / `load_save` 互相打架，
把游戏状态机搞卡死（一直回不到 `InGameState`）。重启游戏才恢复。

**教训：游戏实例是独占资源，同一时刻只能有一个 agent 对它做写操作。**
