## 核心事实（都用命令复现过）

### 编译器在真实场景是 0 可用的

```
不给 --world：3/6 能排出图，但 dry_run 显示会销毁 5/14/27 个既有实体
给 --world  ：0/6，因为 regionClear() 一票否决
```

`compile.mjs:1156`：

```js
function regionClear(ctx) {
    const world = ctx.world;
    if (!world || !Array.isArray(world.entities)) return true;
    return world.entities.filter(e => e && e.type !== "hub").length === 0;
}
```

**有任何非 hub 实体就整单拒绝。** 而用户唯一在乎的就是有工厂的存档。

### 唯一真正打通关卡的动作，不在系统模型里

L4 的解法是「删 3 条带 + 放 1 切割机 + 1 垃圾桶」= 5 个 op。

但：
- `gateG3` 判红：「会销毁 3 个既有实体」
- `gateG4` 判红：「3 个既有实体消失了」
- `rollback()` 只删「新增」，**删掉的 3 条带恢复不了**
- `loadIntent`（`gates.mjs:1723`）只认 `goal/anchor/entities`，**没有删除字段**

**282 条测试锁死的是「只增不删、一次贴完」的工作流。**
真实世界里唯一成功的动作是「就地改旧线」——它既不在闸的模型里，也无法回滚。

### 让 LLM 算坐标确实不可靠（有学术证据）

B 方向调研搜到的：
- 《Stuck in the Matrix》：网格任务随规模增大**平均掉 42.7%，最高 84%**
- WorldSense：**仅 3 个物体就开始出错**
- GPT-4 路径规划：把 prompt 写成 Python 代码能提升，但仍拿不到最优解

而我们自己的 L4 教训正好印证：
43 实体方案被独立审查抓出**两处致命几何错误**（13 个实体朝向全反 + 入口格错一格）。

### 宏动作有定量收益（有学术证据）

- **SkillsBench**：通过率 33.9% → 50.5%（+16.6pp）
  且「**最多三个模块的聚焦技能**优于大而全的包」
- **Voyager**：技能库存可执行代码，独特物品 3.3×、解锁技术树快 15.3×
- **CodeAct**：+20%

### 自验证基本无效，外部验证才有效

- 《On the Self-Verification Limitations of LLMs》：
  「self-critique 导致显著性能崩溃，sound external verification 带来显著提升」
- 《LLMs Cannot Self-Correct Reasoning Yet》：无外部反馈的自我纠正**不提升甚至变差**

**这与我们在 gates.mjs 里独立撞到的教训完全吻合**：

> 「判据必须来自游戏运行时，不能来自编译器自己……用那个模拟器去验编译器的产物，
> 等于让同一套假设自我确认：'方向反了'在编译器的表示里是不动点，模拟器会说'一切正常'。」

这是本项目最健康的资产，而且有学术背书。

## 初步方向（待 A/C 补充）

三份报告的交集指向：

1. **保留**：底层 RPC 原语（obs / dry_run / step / rotationVariant 自证 / serialize-restore /
   并发串行链 / 截图）—— 这些与编译器无关，全部实机验证过
2. **改造**：把「算坐标」从 LLM 手里拿走 —— 不是靠更强的验证，而是靠**宏动作**
3. **废弃/重做**：编译器作为主线。若保留，必须
   - 接受「世界不干净」（删掉 `regionClear` 的一票否决）
   - 输出 `ops[]` 而不是「只增蓝图」
   - 支持 delete
4. **补上**：`delete_uid`（现在连眼前两条堵死的铜带都修不了）
