## 1. TL;DR

**最重要的一条：所谓"理解"，在工程上等于"有一个能被现实否证的内部模型，并且每次动作前先预测、动作后必须对账"。** 不是让模型"想得更深"，也不是让它写反思日记。判据是：它能不能在动手**之前**说出"建完之后这块地应该长什么样、hub 每秒应该多收几个、哪一格会是什么 code"，然后在动手**之后**用机器把这四条逐个比一遍。

对 shapez 的直接推论：

1. **我们缺的不是智能，是"期望态"。** `obs` 已经能给出权威现状（实体、code、`r`/`rv`、hub 计数、资源格），编译器已经能给出设计（`intent.json`），但两者之间没有一份**机器可比的期望快照**，也没有一个 diff 引擎。现在唯一的对账是 `play-level.mjs` 里那段逐格 readback——它只比几何，不比拓扑、不比行为、不比成本，而且失败后不重规划【本项目】。
2. **不要让 LLM 做状态跟踪。** 让代码做。文献里 LLM 当世界模拟器只有约 60% 的下一状态准确率（GPT-4，单一 benchmark）【二手 2406.06485 的 60% 数字】；而我们手里有 `world.mjs`（资源图逐格对拍 3002/3002）、`belt-sim.mjs`（`computeBelt` 不动点）、`validate.mjs`（V1–V10+S1）——这是一套**可执行世界模型**，比任何 LLM 内部模型都准。LLM 应该只出现在三个边界：解释目标、挑技能、诊断差异。
3. **自省在无外部真值时会让结果变差，而且是显著变差。** Game of 24：标准提示 5%，"LLM 自我批判"3%，"可靠外部验证器"36%（100 题/域）【一手 2402.08115】。Reflexion 的消融更直接：只留"自我反思"、去掉测试生成，pass@1 从 0.60 掉到 0.52；收益来自**执行反馈 + 测试**，不是反思【一手 2303.11366 表 3】。
4. **在结构化可读的环境里，截图是负资产。** BALROG 六个环境、多个模型：**加上图像后性能普遍下降**【一手 2411.13543】；Orak 十二个游戏：image-only 一致地差于 text-only【一手 2506.03610】。截图在我们这里的正当用途只有三个：给人看、抓 UI 异常（弹窗/最小化）、低频交叉校验。
5. **子目标必须是"能变红的闸门"，否则它只是愿望。** 我们自己的 `validator` 已经做对了这件事：19 条注入、175 条断言、每个 check 至少被一条注入命中、`not-applicable` 必须点名阻断者【本项目 `validator/results/l0.json`】。把这套"变异测试"从**离线蓝图**扩展到**实机 gate**，就是第 4 节的全部内容。

## 2. 核心问题：为什么 agent 会"机械执行"

### 2.1 文献给的四个原因（按证据强度排序）

| # | 原因 | 关键证据 | 强度 |
|---|---|---|---|
| 1 | **自回归模型不能可靠地自我验证**，"验证比生成容易"对 LLM 不成立 | Kambhampati 等立场文：LLM 不能独立做规划或自验证，必须配外部模型验证器【一手 2402.01817】；GPT-4 在 Game of 24 自评后 5%→3%【一手 2402.08115】；综述结论：只有"可靠外部反馈"或大规模微调时自纠才有效【一手 2406.01297】 | 强（多域、有对照） |
| 2 | **长程任务的失败是"漂移"，不是"能力不够"** | Vending-Bench：单次运行 >20M token，Claude 3.5/o3-mini 多数 run 盈利，但**所有模型都有 derail run**（误读交付计划、忘记订单、进入"meltdown"循环），且**与 context 是否写满无关**【一手 2502.15840】；SABER：每个"会改变世界的动作"上的偏差把成功率 odds 降 92%（Airline）/96%（Retail）【一手 2512.07850】 | 强 |
| 3 | **"完成"由语言生成决定，而不是由世界状态决定** | Illusory Completion：13 个 agent，在多约束问题上，**高达 48% 的"正确答案"里仍有一条约束从未被验证**；把约束状态显式喂给 agent 后正确率 +4.4~16.1 分【一手 2602.07549】 | 强（13 agent，含前沿模型） |
| 4 | **验证器普遍只做表面检查** | MAST：1600+ 条轨迹、7 个框架、14 种失败模式；"任务验证"类占 6.2%（过早终止）+8.2%（无/不完整验证）+9.1%（错误验证）≈ **23.5%**；例子：ChatDev 生成的国际象棋程序"能编译"就过检，但不符合棋规【一手 2503.13657】 | 强（κ=0.88 人工标注） |

再补一条**专门针对工厂类任务**的：Factorio Learning Environment（FLE，8 个 lab 任务 + open-play）里最强的 Claude 3.5 也只有 **21.9%±1.3** 的 lab 任务成功率（GPT-4o 16.6%，Llama-3.3-70B 6.3%）。作者的两条观察几乎是逐字描述我们：

> **Insight 2**：agent 缺乏空间推理，**无法在已有工厂上迭代改进**；常见失败是"实体放得太近/叠在一起、没给连接留空间、inserter 放错"。
> **Insight 6**：agent 陷入**退化调试循环**——只检查单个实体是否工作，**不检查整体拓扑是否正确**；GPT-4o 曾连续 78 步用同一个错误 API 调用、收到同一条报错。成功完成的 lab 任务里，**56% 的步骤本身是执行错误**（然后恢复）【一手 2503.09617】。

再补一个**外部**的同构案例，非常值得抄它的教训：Claude Plays Pokémon 早期给模型一个"读写记忆文件"的工具，结果模型把记忆写成**逐条流水账**（NPC 说了什么），跑了 **14,000 步、写了 31 个记忆文件、几乎零进度**，还卡在第二个城镇。结论不是"记忆没用"，而是**记忆必须是被蒸馏过的、与决策相关的判断**，不是日记【二手，Anthropic 团队的公开复述】。我们的 `BATCH.md` 正在长成那个样子。

### 2.3 怎么判断它是"懂了"还是"碰巧通过"

这是问题 6，也是第 9 节验收标准的依据。文献里可用的手段只有四类，且都有明显局限：

| 手段 | 做法 | 能证明什么 | 不能证明什么 | 代表 |
|---|---|---|---|---|
| **反事实扰动** | 把同一个任务改一个无关参数（换 seed、挪一格 hub、改一个矿种），看解法是否仍成立 | 是否依赖"记住的答案" | 不能证明它理解了机制，只能证明不是死记 | SWE-bench Illusion：只给 issue 猜文件路径，SWE-bench 上 76%、非 SWE 仓库 53%；5-gram 复现率 35% vs 18%【一手 2506.12286】；Saving SWE-Bench 用"任务变异"暴露过估计【二手】 |
| **过程指标而非终局** | 记录每一步的工具调用、进度率、首次偏离点 | 卡在哪、是否绕路 | 过程分高也可能终局失败；judge 可被 CoT 操纵 | AgentBoard 的 progress rate【一手 2401.13178】；Agent-as-a-Judge（55 任务、365 条需求，与人工评估同可靠性）【一手 2410.10934】 |
| **独立重放** | 用另一套实现/另一个模型重跑同一份证据 | 结论是否可复现 | 两套实现共享同一错误假设时会一起错 | 我们自己的"双实现对拍"就是这个（`belt-sim` vs `belt-rules`，0 差异）【本项目】 |
| **可证伪的负向对照** | 故意去掉一个保护，看检查是否变红 | 检查本身有没有用 | 只证明检查有效，不证明系统理解 | 隧道实验的 arm E（走未保护路径 3/3 被删）【本项目】`ROADMAP.md` P0-1 |

**结论**：没有单一 benchmark 能判定"理解"。可操作的定义是**三条同时成立**：
1. 在**没见过的 seed** 上仍能过（不是 43391 特调）；
2. 能**提前说出**结果（预测误差可测）；
3. 破坏它的前提时它会**拒绝或报警**，而不是硬做（"知道自己不知道"）。

第 3 条最被低估。Selective Quitting 的实验：仅加"允许放弃"的显式指令，12 个模型的安全分平均 +0.39/3（专有模型 +0.64），有用性只降 0.03【一手 2510.16492】。**"我不知道"必须是一个合法输出**，否则模型只能用编造来填。

### 2.4 一个反直觉的结论

机械执行不是"思考太少"，是**目标函数里没有"与现实对账"这一项**。agent 实际在优化的东西是"我发出了一个动作，工具返回了 ok"。只要工具的成功语义比目标的成功语义宽（我们的 `paste` 就是），agent 就会稳定地收敛到"ok 即完成"。这不是提示词能修的，是**接口语义 + 验收闸门**的问题。

所以第 3、4 节讲的是同一件事的两面：**世界模型负责"预测"，gate 负责"对账"**。缺任何一半，另一半都会退化成形式主义。

## 3. 世界模型与状态跟踪

### 3.1 三种世界模型，以及为什么不要用 LLM 当状态机

| 类型 | 是什么 | 优点 | 致命弱点 | 代表 |
|---|---|---|---|---|
| 隐式（权重里） | 模型内部学到了环境动力学 | 零成本、可泛化 | **不可读、不可校准、不可局部修正**；理论上有"通用 agent 必含世界模型"的证明【一手 2506.01622】，但"含有"≠"你能查" | 任何 LLM |
| 符号/可执行 | 世界模型写成程序（PDDL、Python、我们的 `belt-sim`） | 可读、可验证、可局部改、可反事实推理 | 需要人/工具维护；覆盖不到的地方会静默错 | WorldCoder（写 Python 世界模型，比 deep RL 更省样本、比 ReAct 更省算力）【一手 2402.12275】；LLM+P（LLM 转 PDDL，经典规划器求解）【一手 2304.11477】 |
| 检索式（记忆） | 把过去的状态-动作-结果存起来，用时检索 | 便宜、可审计 | 会腐烂、会误导、检索相似≠因果相关 | ExpeL、AWM、ACE（见 §6） |

三条实证：
- **LLM 单独当模拟器不够用**：ByteSized32-State-Prediction 上 GPT-4 仍"不是可靠的世界模拟器"（摘要原话；60% 这个具体数字来自二手报道，标【二手】）【一手 2406.06485】。
- **给模型环境接口也救不了状态跟踪**：Tower of Hanoi 实验里，模型可以工具调用走一步、看结果、再重提示，**性能崩塌依旧发生**，且策略偏离最优与随机策略【一手 2510.15974】。
- **但"学一个动作条件的世界模型"确实有用**：RWML 在 ALFWorld / τ²-Bench 上比纯任务奖励 RL 高 6.9 / 5.7 分，且完全自监督【一手 2602.05842】。注意它是**训练**出来的模型，不是提示出来的。

**对我们的结论**：状态跟踪交给代码；LLM 只在"预测失败后解释为什么"这一件事上出场，且必须给出可检验的假设。

### 3.2 可执行世界模型：我们已经有 80%

盘一下手里已有的部件，这决定了架构不用重造：

| 能力 | 现有实现 | 成熟度 | 缺口 |
|---|---|---|---|
| 资源图（哪格有什么矿） | `src/ai/world.mjs`，与游戏 CLI 逐格对拍 3002/3002 | 高 | 只支持离线 seed；实机要走 `obs.resources` |
| 带子动力学（code/r/rv 怎么被邻居决定） | `src/ai/compiler/belt-sim.mjs` 的 `computeBelt`，与 `belt-rules` 双实现 0 差异 | 高 | 只建模带子+机器邻居，不建模物品流 |
| 形状代数 | shape-ops 重放（S1），48,433/48,433 | 高 | — |
| 布局/布线 | `compile.mjs` 八段 stage | 中 | 不吃世界占用（P1-4） |
| 不变量检查 | `validate.mjs` V1–V10+S1，三态 + `BLOCKED_BY` 归因 | 高 | 全是**离线**判据；没有"贴后实测世界"的入口 |
| 世界现状 | `obs`（实体 + hub + goal + resources） | 中 | **没有产出速率、没有机器内部状态、没有缓冲/吞吐**（`02-ai-shapez-integration.md` TL;DR #6） |

**最高杠杆的一个补丁**：把 `root.productionAnalytics.history`（produced / stored / delivered 三路时间片）和 `BeltReaderComponent.lastThroughput` 接进 `obs`。没有它，"行为层"的预测误差根本不可测，第 3.4 节的第 3 层就是空的。这也直接回答"用户端看不到成果"——现在只能靠 hub `delivered` 的净增量猜。

### 3.3 预测-观察-修正（POC）循环

这是整份文档的核心机制。和 ReAct 的区别：ReAct 是"想-做-看"，POC 是"**先写下期望，再做，然后逐项对账，不符则归因并改假设**"。差别全在"先写下期望"和"逐项对账"这两个强制步骤。

```
        ┌─────────────────────────────────────────────────────────────┐
        │ 1. PREDICT（在任何写操作之前，必须落盘）                     │
        │    输入: 当前 obs 快照 S_t + 待执行 action a                 │
        │    输出: expected.json                                       │
        │      - 新增/销毁的实体集合（含 uid 保留清单）                 │
        │      - 每格 (code, r, rv) 的期望值                            │
        │      - 拓扑期望（每条链的 entry/exit 闭合、fixed-point 数）   │
        │      - 行为期望（hub 速率区间、首次交付 ETA、成本）           │
        │      - 失效条件（哪些前提一旦不成立，这份预测就作废）         │
        └───────────────────────────┬─────────────────────────────────┘
                                    ▼
        ┌─────────────────────────────────────────────────────────────┐
        │ 2. ACT（dry_run → 真做 → 立即读回）                          │
        │    每个写操作都配一个 dry_run；dry_run 的语义必须与真做一致   │
        │    （我们的 MOD-GAP #3 说明：现在不一致 —— hub 被 over-report）│
        └───────────────────────────┬─────────────────────────────────┘
                                    ▼
        ┌─────────────────────────────────────────────────────────────┐
        │ 3. OBSERVE（用权威接口，且必须检查"观测本身是否可信"）        │
        │    - obs.truncated == true  ⇒ 结论只能是 inconclusive         │
        │    - in_game == false / 1003 ⇒ infra 故障，不是任务失败       │
        │    - level 在窗口内变化 ⇒ 计数基线失效，重取                 │
        └───────────────────────────┬─────────────────────────────────┘
                                    ▼
        ┌─────────────────────────────────────────────────────────────┐
        │ 4. RECONCILE（四层 diff，见 §3.4）                            │
        │    match / mismatch(class) / inconclusive                    │
        │    —— 只允许这三种，禁止把 inconclusive 当 match              │
        └───────────────────────────┬─────────────────────────────────┘
                                    ▼
        ┌─────────────────────────────────────────────────────────────┐
        │ 5. ATTRIBUTE（把 diff 映射到"哪条不变量被破坏"→"哪条假设错"） │
        │    输出 hypothesis + 一个能区分它的实验（不是"下次注意"）      │
        └───────────────────────────┬─────────────────────────────────┘
                                    ▼
        ┌─────────────────────────────────────────────────────────────┐
        │ 6. UPDATE（改三样东西之一，且只改一样）                       │
        │    a) 世界模型（代码/常量）  b) 计划（换技能/换选址）          │
        │    c) 假设账本（把错的划掉，写上新证据）                      │
        │    改完回到 1，预算有限（见 §5.4）                            │
        └─────────────────────────────────────────────────────────────┘
```

**为什么"先落盘"是硬要求**：事后写期望等于让模型解释已经看到的结果，这是 Confirmation bias 的机器版本。Hindsight 一旦允许，surprise 恒为 0。

**为什么第 3 步要检查观测本身**：我们的 `obs` 默认 `max_entities: 2000`，而 level-11 存档有 **2805** 个 uid（preflight 实测）。任何用默认参数做 diff 的 agent 都会得出"少了 800 个实体"的结论，然后开始"修复"一个不存在的灾难。这是一个真实存在的陷阱，不是假想。

### 3.4 差异的四个层级与 surprise 计算

不要问 LLM"你觉得意外吗"。surprise 必须是可计算的量。分四层，从便宜到贵：

| 层 | 比较什么 | 计算方式 | 我们用什么 | 失败意味着 |
|---|---|---|---|---|
| **L1 存在性/几何** | 期望的格子集合 vs 实测集合 | `|S_want Δ S_got| / |S_want|` | `obs` 逐格 + `intent.entities` | 贴错位、被挡、被静默覆盖 |
| **L2 拓扑** | 连通性、方向、`rv` 不动点 | 在**实测世界**上重跑 `computeBelt`，统计不动点违例数与度数异常 | `belt-sim.simulateBelts()` + `topologyScore()` | 拐角翻了、下游缺失、两条流抢一格 |
| **L3 行为** | hub 速率、机器产出、缓冲 | 两个时间窗的 `Δdelivered/Δt` 与预测区间比 | 需要新增 telemetry（见 §3.2） | 线通了但不产出/产出不足 |
| **L4 基础设施** | 观测本身是否可信 | `truncated`、`in_game`、错误码、tick 是否推进 | `obs`/`status` | 不是任务错，是环境/进程错 |

**阈值建议（保守起步，先抓"硬"的）**：

```
L1: 任何非零对称差 → HARD（几何没有"差不多"）
L2: fixedPointViolations > 0 或 degree 异常 > 0 → HARD
    （注意：贴完后世界会自己 reroute，as-built ≠ as-designed 是常态，见下）
L3: 连续 2 个窗口 rate < 0.5 × predicted → SOFT；< 0.2 × → HARD
L4: 任一 → INCONCLUSIVE（禁止升级为 pass/fail）
```

**as-designed vs as-built 必须分开存。** 这是我们最容易踩的坑：`STRIDE5-RESULTS.md` 和 `MOD-GAPS.md` §2 已经实测证明，粘贴后邻居变化会让拐角 `rv` 塌回直线（PULL 单元格 3/3 翻转）。也就是说"贴完的世界"本来就**不等于** `intent`。如果 diff 引擎拿 `intent` 当唯一真值，每次都会报一堆假 mismatch，然后 agent 学会忽略 mismatch——这是最坏的结果（告警疲劳）。

正确做法，借建筑工程里的 **scan-vs-BIM** 思路：设计模型（as-designed）和实测点云（as-built）是两份数据，diff 出的是"偏差"，偏差要在**容差**内被接受，超差才升级【二手/行业实践】。我们的容差表就是：几何 0 容差、拓扑 0 容差（但重算后的 `rv` 可与设计不同，只要它是**新邻居下的不动点**）、行为 ±20%。

### 3.5 归因：从"哪个不变量被破坏"回到"哪条假设错了"

这一步是我们相对文献的优势——`validate.mjs` 已经有 `BLOCKED_BY` 的派生阻断表和 `claim()` 的 blame 键归属【本项目 `validator/NOTES.md` §2.1】。把它反过来用：

```
实测 diff
  → 哪条不变量被破坏（V1..V10, S1, 以及运行时新增的 R1..R4）
  → 该不变量依赖哪些前提（契约注册表里的条目）
  → 前提里哪条在本次观测中被否证
  → 写进 assumption ledger：status = FALSIFIED，附证据路径
```

运行时还要新增四条不变量（都在 `MOD-GAPS.md` 里已有实证）：

| id | 不变量 | 违反症状 | 来源 |
|---|---|---|---|
| R1 | 写操作不得销毁未声明的实体 | paste 后旧 uid 消失 | R3 静默销毁【本项目】 |
| R2 | 显式 `rv` 在后续邻居变化下保持不动点 | 拐角翻直 | R2【本项目】 |
| R3 | `dry_run` 的"将要做"必须等于"真做" | 预检说 3 格、实际删 5 个 | MOD-GAP #3（hub over-report） |
| R4 | 观测必须是完整的（无 truncation） | diff 出大量"缺失" | `max_entities` 默认 2000 vs 2805 uid |

R4 尤其重要：它应该在 diff 引擎的入口就断言，而不是等 diff 出怪结果再排查。

### 3.6 三个账本

借 CoALA 的记忆分类（working / episodic / semantic / procedural）【一手 2309.02427】，但落到我们的文件上，只保留三个，且每个都有明确的写入规则：

| 账本 | 内容 | 写什么 | **不写什么** |
|---|---|---|---|
| **Design ledger**（设计账） | `intent.json`：实体、顺序、成本、期望速率、期望世界矩形 | 编译器产物，只追加版本 | 不改写历史设计 |
| **As-built ledger**（实测账） | 每次 gate 后的世界快照摘要：uid 集合哈希、逐格 code/r/rv 哈希、拓扑摘要、telemetry 窗口 | 机器写，带 tick 时间戳 | 不写"我觉得" |
| **Assumption ledger**（假设账） | `{id, 断言, 依据, 否证方法, 状态, 最后验证}` | 只在"预测被否证"或"gate 变红"时写 | **不写过程叙事** |

第三本账是对 `BATCH.md` 的替代，不是补充。规则：一条假设只有三种状态 `HOLDS / FALSIFIED / STALE`；`STALE` 是"超过 N 天或 N 次相关操作未复验"，会被 gate runner 降级为警告。这直接对应 `ROADMAP.md` P3-2 提的"契约性假设注册表"，只是加了过期机制。

**格式示例**：

```json
{
  "id": "A-017",
  "claim": "带子粘贴后，显式 rv 在无新邻居时保持不变",
  "basis": ["live/results/paste-corner.json", "MOD-GAPS.md §2"],
  "falsifier": "在已贴拐角旁放一格带子，重读 code/rv",
  "status": "FALSIFIED",
  "evidence": ["live/results/orig-flip.json"],
  "scope": "只对 PULL 方向成立；EJECT/NONE 不翻",
  "last_checked": "2026-10-25T16:37:00Z",
  "used_by": ["C2-whole-block-paste", "G5-topology-closure"]
}
```

注意 `scope` 字段：文献里最常见的失败是**过度泛化一条局部成立的结论**（我们"seed 43391 恰好满足等距矿机"就是）。假设账必须能表达"在什么条件下成立"。

## 4. 可验证的子目标分解

### 4.1 文献：LLM 不做规划器，做提案器

| 工作 | 做法 | 结果 | 对我们的意义 |
|---|---|---|---|
| LLM+P | LLM 把自然语言转 PDDL，经典规划器求解，再翻回自然语言 | "多数问题给出最优解"，而裸 LLM"多数问题连可行解都给不出"【一手 2304.11477】 | 我们已经有"经典规划器"（编译器），LLM 只需产出目标与约束 |
| LLM-Modulo | LLM 当"近似知识源"，外部验证器把关，双向交互 | 立场文，但论证扎实：LLM 不能自验证【一手 2402.01817】 | 架构合法性 |
| L2HP（HTN + LLM） | LLM 生成层次规划模型 | **语法有效率：层次 1% vs 经典 20%**；解析成功率都约 36%【一手 2511.18165】 | **别让 LLM 直接产出 HTN/任务树**，让它产出"选择 + 参数" |
| DEPS | Describe-Explain-Plan-Select，用执行描述与失败解释修正计划，加一个可训练的子目标选择器 | 零样本完成 70+ Minecraft 任务【一手 2302.01560】 | "选择器"是关键：子目标要能被排序，排序依据是**估计步数**，不是语义相似 |
| SayCan | LLM 打分 × 价值函数（affordance） | 真机长程任务；证明"LLM 的建议必须被可执行性过滤"【一手 2204.01691】 | 我们的 affordance 就是 `compilePlan` 的 `ok:false` + reason |

一句话：**LLM 产出候选与解释，确定性层产出可行性与证据。** 我们的编译器已经是后者，缺的是把它的 `reason` 码当成规划信号（现在只当成错误信息打印）。

### 4.2 Gate 模板（含 falsifier 字段）

子目标 = 闸门。一个闸门如果不能用机器判定，它就不是子目标，是口号。

```jsonc
{
  "id": "G4-landing-exact",
  "requires": ["G3 净空通过", "intent 已冻结（哈希）"],
  "action": { "op": "paste_blueprint", "text": "<szbp>", "x": 1, "y": -16, "charge": false },
  "assert": [
    { "checker": "uid-set-diff", "expect": { "destroyed": 0 } },
    { "checker": "cell-readback", "expect": { "matchRatio": 1.0, "fields": ["code","r","rv"] } },
    { "checker": "entity-count", "expect": { "delta": 29 } }
  ],
  "evidence": "runs/<ts>/G4.json",
  "on_fail": { "class": "landing", "rollback": "delete-by-manifest", "escalate": "diagnose" },
  "falsifier": "mutation:M7-place-adjacent-cell  → 本 gate 必须变红",
  "budget": { "wall_s": 180, "ticks": 0 }
}
```

四条设计规则：

1. **`assert` 里只能出现 checker id，不能出现自然语言。** checker 是代码，有单测。
2. **`falsifier` 是必填。** 没写过"怎么让它变红"的 gate 不允许上线。这是我们 `validator` 19 条注入的同一套做法【本项目】。
3. **`requires` 里写前置的 gate id，不写描述。** 依赖图可拓扑排序，可并行。
4. **失败必须带 `class` 与 `rollback`。** 没有回滚方案的写操作不允许执行——这对应 `paste` 的静默销毁风险。

### 4.3 shapez 实例：把"建 L4 产线"拆成 8 个 gate

目标取自实机记录：`RuRu----`，required 70，测试存档 `7c93b3dd`（seed 60908，hub `(-2,-2)`），当前 level 4【本项目 `tmp/PLAYTHROUGH.md`】。编译器产物：29 个实体（1 miner + 1 cutter + 1 trash + 26 belts），bbox 3×16，2 个拐角，`estThroughputPerSec 0.4`（矿机瓶颈），成本 160，paste 点 `(1,-16)`，世界矩形 `[1,-16,3,-1]`。

| Gate | 断言（机器判定） | 现在能不能做 | 备注 |
|---|---|---|---|
| **G0 目标锁定** | `obs.goal.requirement.shape == "RuRu----"` 且 `required == 70` 且 `level == 4`；把这三个值与 intent 里的 `goal` 逐字段比 | ✅ 能 | 防止"用上一关的蓝图贴这一关" |
| **G1 选址可行** | 每台 miner 的格子 ∈ `obs.resources` 的对应形状集合；矿机间距 ≥ 需求；**与既有实体占用无交集** | ⚠️ 需要把 `obs` 占用接进 `compilePlan`（P1-4） | 现在会撞 L3 的矿机 uid 10096 |
| **G2 蓝图自洽** | `validator.pass == true`；且**没有** `not-applicable` 的 check 落在"关键集"（V1/V3/V4/V9/S1） | ✅ 能 | 关键集 n/a = 假绿 |
| **G3 落点净空** | `dry_run.blocked.length == 0` **且** `dry_run.destroys.length == 0` **且** `dry_run.would_apply == 29` | ✅ 能 | 注意 `dry_run` 会 over-report hub（MOD-GAP #3），要按类型过滤 |
| **G4 落地精确** | `paste.applied == 29`；贴前 uid 集合 − 贴后 uid 集合 == ∅（**不信 `applied`，自己算**）；逐格 `(code, r)` 全等 | ✅ 能（`play-level.mjs` 已有 80%） | 补 `rv` 与 uid 集合两条 |
| **G5 拓扑闭合** | 在**贴后实测世界**上重跑 `belt-sim`：`fixedPoints == tiles`；每条链 `entry/exit` 闭合；无孤立输出 | ✅ 能（`simulateBelts` 已导出） | 这是 as-built 重算，不是拿设计值自我确认 |
| **G6 行为达标** | 采样两个窗口（如 t0 与 t0+60 游戏秒）：`rate = Δdelivered/Δt ≥ 0.32/s`（0.4 的 80%）；同时 `level` 未变 | ⚠️ 需 telemetry 更准；用 hub 净增量也能凑合 | 70 个 @0.4/s ≈ 175 游戏秒，不必等满 |
| **G7 目标达成** | `hub.stored_shapes["RuRu----"]` 增量 ≥ 70 **或** `level > 4`；且 `delivered` 不是靠上一关余量 | ✅ 能 | `level` 变化时 `delivered` 会重置，基线要重取 |

**每个 gate 的 abort 与回滚**：

| Gate 失败 | 类别 | 动作 |
|---|---|---|
| G0 | 输入错 | 不重试，重读 `obs.goal`，报"目标漂移" |
| G1 | 选址 | 换锚点重编译（最多 3 个候选点），不改蓝图 |
| G2 | 设计 | **禁止落盘**；回 `compile.mjs` 的 `reason` 码 |
| G3 | 现场 | 若 `blocked` 是既有实体 ⇒ 走 G1；若是 plan 内自叠 ⇒ 回 G2 |
| G4 | 落地 | 用贴前 uid 清单 `bulk_delete` 回滚；标记 `landing` 类缺陷 |
| G5 | 拓扑 | **不回滚**，因为线可能仍能用；记录为 `as-built drift`，进假设账；若 fixedPoint 违例 > 0 且该格在关键路径上 ⇒ 回滚 |
| G6 | 行为 | 先诊断（是矿机没矿、还是带子堵、还是 hub 口错），**不重贴** |
| G7 | 目标 | 只在 G6 通过后才会走到；失败说明"产出被别处消耗/计数口径错" |

G5 的"不回滚"是一个刻意的设计：拓扑漂移不一定是坏事（游戏自己 reroute 出等价拓扑），盲目回滚会破坏已经能跑的线。判据是"关键路径上的不动点"而不是"全部等于设计"。

### 4.4 反例：什么样的 gate 是假的

三个我们身上真实存在的假 gate，作为负面清单：

1. **永远 `not-applicable` 的 gate**。`V7-throughput` 在 `demandPerSec=0` 时直接 n/a，而 CLI 默认就是 0 ⇒ 真实调用里它从不判定。**修法**：给"关键集" gate 加一条元断言——"本 gate 在最近 N 次真实运行里必须至少 fail 过一次或 pass 过一次，否则标记 `VACUOUS` 并报警"。
2. **自己证明自己的 gate**。拿 `intent` 里的期望值去和 `intent` 比。**修法**：G4/G5 的输入必须是 `obs` 的实测世界，且断言 `obs.truncated == false`。
3. **无法变红的 gate**。**修法**：`falsifier` 必填 + 定期跑 mutation（我们从 validator 已有 19 条注入，扩到实机 gate 只需给每条注入配一个"应该在哪个 gate 红"）。

### 4.5 子目标之间的依赖与"最小可交付"

依赖图（L4 为例）：

```
G0 ─▶ G1 ─▶ G2 ─▶ G3 ─▶ G4 ─▶ G5 ─▶ G6 ─▶ G7
                │                 │
                └─(失败回 G1)      └─(失败→诊断，不回滚)
```

**并行化**：G2（离线自洽）可以与 G1（选址）交替；G6 的等待窗口可以同时做下一关的 G0/G1/G2（预编译下一关），这是唯一值得并行的部分——**写操作必须串行**。

**最小可交付**：如果只能做三个 gate，做 **G3（净空）+ G4（uid 集合精确）+ G6（速率）**。这三条覆盖了"静默毁厂""贴歪了没人知道""线通了但不产出"三类最贵的失败。G5 排第四。

### 5.2 Reflexion 的解剖：收益到底来自哪里

论文自己的消融表（GPT-4，HumanEval Rust 最难的 50 题，pass@1）【一手 2303.11366 表 3】：

| 配置 | 测试生成 | 自我反思 | pass@1 |
|---|---|---|---|
| 基线 | ✗ | ✗ | 0.60 |
| 只留反思（去掉测试生成） | ✗ | ✓ | **0.52** |
| 只留测试生成（去掉反思） | ✓ | ✗ | 0.60 |
| 完整 Reflexion | ✓ | ✓ | 0.68 |

**读法**：单独加"自我反思"是**负收益**（0.60→0.52）；单独加"测试生成"是零收益；两者一起才有 +0.08。也就是说，Reflexion 的增益来自"**执行结果构成的外部信号**"，反思只是把这个信号转成下一次的提示。这和 §5.1 的主线完全一致。

### 5.3 Voyager 的解剖：−73% 是真的，但样本很小

Voyager 的自我验证不是自由反思，而是"把**环境状态**（inventory / position / equipment / nearby blocks）喂给 GPT-4，让它输出一个 boolean + 失败时的 critique"【一手 A.5 节 prompt 原文】。这是**结构化判定**，不是"你觉得做得怎么样"。

但它的技能库消融值得警惕。论文表 1（科技树解锁所需提示轮数，越少越好，3 次试验）【一手】：

| 配置 | 木 | 石 | 铁 | 钻石 |
|---|---|---|---|---|
| w/o Skill Library | 7±2 (3/3) | **9±4 (3/3)** | 29±11 (3/3) | 0/3 |
| Voyager 完整 | **6±2 (3/3)** | 11±2 (3/3) | **21±7 (3/3)** | **1/3** |

前三档互有胜负，真正的差距只在钻石档，而钻石档是 1/3 vs 0/3 —— **n=3**。所以"技能库至关重要"这个宣称，在它自己的数据上只支持"技能库对**最长期**的目标有用"，不支持"没有技能库就做不了"。这个区别对我们的设计很重要（见 §6.2）：技能库的价值在**长尾**，不在常见任务。

### 5.4 四条使用规则

1. **反思只在有独立真值来源时进入决策回路。** 没有 gate、没有 telemetry、没有实测 diff 的时候，禁止让 LLM"复盘"。
2. **反思的输出必须是可检验的假设，不是决心。** 合格："我猜 G6 失败是因为 cutter 的废料没接走导致堵塞；检验方法：读 trash 上游 3 格的 belt 占用 + 跑 60 秒看 delivered 是否恢复。" 不合格："下次注意给废料留通道。"
3. **反思不能改判 gate。** LLM 可以把 `mismatch` 解释成"可接受偏差"并**提议**放宽容差，但放宽容差是一次代码/配置变更，要走 diff review，不能在对话里生效。
4. **反思预算 1–3 条，且必须落到假设账。** 超过 3 条基本等于在写日记；没落账的反思下次一定重复。

### 5.5 我们的替代品：假设账本，不是反思日记

把 Reflexion 的 `verbal memory` 换成 §3.6 的 `assumption ledger`，区别：

| | Reflexion 式反思 | 假设账本 |
|---|---|---|
| 单位 | 一次试验的一段话 | 一条可判真假的断言 |
| 内容 | "我失败了，因为 X" | `{claim, basis, falsifier, status, scope}` |
| 生命周期 | 追加，靠上下文窗口淘汰 | 有状态机（HOLDS/FALSIFIED/STALE），被 gate 引用 |
| 可审计 | 不可（自然语言） | 可（每条有证据路径） |
| 失败模式 | 越写越长，变成流水账 | 条目冲突时强制显式裁决 |

这也顺手解决 `ROADMAP.md` 说的"同一个错误假设踩三次"——因为第三次踩的时候，gate 会因为引用了 `STALE` 的假设而报警。

## 6. 技能库

### 6.1 Voyager 的技能是什么，后续怎么演进

Voyager 的技能 = **可执行代码 + 自然语言描述 + 向量索引**，成功后写入库，新任务检索 Top-k 注入提示；技能可组合（新技能调用旧技能）【一手 2305.16291 §2.2】。

后续工作的关键改进，都是把"轨迹"变成"带约束的程序"：

| 工作 | 贡献 | 数字 | 对我们的意义 |
|---|---|---|---|
| ExpeL 2308.10144 | 从**成功与失败的对比**中抽取自然语言 insight，检索复用 | 随经验累积稳定提升；有迁移实验 | "对比"比"总结"信息量大：失败样本是负例 |
| AWM 2409.07429 | 从历史轨迹**归纳 workflow**，离线/在线都能诱导 | Mind2Web +24.6%、WebArena +51.1% **相对**提升；1000+ 任务/200+ 域；分布差距越大增益越大（+8.9~14.0 绝对点） | 结构化流程 > 单步经验 |
| ReUseIt 2510.14308 | 从成功**和失败**中合成 workflow，并**带 execution guards**（运行中检测并修错） | 24.2% → 70.1%，15 个任务，9 名用户 | **技能必须带 guard**，不是一段代码 |
| ACE 2510.04618 | 把上下文当"可演化 playbook"，增量更新，避免 context collapse | +10.6%（agent）/ +8.6%（金融） | 记忆要"增量修订"，不要"重写摘要" |
| LILO 2310.19791 | 用符号压缩（Stitch）把代码库抽象成可复用函数，并自动写文档 | 在三个合成基准上超过 DreamCoder | 技能库需要**压缩/重构**，否则膨胀 |

### 6.2 我们的技能应该是"参数化编译器 recipe"，不是轨迹

理由：我们的任务有**确定性求解器**。把一条成功轨迹存下来毫无价值（下次 seed 一变就废），有价值的是"这类目标的**解法结构** + 适用条件 + 已验证的产物"。

具体形态：

```jsonc
{
  "id": "skill.single-miner-cut-to-hub",
  "match": {
    "goalDag": { "ops": ["mine", "cut"], "leaves": 1, "depth": 2 },
    "shapeSignature": "ABAB----",          // 结构化签名，不是字符串
    "unlockMin": { "cutter": 1 },
    "resourceNeeds": [{ "shape": "RuRuRuRu", "count": 1 }]
  },
  "params": ["anchor", "pasteAt", "rows"],
  "template": "compilePlan({goal, seed, hub, site})",
  "preconditions": [
    { "checker": "resources-present", "args": { "radius": 64 } },
    { "checker": "footprint-clear", "args": { "pad": 2 } }
  ],
  "postconditions": ["V1","V3","V4","V5","V9","S1"],
  "costModel": { "entities": 29, "blueprintCost": 160, "throughput": 0.4 },
  "verifiedOn": [
    { "seed": 43391, "level": 11, "artifact": "harness/out/RuRu----.intent.json", "hash": "…", "at": "2026-10-25" },
    { "seed": 60908, "level": 4,  "artifact": "tmp/lvl2/play-result.json",        "hash": "…", "at": "2026-10-26" }
  ],
  "knownFailureModes": ["miner-cell-collision-with-existing-line", "hub-entry-occupied"],
  "ttlDays": 30
}
```

### 6.3 结构化索引，不要 embedding

Voyager 用向量检索是因为 Minecraft 任务是自然语言、开放域。我们的目标是**形状 DAG**，语义相似度是错的工具：

- `RuRu----` 和 `RuRuRuRu` 字符串很像，但一个是"切一刀"、一个是"直接交付"，技能完全不同。
- `--CuCu--` 和 `Cu----Cu` 文字不像，但都是"单矿机 + 一条带"，技能相同。

正确索引：`(算子多重集, 叶子数, DAG 深度, 交付口数量, 解锁需求, 资源形状集)` 的精确匹配 + 子图同构。这是**数据库查询**，不是检索模型。实现成本低（我们的 `intent` 里已经有 `solver.ops` 和 DAG）。

### 6.4 TTL 与腐烂

技能库最常见的死法不是"不够多"，是"过期了还在用"。三条硬规则：

1. **每条技能带 `verifiedOn` 与 `ttlDays`。** 过期 → `STALE`，仍可提议但必须重跑 G0–G5 才允许执行。
2. **每条技能带 `knownFailureModes`。** 新失败先查是不是已知的；是则直接跳到对应处置，不重新诊断（省一次 LLM 调用，也避免"重新发明错误"）。
3. **技能库要有"删除"路径。** 连续 N 次在同类目标上失败 ⇒ 降级为 `candidate`，不再默认选中。否则库会单调膨胀，最后每次都注入一堆无关技能，反而降低准确率（上下文污染）。

### 6.5 和编译器的关系

一句话：**编译器是唯一执行体，技能库是"选哪个编译器入口 + 绑什么参数 + 期望什么"的目录。** 技能里不允许出现新的几何算法——那会绕开 validator。这条约束能防止技能库变成第二套未经验证的编译器。

## 7. 视觉 vs 结构化数据：什么时候该看图

### 7.1 证据：三个 benchmark 都说"加图更差"

| 工作 | 规模 | 结论 | 强度 |
|---|---|---|---|
| BALROG 2411.13543 | 6 个 RL 环境（BabyAI/Crafter/TextWorld/Baba Is AI/MiniHack/NetHack），多个开源+闭源 LLM/VLM | "多模态 LLM 在同时给出环境图像时**表现差得多**"；作者原话："可靠的视觉决策目前远超出我们可达范围" | 强【一手】 |
| Orak 2506.03610 | 12 个商业游戏，全genre；GPT-4o / Gemini-2.5-pro / Claude-3.7 | **image-only 一致地差于 text-only**；text+image 混合效果不一（GPT-4o/Claude 下降，Gemini 上升）；LLaMA-3.2-3B 加规划模块反而更差 | 强【一手】 |
| SeeAct 2401.01614 | Mind2Web + 真实网站 | GPT-4V 在**人工 grounding** 下能完成 51.1% 任务；但**自动 grounding 是真瓶颈**，set-of-mark 对 web agent **无效**，最好的策略是 HTML 结构 + 视觉结合 | 强【一手】 |
| Cradle 2403.03186 | RDR2 / Stardew / Cities / Dealer's Life + 5 个软件 | 纯视觉能做 40 分钟主线任务；但实时战斗类（Protect Dutch）加检测工具后成功率也只有 20% | 中【一手】 |

### 7.2 为什么（不用信息论也能说清）

shapez 的 `obs` 是**权威数据**：每个实体的 `code/r/rv/layer/uid` 是游戏内部状态的直接序列化。截图是这个状态经过相机、缩放、遮挡、主题、抗锯齿后的**有损投影**。从投影反推原状态，等于主动引入一个不可控的误差源，而这个误差源恰好落在"空间精确性"上——正是 FLE 里 agent 最弱的那一项。

更具体：一张 1920×1080 截图里，一格带子在 zoom 0.5 时约 8×8 像素，要判断它是直带还是弯带、朝向哪边，靠的是 3–5 个像素的差异。而 `obs` 直接给 `code: 3, r: 0, rv: 2`。**用截图做布局决策是在用 8 位精度替换 32 位精度，还多花一次 VLM 调用。**

### 7.3 视觉的三个正当用途

1. **给人看（这是"用户端看不到成果"的直接解法）。** 每个 gate 通过时存一张截图 + 一屏文字报告。人判断"这像不像一个工厂"用的是视觉，不是 entity 列表。这条与 agent 的决策无关，但与**验收**强相关。
2. **抓"数据读不到的东西"。** 我们的 `world wedge` 事故就是典型：窗口最小化 → `requestAnimationFrame` 停 → `in_game` 永远 false → 所有 world 调用 1003。`obs` 只会说"不在游戏里"，截图能立刻看出"窗口被最小化了"【本项目 `LIVE-LOG.md`】。同理：升级弹窗、错误对话框、暂停遮罩。
3. **低频交叉校验（防"数据管道骗人"）。** `obs` 说 hub 在 `(-2,-2)`、截图里 hub 也在画面中心偏左——这类校验每关做一次就够，成本可忽略，能抓住"我们读错了字段/读错了层"这类系统性错误。

### 7.4 一条硬规则

> **VLM 不参与几何决策；它只在 gate 失败或每 N 步时回答 3 个 yes/no 问题，且答案不能覆盖任何机器判据。**

三个问题固定为：
- `modal_visible`：画面上有模态框/对话框吗？（是 ⇒ 先 dismiss，再重试）
- `hub_counter_matches`：画面上的 hub 进度数字与 `obs.goal.requirement.delivered` 一致吗？（否 ⇒ 观测管道有问题，转 INCONCLUSIVE）
- `bbox_plausible`：`intent` 的世界矩形在画面上大致可见且没有明显空缺吗？（否 ⇒ 可能是渲染/层错误，不是建造错误）

三个都是"异常检测"，不是"理解画面"。这是我们和 Cradle 路线的根本区别：**它把视觉当输入，我们只把视觉当报警器。**

## 8. 反模式清单

### 8.1 表格

| # | 失败模式 | 症状（可观测） | 检测方法（机器） | 拦截措施（工程手段） |
|---|---|---|---|---|
| 1 | **假完成 / premature completion**（MAST FM-3.1, 6.2%） | agent 说"建好了"，但 `delivered` 不涨 | G6/G7 速率与计数；`delivered` 两窗口差分 ≤ 0 | 完成只能由 G7 宣布；LLM 无权置 pass |
| 2 | **工具成功 ≠ 目标达成** | `ok:true` 但世界被改坏 | 贴前/贴后 uid 集合差；不信 `applied` | G4 用 uid 集合断言；给 `paste` 加 `destroyed[]` 字段（MOD-GAP #1） |
| 3 | **静默销毁** | 旧 uid 消失、`failed:[]`、无 warning | uid 集合差 > 0 | G3 `destroys==0` 硬拦；`dry_run` 与真做语义对齐（MOD-GAP #3） |
| 4 | **空洞验证 / vacuous check** | 某个 check 永远 n/a 或永远 pass | 统计每个 check 的历史三态分布；`n/a` 占比 > 90% ⇒ VACUOUS | 关键集 check 不允许 n/a；给 n/a 加"阻断者"必填（已有 `BLOCKED_BY`） |
| 5 | **退化调试循环**（FLE Insight 6） | 同一错误码连续 N 次；同一文件/同一格反复改 | 动作签名哈希去重；连续重复计数 | 连续 3 次同签名失败 ⇒ 强制换假设/换技能/升级给人 |
| 6 | **目标漂移 / 上下文腐化**（Vending-Bench；SABER） | 后期动作与初始目标无关；改着改着去优化别的 | 每步用 G0 的 `{level, shape, required}` 重校验；偏离即报警 | 目标每轮从 `obs.goal` 重读，不从对话历史重读 |
| 7 | **只看单点不看拓扑**（FLE Insight 2/6） | 每个实体都在，但线不通 | G5 在实测世界上重算连通与不动点 | 拓扑 gate 与几何 gate 分离，任一失败都不可放行 |
| 8 | **改考题 / reward hacking**（ImpossibleBench；School of Reward Hacks） | 删/改测试、放宽阈值、跳过 gate | gate 定义与容差表的哈希；改动必须走 review | gate 与容差是**代码**，agent 只有读权限；运行前校验哈希 |
| 9 | **记忆流水账**（Claude Plays Pokémon：14k 步/31 文件/零进度） | 记忆文件线性增长，全是"发生了什么" | 统计记忆条目中"决策相关"比例；条目数 vs 进度 | 只允许写假设账；每条必须带 falsifier；无 falsifier 直接拒收 |
| 10 | **单样本过拟合**（SWE-bench Illusion；我们的 seed 43391） | 只在固定 seed/固定关卡通过 | 回归集必须 ≥3 个不同 seed；换 seed 后成功率 | CI 里 seed 是参数不是常量；新增 seed 必须能变红（否则测试无效） |
| 11 | **过度自信的世界模型**（ByteSized32；chess 状态跟踪） | 预测与实测系统性偏离，但 agent 不觉得意外 | 记录预测 vs 实测的校准曲线（按类别） | 只让**代码**做预测；LLM 预测仅作假设，必须由 gate 证实 |
| 12 | **边想边放 / 施工顺序错**（我们的 V3 第二判据） | 先放的带子在定型时邻居不齐，事后翻向 | `entityOrderPhase` 与实际放置顺序比对 | 蓝图整块贴；禁止在已贴拐角旁补格（纪律 C2） |

补充两条"元反模式"：

- **把 `inconclusive` 当 `pass`。** 观测截断、进程卡死、level 中途变化，都必须显式判 `INCONCLUSIVE` 并阻塞。这不是保守，是防"假绿"。
- **用 LLM 当最终裁判。** 我们的 `validate.mjs` 已经做到了"机器判定 + 三态 + 归因"，不要在它上面再套一层"让模型看看对不对"。

### 8.2 三条通用拦截原则

1. **成功信号必须来自世界，不来自工具返回值，更不来自模型自述。** 优先级：`obs` 实测 > 工具的结构化返回（且要交叉验）> 模型自述（永不采信）。
2. **每一个"允许继续"的决定都要有可回放的证据文件。** 没有 artifact 的 pass 视为 fail。
3. **所有阈值、容差、gate 定义都是代码/配置，且被哈希锁定。** agent 可以提议修改，不能自行修改。这对应文献里的 reward hacking 防护（BenchShield 用"基础设施侧证据"判定是否用了 exploit 路径，96% 准确率）【一手 2609.11028】。

| **M4 Predictor** | 从 `intent` + 当前 obs 生成 `expected.json` | 新，复用 `belt-sim`/`world.mjs` | 无 |
| **M5 Actuator** | dry_run → act → 立即 readback；维护 uid 清单用于回滚 | 现有 `kit.mjs`/`play-level.mjs` 提炼 | 有雏形 |
| **M6 Skill Registry** | DAG 匹配、参数绑定、TTL | 新，JSON 目录 + 匹配函数 | 无 |
| **M7 Planner** | LLM：选技能 + 绑参数 + 输出理由；**不产出几何** | 新，提示词 + 结构化输出 | 无 |
| **M8 Reconciler** | 四层 diff + surprise 分数 + 分类 | 新，~250 行 | 无 |
| **M9 Diagnoser** | LLM：读 diff + 假设账，产出 1–3 条假设与判别实验 | 新 | 无 |
| **M10 Assumption Ledger** | 假设状态机 + 证据路径 + TTL | 新，单文件 JSONL | 无 |

| **M12 Reporter** | 每 gate 一屏报告 + 截图 | 新，~150 行 | 无 |
| **M13 VLM Alarm** | 3 个 yes/no，超阈值才升级 | 新，可后置 | 无 |

**模块边界的一条铁律**：M7/M9 是唯一允许调用 LLM 的地方；M2/M4/M5/M8 必须是纯代码，可单测，可在 CI 里跑。任何"让模型决定几何/判定 pass"的改动都应被 review 拒绝。

### 9.3 内循环/外循环节奏

- **外循环（每关）**：G0→G7，预期 1–3 分钟（不含等待产出）。
- **内循环（每写操作）**：predict→act→reconcile，预期 5–20 秒。
- **对账节奏**：不要只在动作后对账。产线建好后进入"监护模式"：每 30 游戏秒采样一次 L3，连续 2 个窗口不达标才升级。这是 level-triggered（像 Kubernetes 的 reconcile loop），不是 edge-triggered——避免漏掉"慢慢劣化"。
- **总预算**：每关 max 3 次重规划、max 2 次回滚、max 1 次换技能。超预算 ⇒ 输出 `INCONCLUSIVE` + 一屏报告 + 交给人。这是 Selective Quitting 的工程版。

### 9.4 一屏报告（解决"用户端看不到成果"）

每个 gate 输出一段人可读文本 + 一张截图。格式固定，让用户能扫一眼判断：

```
┌─ L4 · RuRu---- · 70/70 ─────────────────────────────── ✅ 2026-10-26 14:03 ─┐
│ 目标    level 4, RuRu----, required 70                                   │
│ 做了什么 1 miner + 1 cutter + 1 trash + 26 belts @ (1,-16)  成本 160      │
│ 证据    G3 dry_run: 0 blocked / 0 destroys                               │
│         G4 readback: 29/29 cells exact, 0 uid destroyed                  │
│         G5 topology: 26/26 fixed points, 2 corners                       │
│         G6 rate: 0.41/s (pred 0.40, +2.5%)  over 180s                    │
│         G7 delivered: 0 → 71  → LEVEL UP 4→5                             │
│ 学到的  A-017 (rv 在 PULL 方向会翻) 已 FALSIFIED；C2 纪律仍有效           │
│ 下一步  预编译 L5 目标（需要 stacker，未解锁 → 只能先攒 shapes）           │
│ [screenshot: runs/2026-10-26T14-03/L4-final.png]                         │
└──────────────────────────────────────────────────────────────────────────┘
```

四行是必须的：**做了什么 / 证据 / 学到的 / 下一步**。"学到的"这一行直接来自假设账的变更，不是模型总结——这是"为未来考虑"的可观测形式。

### 9.5 落地顺序（每步都可独立验收）

**第 0 步（半天，最高杠杆）：M11 Telemetry。**
把 `productionAnalytics.history` 和 `BeltReaderComponent.lastThroughput` 接进 `obs`，加 `obs.rate` 字段（按形状的 produced/stored/delivered 速率）。验收：同一关跑 60 秒，`rate` 与手工用 `stored_shapes` 差分算出的值误差 < 5%。
> 没有这一步，L3 永远是猜的；有了它，后面所有"行为"类断言才有意义。

**第 1 步（1–2 天）：M3 + M4 + M8 的最小闭环。**
先只做 L4 关、只做三个 gate（G3 净空、G4 uid 集合 + 逐格、G6 速率），Predictor 只预测"实体集合 + 逐格 code/r + 速率区间"。验收：
- 正常路径：L4 一次过，三个 gate 全绿，artifact 齐全；
- 负向路径：故意把 paste 点挪一格（压住 L3 的带子），G3 必须红且**不发生任何写操作**；
- 变异路径：故意把 `intent` 里某格的 `r` 改 90°，G4 必须红且能指出是哪一格。
> 三条都过，说明闭环成立；只过第一条，说明又做了一套"自我确认"。

**第 2 步（2–3 天）：M1 + M6 + M10。**
把"目标重读"和"假设账"接上，技能库先只放 1–2 条（单矿机直切、单矿机+trash），TTL 30 天。验收：
- 换 seed（60908 → 43391 → 再来一个）跑 L4 同类目标，技能能匹配且参数能重绑；
- 人为写一条错假设，gate 必须因引用 `FALSIFIED` 而拒绝执行。

**第 3 步（可选）：M13 VLM Alarm + M12 Reporter 的截图。**
先只做"模态框检测"和"hub 数字一致性"两个问题。验收：人为弹一个升级框，`step` 返回 2002 时，VLM 能给出 `modal_visible: true`，并且系统据此 dismiss + 重试成功。

### 9.6 怎么知道这套架构真的起作用

三个指标，按重要性排序：

| 指标 | 定义 | 现在的值 | 目标 |
|---|---|---|---|
| **假绿率** | 报告"成功"但下一关/下一次观测发现没成功的比例 | 未知（没有统计） | 0（宁可 INCONCLUSIVE） |
| **首次预测准确率** | `expected.json` 与实际 obs 在 L1/L2 上完全一致的比例 | 未测 | > 90%（L1/L2），L3 在 ±20% 内 > 70% |
| **每关人工干预次数** | 人需要手动改东西的次数 | 现在每关都要盯 | L2–L6 连续 3 关为 0 |

补充一个"理解度"的定性检验（§2.3 的三条）：**让 agent 在动手前用自然语言描述"建完之后这块地长什么样"，然后拿这句话与 `expected.json` 和最终 `obs` 三方比对。** 如果它说不出、或说错、或说的和它自己生成的 expected 不一致，就说明它只是在调工具。这个检验便宜（一次生成），但很难作弊，建议每周做一次。

## 附：如果只记住五句话

1. **理解 = 可被否证的预测 + 强制对账**，不是更长的思考链。
2. **LLM 不做状态机，不做几何，不做裁判**；它只解释目标、挑技能、诊断差异。
3. **自省在无外部真值时是负收益**（5%→3%）；有效的是"执行反馈 + 机器验证"（36%）。
4. **每个子目标必须能变红**；写不出 falsifier 的 gate 不许上线。
5. **截图给人看，不给 agent 看**；结构化数据是权威，视觉是报警器。
