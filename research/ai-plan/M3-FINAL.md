# M3 Gate Runner：三轮审查后的最终形态

> 从"8 道闸"到"5 道闸"，从"用编译器验编译器"到"只认游戏运行时"。
> 每一次改动都对应一次实测发现，不是设计推演。

---

## 一、最重要的转折：批判推翻了原设计

我最初按研究文档设计了 8 道闸（G0~G7）。6 个独立批判 agent 得出同一结论：

> 8 闸共享编译器的 oracle 且零反证。按现状它会在 A2 上以
> **108/108、0 销毁、drift=[]** 亮绿灯，与 L4 的假绿同形。

机制是这样的：

```
G2  验 intent.validation  → 验的是编译器自己的产物
G4  比 rv/code            → rv 来自 intent，编译器自己错了两次也一致
G5  simulateBelts 重跑    → 与 G2 用同一个模拟器、同一张几何表
                            "方向反了"在编译器表示里是不动点 ⇒ drift 恒空
```

**三层检查全部指向同一个错误源，所以三层会同时透过同一个错误。**

这正是 L4 的实际情形：贴了 108 个实体，`dry_run` 报 0 阻断 0 销毁，而切割机输入方向反了。

### 砍到 5 道

| 闸 | 判据 | 为什么它不假绿 |
|---|---|---|
| G-1 | 游戏时钟在走 | 游戏自己的时钟 |
| G3 | `dry_run` 干净 | dry_run 读的是真实世界 |
| G4 | uid 不消失 + 逐台比对 | uid 是游戏分配的 |
| G6 | 本线交付速率 | 游戏自己的 production |
| G6b | 目标线每段有去处 | 运行时实际连接关系 |

G0/G1/G2/G5/G7 降级为诊断 —— 自证或重复，独立信息量接近零。

## 二、实测挖出的九个 bug

每一条都有 agent 实际复现，不是我推演的。

### 致命 · G4 在真实数据上恒红（假红比摆设更危险）

`obs.entities[]` 对每台建筑只报**一条**记录（origin）。
cutter 2×1 物理占两格，但 obs 里只有一条：

```
obs:   cutter@(-8,-11) uid=10036        ← 只有这一条
物理:  往 (-7,-11) 放 belt → 游戏拒绝    ← 但那一格确实被占着
```

旧 G4 用展开后的格要求"每格都有新实体" —— 游戏永远不给，
**任何含 cutter/hub 的蓝图都被判死**，还报"蓝图没贴全"。

### 致命 · G6 全厂掩盖（假绿）

给同一目标加第二条线（L2→L4 的正常升级路径）时，老线自己的产出就过阈值。
实测：L4 全厂 4.18/s 恒过 1.6 的阈值，而新线零产出。

修法：用两次 `delivered_total` 的**差值** ÷ 游戏时钟差。

### 致命 · after.truncated 从不检查

obs 有 max_entities 上限。截断时既有 uid 会"消失"，
被误报成"paste 销毁了它们，必须回滚"；而 rollback 因 added 为空返回 ok。
实测复现：G4 红"29 台没落地"，rollback-plan 绿"无需回滚"，两边都错。

### 高 · 隧道格让 G6b 永久假红

游戏的地下带没有 Belt 组件，`beltPaths` 只由 Belt 组件构成。
实测：隧道在 `(-7,-12)`/`(-7,-14)`，经过它的路径 cells 是
`[-8,-13],[-7,-13],[-6,-13]` —— 直接跨过去，两个隧道格都不在。

### 高 · G4 不校验朝向

cutter `rot=0` 占 `{(x,y),(x+1,y)}`，`rot=90` 占 `{(x,y),(x,y+1)}` —
origin 和 code 完全一样，物理格不同。**这正是 A2 的形态。**

### 高 · expectedRateOf 忽略加工链

stacker 吃 2 份产 1 份。2 台矿机的 `CpCpCpCp` 按"矿机数×速率"算 0.8/s，
物理上只能交付 0.4/s → 阈值 0.64 永远达不到。

### 高 · rollback 静默接受部分删除

不校验 `applied === added.length`，删了 5/29 也返回 ok。

### 高 · step 失败被吞

游戏暂停于对话框（2002）、`allow_step=false`（1004）、超时 ——
全都变成 `null` 然后当成"推进成功"。后果是 G6b 读到贴完瞬间的状态（假红），
或 G6 拿到混着贴前产量的窗口（假绿）。

### 中 · 其它

- `expectedCells` 同格冲突静默覆盖（belt 被 cutter 吃掉 → G6b 少要求一格）
- `entityCells` 的 180/270 应向负方向长（游戏 `getTileSpaceBounds` 如此）
- `boundAcceptor` 用 `=== null` 会 fail-open（undefined 也是"没有"）
- `debug_items` 的 `beltError` 要明说，不能混成"没连上"
- 形状键从未出现 ≠ 速率为 0（格式不符时会指向错误方向）

## 三、一条被实测推翻的批判

批判说 `dry_run.would_apply` 是**格数**，按此实现会让闸永久红。

**实测否掉了**：空地上 29 实体 → `would_apply=29`，展开是 30 格。
源码里 `wouldApplyCells.push({cell, kind})` 每个条目只 push 一次。

差一点就按那段批判写出一个永久红的闸。
**这是"每条批判都要实测"的最好理由。**

## 四、为什么我的离线自测一开始骗了我

第一版 26 条测试全过，但 G4 在真实数据上恒红。

因为**夹具在作弊**：我写了

```js
{ uid: 12, x: 11, y: 10, code: 7, type: "miner" },   // "miner 右半"
```

而游戏永远不产生这条记录。

测试测的是"gate 的假设"，不是"游戏的现实"。
现在的夹具全部对齐真实 obs 语义（每台建筑一条），
并且专门留了一条回归锁：

```js
ok(gateG4(intent, before, cutterOriginOnly).ok,
    "cutter 只有 origin 一条 obs 时也要绿（回归锁：不按格要求）");
```

## 六、多 agent 编排的三条教训

前三次 workflow 全部失败，原因同源 —— **agent 会做我没让它做的事**：

| 尝试 | 失败原因 | 耗时 |
|---|---|---|
| v1 | 让它读 3 个大文件做侦察（其中一个 2808 行） | 卡死 |
| v2 | 给了仓库路径，agent 去**实际执行代码**验证设计，82 次 Bash | 35 分钟 1.6MB |
| v3 | JSON schema 强制 StructuredOutput，某字段反复验证失败 | 15 次重试 |

v4 的解法：**禁止工具 + 限制输出长度（1500 字）** → 一次成功，零重试。

但**执行类任务必须允许工具**。写代码、跑测试的 agent 需要 Bash 和 Read，
这时候限制的是**范围**（"只写这一个文件"），不是工具。

最有价值的不是设计 agent，是**批判 agent**。
三个设计 agent 全照着我给的 8 闸去设计，没人质疑"这 8 闸是否独立"。
6 个批判 agent 花了不到 10 分钟，挖出了会让整个方案失效的机制性问题。
