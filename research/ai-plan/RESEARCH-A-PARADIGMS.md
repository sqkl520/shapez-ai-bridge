# RESEARCH-A：AI 玩游戏的范式调研（我们该学谁？）

> 调研范围：Voyager / CodeAct / PAL / SkillsBench / 工厂类游戏 AI（FLE）/ LLM 空间推理
> 约定：标 **【搜到】** 为有来源支撑；**【推断】** 为基于证据的推理；⚠️ 为二手转述未核原表。

---

## 0. 一句话结论

**我们不该做"通用布局编译器"，该做"Voyager 式的增量改造技能库 + 外部验证器"。**
三条证据同向：(a) 唯一认真的工厂游戏 benchmark（FLE）把动作空间设成"调 API 改现有世界"，不是"生成整张蓝图"；(b) CodeAct 类方法收益全在"用代码表达动作 + 用执行器当裁判"；(c) 我们的 0/6、L4 真解 5 op、闸只否决不修复，从反面证明"从零生成 + 静态闸"是范式错配。

**LLM 的正确定位是 delta proposer（差量提议者）**：读现状 → 选目标 → 写 5 条 op 的 DSL 程序。坐标与合法性都由外部承担。

## 2. Q1：我们该学 Voyager 的什么？

### Voyager 到底做了什么（【搜到】）

三件套（[2305.16291](https://arxiv.org/abs/2305.16291)）：

1. **自动课程**：不给人给的任务列表，而是按"新颖度"生成下一个**略难于当前能力**的任务——带难度爬坡的 novelty search。
2. **技能库**：每个技能是一段**可执行 JS 函数**，带描述做 embedding 检索；上层技能**调用下层技能**，是组合出来的。
3. **迭代提示**：每轮把 (a) 环境反馈、(b) 执行错误栈、(c) 自验证结果 一起回灌，让它改代码。不微调任何参数。

相对 AutoGPT 类基线：独特物品 **3.3×**、探索距离 **2.3×**、科技树解锁快 **15.3×**（⚠️ 二手转述，见[中文解读](https://www.bilibili.com/read/cv26838369)）。

### 为什么不用手写技能？

Voyager 的 ablation 逐一拿掉技能库 / 自验证 / 自动课程，性能分别掉。核心论证是 **技能空间开放、无法预先枚举**："木板→木棍→镐→挖石头"的链条人手写要穷举到天荒地老，LLM 却能现写、失败再改，**写出来的沉淀成下次的积木**。**手写的天花板是作者的想象力，生成的天花板是验证器的严格程度。**

### 差别在哪（对照我们）

| 维度 | Voyager | 我们 |
|---|---|---|
| 技能来源 | LLM 写、失败后自己改 | 人手写编译器 + 282 条闸 |
| 技能粒度 | 一个函数 = 一个可复用行为 | 一个编译器 = 反推**全关布局** |
| 验证 | 环境自验证（背包里有没有木头）：客观、便宜 | 282 条静态闸：主观、昂贵、只否决不定位 |
| 失败处理 | 报错回灌 → 重写 → 再跑 | 闸红 = 拒绝执行，**无修复回路** |
| 知识增长 | 技能库只增不减，跨任务复用 | 每关重新编译，**0 复用** |
| 与世界交互 | 在**现有世界**上叠加 | 假设**白纸**，regionClear 一票否决 |

### 哪个更适合 shapez？

**【推断】Voyager 式更适合，但必须改造技能粒度。**

shapez 的关卡不是"从白纸造工厂"，而是**在已有工厂上做增量改造**——L4 真解就是 5 个 op：删 3 条带 + 放 1 切割机 + 1 垃圾桶。这是典型的 Voyager 场景：不是生成，是**局部编辑**。

所以技能不该是 `compile_layout(goal) -> full_blueprint`，而该是 `reroute_belt` / `insert_machine` / `remove_segment` / `trash_sink` 这样的宏。每个宏 = 可执行代码 + 前置条件 + 后置验证，坐标在宏内部算。LLM 的任务是**挑宏、填参数、串成程序**，失败时看报错改——这正是 CodeAct 的形态（[2402.01030](https://arxiv.org/abs/2402.01030)）。

## 3. Q2：为什么"手写编译器"这条路业界没人走？

### 证据一：同品类唯一的严肃工作，动作空间是"改世界"不是"生成蓝图"（【搜到】）

**Factorio Learning Environment（FLE）**，[arxiv 2503.09617](https://arxiv.org/abs/2503.09617)（Hopkins, Bakler, Khan, 2025-03），动作空间定义为**通过 Python API 操作现有世界**：lab-play 是 8 个固定资源的结构化任务，open-play 是"造最大的工厂"，考长期规划 / 程序合成 / 资源优化。

注意它的设计选择：**没有一个任务叫"给定目标产物，生成整张布局"**。这不是遗漏——工厂游戏的真实难度在**反馈循环**（产线堵了、料断了、比例不对），不在一次性坐标排布。

实测结论直接命中我们：作者用 Claude 3.5 Sonnet、GPT-4o(+mini)、DeepSeek-V3、Gemini 2.0 Flash、Llama-3.3-70B 评测，这些模型**在空间推理、长期规划、机器布局与连线、错误修正上明显吃力，产出次优布局与产能瓶颈**（[2503.09617](https://arxiv.org/abs/2503.09617)，⚠️ 来自检索摘要）。**最强模型 + 最好的工厂环境，做"布局"仍不及格**——我们手写编译器替模型做这件事，等于把最难的部分留给自己，又没把最容易的部分交给它。

**【推断】** 如果最有代表性的子问题都没人单独设成任务，说明它要么太简单（有解析解），要么太病态（约束爆炸）。0/6 支持后者。

### 证据二：布局是**求解器**的活，不是 LLM 的活（【推断】）

布局 = 带大量硬约束的组合优化（连通性、吞吐、占地、不重叠），有成熟解法（CP-SAT / ILP / 搜索），**不该用 LLM**。LLM 强在"读懂模糊目标 + 调用工具 + 看结果决定下一步"，弱在"精确满足 200 条硬约束"。我们实质上是在**用自然语言推理替代约束求解器**，再用 282 条手写规则补它的不精确——所以闸越加越多、收益越来越小（对照 SkillsBench，[2602.12670](https://arxiv.org/abs/2602.12670)）。

### 证据三：Mindustry / shapez 专用 AI —— 搜不到（【搜到=空】）

多次检索（"Mindustry AI agent"、"shapez AI solver"、"factory layout generator constraint solver"）**全部空结果**。社区层面 Factorio 只有产量计算器和 belt balancer 的数学解，**没有人做"通用布局编译器"**。

**这本身是证据。** 这么大玩家基数、这么明确需求，若通用编译器可行，早该有人做了。最可能的解释：**它不是这个问题的正确分解方式**。

## 4. Q3：LLM 到底该做什么？

五个候选角色，逐个判：

| 角色 | 判决 | 依据 |
|---|---|---|
| **算坐标** | ❌ **绝对不要** | 网格推理随维度上升显著退化（[2510.20198](https://arxiv.org/abs/2510.20198)）；PAL 正是为此把计算卸载给解释器（[2211.10435](https://arxiv.org/abs/2211.10435)） |
| **生成整张布局** | ❌ 不要 | 硬约束组合优化该给求解器；0/6 已证 |
| **判断结果对不对** | ⚠️ 只能辅助，不能当裁判 | 无外部信号的自我纠错不提升、常变差（[2310.01798](https://arxiv.org/pdf/2310.01798)）；自生成测试可被 gaming（[2501.12793](https://arxiv.org/html/2501.12793v1)）。**裁决权必须归模拟器/断言** |
| **选目标** | ✅ **强项** | Voyager 自动课程（[2305.16291](https://arxiv.org/abs/2305.16291)）、FLE open-play（[2503.09617](https://arxiv.org/abs/2503.09617)）都是这个 |
| **写代码 / 调宏** | ✅ **最强项** | CodeAct：代码当动作空间，+20%（[2402.01030](https://arxiv.org/abs/2402.01030)）；Voyager 技能库全是代码 |

### 【推断】结论

**LLM 的正确角色是"写程序的人"，不是"算数的人"，也不是"画图的人"**：看现状（读实体清单与瓶颈）→ 写程序（拼 5–50 个 op 的改造脚本）→ 看报错改程序。**坐标由宏内部算，目标由宏签名约束，正确性由模拟器判。**

### 4.1 用"5 op vs 282 闸"反推角色

| 量 | 数值 | 含义 |
|---|---|---|
| L4 真解 op 数 | **5**（删 3 带 + 1 切割机 + 1 垃圾桶） | 决策空间极小 |
| 为它准备的验证闸 | **282 条** | 规则空间极大 |
| 真解中"删"的比例 | **3/5** | 主要是减法 |
| 编译器 6 关通过数 | **0** | 从零生成假设失效 |

**56 条闸 : 1 个真解 op**——任何"再补几条闸就能过"的说法，都要先解释这个比值凭什么翻转。

更关键的是**信息结构**：从零生成要求同时决定「目标 + 全部坐标 + 全部连线」；增量改造只要求决定「现状哪里不对 + 改哪 5 处」。这把搜索空间压到局部差量，正落在 LLM 能力区内，坐标与合法性留在区外（[2510.20198](https://arxiv.org/abs/2510.20198)、[2211.10435](https://arxiv.org/abs/2211.10435)）。

**【推断】所以角色应定义为 delta proposer（差量提议者）**：输入"实体清单 + 目标 + 上次失败诊断"，输出 `[remove_segment(...), place_machine(...)]` 一段**有副作用的短程序**。它不是设计者，是**改稿人**。这也解释了 282 条闸为什么红：闸的语义是"不许碰既有实体"，而改稿人的工作**天生就是碰既有实体**——冲突在定义层，不是模型不听话。

## 5. 三条具体建议

### 建议 1：把"编译器"换成"宏库 + 程序合成"，第一步先做**减法**

定义 8–12 个**带前置/后置条件的宏**（`reroute_belt` / `insert_machine` / `remove_segment` / `trash_sink` / `split` / `merge` / `extend_belt`），坐标在宏内部算（PAL 原则）。LLM 输出**宏调用序列**（CodeAct 形态），不是逐 op JSON，更不是整张蓝图。

**`remove_segment` 必须是一等公民**——现在回滚只能撤销新增，等于系统只会加法，而 L4 真解第一步就是删 3 条带。这是最便宜的修复、收益最大。验收：L4 用 ≤10 个宏调用解决。

### 建议 2：闸从"否决"改成"诊断 + 重试信号"，282 条砍到 10 条以内

SkillsBench 的拐点是 >4 个技能收益崩塌（[2602.12670](https://arxiv.org/abs/2602.12670)），282 条几乎肯定在悬崖另一侧。改法是让闸返回 **`{failed_rule, offending_entity_ids, suggested_fix}`**——即 Voyager 的"执行错误栈"，LLM 靠它改程序。保留的只该是**硬不变量**（不重叠、端口连通、不越界、不删 hub），语义正确性交给**模拟器跑 N tick 看产出**。反直觉的是：**让模型自生成规则是负收益**，不要做"LLM 自动扩充闸"。

### 建议 3：先复现 L4 的 5 op，别做通用性

失败源于**过早追求通用**（编译器要一把过 6 关）却 0/6。Voyager 反过来：先把一个技能做扎实，再靠组合扩展。把 L4 硬编码成 5 个宏调用的"金标准轨迹"，兼作宏库单元测试、few-shot 示例、回归闸。通了再加 L5/L6，每关沉淀 2–3 个新宏——**技能库的增长就是进度条**。这正是 FLE lab-play 的设计（[2503.09617](https://arxiv.org/abs/2503.09617)）：固定资源、结构化任务、逐级加难。

---

## 6. 诊断总结

0/6、5 op、282 闸不是三个 bug，是**一个范式错配的三个症状**：编译器假设"世界是空的"（regionClear），而真实存档永远不空；真解只需 5 个 op，说明搜索空间极小；闸只否决不修复、回滚只能加法，而 L4 真解第一件事就是减法——**我们的架构在物理上无法表达正确答案。**

### 存疑

- SkillsBench 与 Voyager 的数字均为二手转述，**方向可信，数值以原文为准**。
