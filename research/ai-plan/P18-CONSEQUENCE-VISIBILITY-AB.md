# P18 —— 「后果可见」的 A/B：又证伪了，但逼出了真正的根因

日期：2026-11-09
前置：P17 证伪了「给卡片加理由」，并发现**宏的 warnings 从来没进过 prompt**。本轮修了接线，然后测它有没有用。

---

## 1. 实验设计

两臂同一份 obs / 诊断 / 候选 / 预算（16000/4600），唯一差别是 `## LAST ROUND` 里多不多这一段：

```
ON:  ## LAST ROUND
     round 1: calls [remove_run]
     consequences of last round's calls:
       · remove_run: removal-is-clean — 这 3 格拆除不会让任何下游失去供料…
     decision: continue

OFF: ## LAST ROUND
     round 1: calls [remove_run]
     decision: continue
```

自检 7 项全过，含「ON 的 S5 去掉 consequences 段后与 OFF 逐字节相同」+「带子数/CAPACITY 一致」。
差 131 字符。

**预注册假设 H1**：ON 臂 `remove_run` 占比上升（机制：给模型「你上一刀是安全的」这个确定感）。

---

## 2. 结果：H1 被证伪，而且是反向

```
remove_run   ON 0/30 [0.00,0.11]   OFF 3/30 [0.03,0.26]   Fisher p = 0.2373
引用后果     ON 0/30 [0.00,0.11]
```

方向是**反的**（OFF 反而更敢拆），但 p=0.24，不能算显著 —— 只能说 H1 完全没得到支持。

### 2.1 更严重的是「引用后果 0/30」

ON 臂**一次都没有**提到 `removal-is-clean`、也没提到「不会让任何下游失去供料」
或任何同义表述。进一步检查发现两臂都不读 `## LAST ROUND`：

```
                      ON      OFF
提到 remove_run      0/30    (3/30 —— 但那是它自己新调的，不是引用上一轮)
提到 previous/last round  0/30   0/30
提到 decision:continue    0/30   0/30
```

`## LAST ROUND` 在 prompt 里的位置是字符 6684 / 约 7500 —— 就在 `## YOUR TURN` 前面。
它**位置正常、措辞清楚、内容相关**，模型就是不用。

这与 P17 完全一致：P17 测的是卡片段（S2，字符 0–1929），本轮测的是上一轮段（S5，字符 6684），
**两个不同的位置、两种不同的信息，模型都不用。** 这不是"某一段写得不好"，
是模型压根不按这两处的信息调整动作。

---

## 3. ★ 真正的根因：在这些世界里 `remove_run` 本来就不该用 ★

我一直在问"为什么模型不愿删"。现在做了一件更基本的事：**数一数有多少带子是可以安全删的。**

```
世界                     带子数   可安全单删    会断东西
L4 夹具（161 带）          161        0           161
L5 真机基线（158 带）      158        0           158
L11 成熟世界（2107 带）   2107      265 (12.6%)  1842
```

**L4 和 L5 里，每一条带子单独删掉都会断东西** —— 161/161、158/158。
断开种类：

```
starved-belt       145     删了会让某条下游带子没人供料
orphaned-output    159     删了会让某条上游带子无处可去
starved-machine     12     删了会让某台机器饿死
```

这解释了所有现象，而且推翻了我此前两轮的归因：

- 不是"模型不敢删"（风险偏好）—— **在那里删就是错的**。
- 不是"缺理由"（P17 证伪）—— 给了理由也不会让它做错事。
- 不是"缺确定感"（P18 证伪）—— 确定感也救不了，因为真相是"这一步会坏事"。

**模型三次实验都拒绝裸 `remove_run`，是因为它是对的。** 我把它读成了缺陷。

### 3.1 那正确的修法是什么：成对操作

既然单删总会断东西，正确的修法就只有两条：

1. **成对**：先 `remove_run`，同一计划里立刻 `connect` / `insert_machine` 补上
   （`would-disconnect` 的 hint 早就这么写了：「执行后立刻用 insert_machine / trash_unused 把断点补上；不要停在中间态」—— **这条 hint 也从来没进过 prompt**）。
2. **原子替代**：`replace_run` 一次做完"删旧带 + 放机器 + 检查留下的还连着"。

实测模型的选择（60 条）:

```
                      ON      OFF
remove_run           0/30    3/30
replace_run          5/30    6/30      ← 原子替代，正确
拆+建配对            8/30    11/30     ← 成对，正确
```

**19/60 的计划是成对的**，`replace_run` 也有 11/60。也就是说模型**已经在大半时候用对了修法**。
剩下的那些是它在做别的事（补矿机、接死路），不是"该删而不敢删"。

### 3.2 L11 那个 12.6% 说明什么

成熟世界里 12.6% 的带子可以安全单删 —— 那些是真正的冗余、过时的绕路。
**L4/L5 的问题是"没有冗余"，是缺连接、缺产能。**
在一个没有冗余的世界里要求模型多删东西，是把方向搞反了。

## 4. 我这一轮的判断错在哪（三连错，逐条记）

| 轮次 | 我的假设 | 结果 | 错在哪 |
|---|---|---|---|
| P14 | 修 `$ore` 提示 → `remove_run` 上来 | 2/8 vs 2/8 | 归因到"不知道怎么指定位置"，那只解释了一部分 |
| P17 | 给卡片加 `when:` → `remove_run` 上来 | 1/50 vs 0/50 | "卡上没理由"不等于"模型因此不选它" |
| **P18** | 让后果可见 → `remove_run` 上来 | 0/30 vs 3/30 | **前提就错了：那些世界里删任何一条都是错的** |

前两次是"归因错了"，第三次是**问题本身问错了**。
`remove_run` 采用率低从来不是缺陷 —— 在一个零冗余的世界里它是正确行为。
我拿一个不适用的指标做了三轮实验。

### 4.1 真正的教训

**先测清楚「正确行为在数据里长什么样」，再去测「模型有没有做到」。**
我三轮都在优化一个我没定义过正确值的指标。
正确的做法是在 P14 之前就问：在这个场景里，有多少步是应该用 `remove_run` 的？
答案是 0。那三轮实验从一开始就没有可测的效应。

## 5. 本轮实际交付的东西（仍然有价值）

虽然 H1 被证伪，但有两条改动是**独立的真缺陷修复**：

### 5.1 宏的 warnings 从没进过 prompt（P17 §6.2）

`would-disconnect` 从 P4 就有、`rv-drift` 从 P5 就有，**一次都没到过模型眼前**。
`grep -rn "warnings" src/agent/loop/prompt.mjs` 之前是零结果。

已修：`executed[].result.warnings` → `planned.macro_warnings` → `lastPlanSummary`
→ `renderLastRound` 的 `consequences of last round's calls:`。

**即使模型不读它**，这条接线也该在：它是唯一让"宏算出来的后果"能被后续轮次
（以及读 transcript 的人）看见的通路。而且它让 `would-disconnect` 那句
「执行后立刻补上」的 hint 第一次有可能被看到。

### 5.2 `removal-is-clean`（P17 §6.1）

拆干净时原本零反馈。现在有正面陈述。但因为 §3 的发现，它在 L4/L5 里**永不出现**
（那两种世界没有零后果删除）—— 只有像 L11 那样有真冗余的世界才会看到它。
这反而验证了它的正确性：它只在真话是"安全"的时候才说话。

## 6. 下一步：把指标换掉（已实施，见 §7）

`remove_run` 采用率是个坏指标。应该换成**在世界状态上量的东西**：

1. **冗余率**：世界里有多少格带子是"删了不影响任何下游"的。
   L4=0、L5=0、L11=12.6%。这是世界属性，不是模型属性。
   它下降 = 模型在清理真冗余；它在 L4/L5 为 0 说明那里该做的是**建**而不是删。
2. **成对完成率**：计划里出现 `remove_run` 时，同计划里有没有补上断点。
   这才是"拆得对不对"的判据，而不是"拆得多不多"。
3. **到 hub 率 / 产能利用率**：这是用户最初抱怨的东西
   （「明明有可以快捷提高产能的方法却没有用」）。P8 的 `worldHealth` 已经在算了。

按这三条重排优先级：**接下来该做的是产能（CAPACITY 那条路），不是删除。**

## 7. 已实施：冗余度成为正式度量

按 §6 的第 1 条，新建 `src/agent/loop/redundancy.mjs`，并把结果接进 `worldHealth`。

### 7.1 接口

```js
removalRedundancy(obs, { sample }) → {
  belts,        // 带子总数（**永远报全量**）
  safe,         // 逐条试删，不会让任何下游失去供料的格数
  breaking,     // = belts - safe（抽样时是样本内）
  safe_pct,     // 0..1，belts=0 时为 null
  break_kinds,  // {starved-belt, orphaned-output, starved-machine, …} 计数
  sampled,      // 抽样时如实标注，否则 null
  reason,       // 失败原因（belts=null 时）
}
```

### 7.2 三条口径纪律

1. **复用 `removeRun` 的真实行为**，不另写「删了会不会断」的逻辑。
   这个项目因为"两份真值"出过至少 3 次事故，不能再犯。
2. **失败降级为 `null`，不报 0**。`belts: null` 与 `belts: 0` 在
   「这个场景该不该删」的结论里是**相反**的两个答案。
3. **抽样不许谎报全量**。超过 `BUDGET.REDUNDANCY_FULL_MAX`（3000）抽前 600 条，
   `sampled` 字段标注，但 `belts` 分母仍是全量。

### 7.3 `formatRedundancy` 的措辞

`safe_pct === 0` 时的措辞是本轮最重要的产出：

> 冗余度 0%：161 条带子逐条删除全都会断下游 —— 这个世界**没有可清理的东西**，
> 该做的是建连接/加产能，不是删。

这句话如果早点写出来，P14 / P17 / P18 三轮实验都不会做。

### 7.4 接线与成本

接进 `loop.mjs` 每轮的 `worldHealth`（`healthNow.redundancy`），
失败时降级为 `{belts:null, reason}`，绝不让它拖垮 health。

实测成本：L4（161 带）43ms、L11（2107 带）91ms。大世界有抽样阈值兜底。

#### 接线时抓到的真 bug：**有三个赋值点，我只改了一个**

第一版只在轮首那处 `worldHealth` 后面挂了 `redundancy`。`loop.test.mjs` 的
端到端断言（"health 里必须有 redundancy"）立刻变红 —— 因为 `loop` 里有**三处**
建 health 快照：

```
轮首              st.healthNow = healthNow
撤销后            st.healthNow = rh        ← 覆盖，没有 redundancy
收尾              st.healthNow = hf        ← 覆盖，没有 redundancy
```

后两处覆盖掉之后，`run` 返回的 `health` 里就没有这个字段了。

修法不是复制三段 try/catch，而是升格成 `healthWithRedundancy(p)` helper，
三处统一调用。这是本项目反复踩的同一个坑（"加字段时没数清赋值点"），
所以把教训写进 helper 的注释和测试里。

**写测试时我还写错了一个期望值**：断言 `belts === 161`，实际是 158 ——
这次 run 用 `replace_run` 把 3 条带子换成了 cutter + trash。
161 是 L4 的初始值，`health` 反映的是 **tx 之后**的世界。
这个错误反而成了旁证：它证明 health 不是抄的旧快照。

### 7.5 测试（`redundancy.test.mjs` 11 项 + `loop.test.mjs` 端到端）

关键的几条：

- **R5 ★ L4：161 条带子，0 条可安全单删 ★**
- **R6 ★ L5：158 条带子，0 条可安全单删 ★**
- **R7 ★ L11 对照：2107 条带子里有 265 条（12.6%）可安全删 ★**
  —— 这条的作用是证明度量**不是永远报 0**。没有 R7，R5/R6 就没有信息量。
- R8 坏 obs ⇒ 降级 null，不报 0。
- R10 抽样时如实标注，分母报全量。
- R9 纯函数：两次调用逐字节相同。

写这些测试时又踩了一个已知的坑：我第一次手工构造 `miner(0,0) + belt(0,1) + hub(0,2)`
期望「断链」，结果 `safe=1` —— **手工实体没有正确的朝向，拓扑根本连不上**。
改用真实夹具的邻域切片才正确。带子的方向不是"上下左右相邻"那么简单。
