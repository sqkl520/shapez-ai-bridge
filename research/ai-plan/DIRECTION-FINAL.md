## 0. 唯一方向

**把系统从「蓝图编译器 + 静态检查单」改成「差量执行器 + 宏技能库 + 运行时裁决器」。**

编译器不删、不重写：保留为**库**，降级为宏 `build_line` 的内部实现，退出主线。

一句话的角色定义：**LLM 是改稿人，不是设计者，也不是算数的人。**

---

## 1. 三条冲突的裁决

### 1.1 编译器：保留代码，撤销主线地位（不是"删掉"，也不是"继续修"）

**裁决：`src/ai/compiler/*` 从 main 降为 library；`compilePlan()` 不再有 CLI 主入口，只作为 `build_line` 宏被调用；`regionClear` 从全局闸降为该宏的前置条件（语义从"世界必须空"变成"这个宏只在空地工作，并如实声明"）。**

不删的理由有三条硬证据：`op-templates.mjs`（1250 行槽位/footprint/code 真值，385 条测试）、`belt-rules.mjs`（1906 条实机带子验证的**唯一**方向权威）、`world.mjs`（3002/3002 逐格矿图对拍）。这三样与"会不会做布局"无关，删了等于把已完成的地基重埋一遍。【报告：COMPILER-REALITY-CHECK「反方观点」、D §3】

但也不修主线，因为**空地 9/12 不是用户场景**。【实测：9/12，与主线程一致】真实存档 0/6【实测】。而空地剩下失败的 3 个里，`CrCrCrCr` / `CpCpCpCp` 是上色目标（`dag-not-placeable:column-conflict-unresolved`）、`RuRu----` 是 `no-site-large-enough`——即"空地到 11/12"这个上限本身也要再投入一轮几何工作才够得着。

降级后的正确用法只有一条：**当 `connect` 在空地上没有可连的东西时，`build_line(goal, site)` 在净空区合成一整条新线**。这是合法且真实的策略（在远处空地建线，再用一条主干接回 hub），但它是一个宏，不是入口。

### 1.2 宏的粒度：库 8–12 个，单任务最多加载 3 个；C 的算法放进宏内部，不暴露给 LLM

B 的"≤3 个模块"和 C 的"Left-Edge 就够了"**不是同一层的问题**，所以不冲突：

- B 的 ≤3 是**技能包检索粒度**（SkillsBench 原文：*focused skills with at most three modules outperform larger or exhaustive bundles*）。它约束的是"为这个任务该加载哪几个宏"，不是库容量。Voyager 的库很大，但每个技能很小、可组合。【报告：B §3.2、A §2】
- C 的算法是**宏内部实现**。C 自己也写了这一条：「主线改成 `connect(from,to)` 宏动作后，宏的内部仍需要 pin assignment + rip-up」【报告：C §5 第 5 条】。

所以：**不给 LLM 一个 `route_net` 宏，不让它选车道、选入口、选顺序。** 它只调 `connect(from, to)`；pin assignment、rip-up、几何放宽全在宏里，坐标在宏里算（PAL 原则）。这与 A §4 的角色表、B §5.1A 的批判完全同向。

### 1.3 282 条闸：不砍数量，改语义、移裁决权

E 说"闸和角色在定义上冲突"——**这个判断是对的**，但解法不是砍闸，是让闸跟着角色改。282 条测试的真正价值是"几何/emit 层的离线回归"（1.9 秒跑完，且 `gates.mjs` 头注释自己记录了"判据必须来自运行时"这条血泪教训），这部分必须留。【报告：D §1.3、B §4.2】

要改的是三处**语义**，不是数量：

1. `loadIntent` 加 `removes[]`；G3 的绝对律令「不许销毁」改成「**销毁必须在计划里声明且可恢复**」。
2. `rollback` 从"只删新增"改成"删新增 + 用 `serializeEntity/restoreEntity` 恢复被删"（原语已提交，`3306ade`，只是没接）。
3. 新增两道：`G-delete-replay`（声明的删除在游戏里逐 uid 发生）、`G-rollback-restore`（回滚后 uid 集合与贴前逐字节相等）。同时修 `--plan` 不是零写入（G-1 会推进 600 tick）这个谎言。

砍掉的是**做法**不是文件：不要再把"第 283 条闸"当进度条。判据从"闸数"换成"L4 五 op 回放全绿 + 回滚逐字节还原"。

### 1.4 报告之间的两处数字冲突，以复跑为准

- E 报"空地 6/12"，实测 **9/12**（多出 `Ru----Ru`/`RbRb----`/`--SuSu--`/`Cu------`）。E 的数字偏悲观，但这不动摇它的结论：真实存档仍是 0。
- E 说根因是 `regionClear` 一票否决；主线程实测说修掉 `--world` 合流后主因是 `V6-crossing`。我复跑 6 个目标：**5 例 `column-conflict-unresolved`、1 例 `no-site-large-enough`**——支持"主因是布线撞车，不是净空"。**结论：`regionClear` 该降级，但它不是唯一的墙，别指望拆了它就能过。**

这也直接说明一件事：**争论"哪条闸挡路"本身就是这个架构的病**。5 个目标以同一种方式失败，说明缺的是一层能力，不是一道闸。

## 2. 其他选项为什么被排除

| 选项 | 排除理由 |
|---|---|
| 继续加厚编译器到空地 11/12 | 上限是错的方向：真实场景仍 0。且 `--world` 还带 seed 不传递的假绿 bug（矿机挖空气却报 ok）【报告：L4-E2E-STATUS】——先把主线修到 11/12 再发现真实场景是 0，是同一错误再来一遍 |
| 推倒重来，只做宏 | 丢掉 op-templates / belt-rules / 1906 条实机验证 / 9 个可用空地目标；且 `connect` 在拥挤旧厂里照样需要 C 指出的那 300 行，等于重写 |
| 上 CP-SAT / 求解器 | 违反零依赖铁律；问题是**可行性**不是最优性（连 1 条都没通）；MIP-Router 作者自述开源替代"practical 上都跑不动"【报告：C §3】 |
| 让 LLM 直接吐蓝图/坐标 | 学术（网格推理随规模掉 42.7%）+ 我们自己的 43 实体事故（13 个朝向全反）双证否【报告：A §4、E §2】 |
| 继续加闸 | 56 条闸 : 1 个真解 op，任何"再补几条就能过"都要先解释这个比值凭什么翻转【报告：A §4.1】 |
| 分支：MCP 上 tool search / 动态工具发现 | 8 个工具，官方阈值 >20，纯浪费【报告：B §5.3】 |

## 3. 五阶段（按"修好之后能多做哪些以前做不到的事"排序）

依赖：0 → 1 → 2 → (3 ∥ 4)。**阶段 0/1 的代码量远小于阶段 2 的价值，但它解锁的东西最多，所以必须最先做。**

### 阶段 0　让正确答案可以被表达（最高优先）

今天系统**在物理上无法表达唯一已知的正确解**：L4 = 删 3 带 + 放 1 切割机 + 1 垃圾桶，而 `delete` 只认坐标不认 uid、`intent` 没有删除字段、`rollback` 只能删新增。【报告：E §1.2、D §1.2】

- 交付：mod 加 `delete{uid}` 与 `tx`（serialize 快照 → 执行 → 失败 restore）；`intent` 加 `removes[]`；`rollback` 支持恢复；`verifyRuntime(planId)`。
- 判据（可执行）：
  1. 实机删一条带 → `restoreEntity` → 前后 uid 集合 diff = 0；
  2. L4 五 op 写成 JSON，`node src/agent/gates.mjs --plan X --apply` 全绿，且 `--apply` 推进 ≤1 游戏秒；
  3. **负例必须红**：把切割机朝向改反，G4 或 G8 必须报错（否则闸是空的）；
  4. `node src/agent/gates.test.mjs` 等价通过。
- 依赖：无　工作量：约 1.5 人日 / 2 agent

### 阶段 1　宏技能库（坐标从 LLM 手里拿走）

- 交付（6 个，每个都带"何时不该用"的描述）：`connect(from,to)`、`insert_machine(at,facing,machine)`、`remove_run(uids | cells)`、`extend_line(from,len,dir)`、`replace_run(region,building)`、`trash_unused(outlet)`。返回 `{ok, cells_planned, cells_placed, first_mismatch}`。
- 判据：
  1. L4 五 op 用 **≤5 个宏调用**重写并通过运行时验证；
  2. lint：`connect` 的签名不接受裸 x/y，仓库里不存在"LLM 传入绝对坐标"的调用（机器检查，不是人看）；
  3. `connect` 在 181 实体存档上，任意两台相邻机器 A→B 成功率 ≥90%（这是它区别于手算的硬指标）。
- 依赖：阶段 0（需要 `tx` 才能安全试错）　工作量：约 3 人日 / 4 agent

### 阶段 2　闭环打通一关（真正的分水岭）

注意：**L4 当年是通的，但是人算的坐标**（+2 实体、手写）。所以这里的判据不能是"打通 L4"，必须是"**没人算坐标**也能打通"。

- 交付：`src/agent/loop.mjs`（observe → diagnose → propose → apply → verify → repair，≤N 轮）+ LLM 层（现在 `src` 里**完全没有**，`llm-layer-DESIGN.md` 只是设计）+ 可回放 transcript。
- 判据：
  1. 冷启动（只给存档 + 目标）在 L4 上成功；
  2. plan 里所有坐标要么来自 obs 的 uid，要么是宏返回值——**无人工绝对坐标**（可脚本检查）；
  3. 连续 5 次独立尝试 ≥3 次成功；
  4. 失败必须给结构化诊断，不许静默（`production` 系统性偏低 8~12% 这类坑也要在诊断里排除）。
- 依赖：0 + 1　工作量：约 3 人日 / 2 agent

**为什么这一阶段可以不等布线算法**：L4 是**就地改造**，不需要新建 hub 连接。把 hub 16 口这个最难的子问题推后，是这轮排序里最省风险的决定。

### 阶段 3　拥挤工厂里的布线（C 的算法，放进 `connect` 内部）

- 交付：`connect` 内部接 pin assignment（hub 16 口，匈牙利/贪心）→ 有限轮 rip-up（≤5 轮，确定性，用现成但未接线的 `Grid.clone()`）→ Z 形降为快路径，失败记 `softCost` 交 `dijkstraOriented` → 可行性预检（源宿量相等，抄 MIP-Router 的 A3）。
- 判据：`connect` 到 hub 成功率 ≥80%；hub 入口类失败占比从当前 100% 降到 ≤30%；编译器 `--world` 从 0/N 到 ≥3/N（**当回归用，不当主线**）。
- 依赖：阶段 1　工作量：约 3 人日 / 3 agent

### 阶段 4　技能库自增长（Voyager 那一半）

- 交付：每通一关沉淀 2–3 个新宏；朴素检索（关键词/描述即可，零依赖）。
- 判据：L5/L6 只用已有宏 + ≤2 个新宏通过；给定目标，top-3 检索命中正确宏 ≥80%。
- 依赖：阶段 2　工作量：持续

## 5. 证据强度（不要把这些说成一样确定）

**硬（我复跑或代码可查）**：空地 9/12；真实 181 实体 0/6；282 测试全离线跑假桥；MCP 仅 8 工具且 4 个已实现的读接口未转发；`src` 无 LLM 层；`delete` 不认 uid；`rollback` 无法恢复删除；`loadIntent` 无删除字段；`routeAll` 无 rip-up，`Grid.clone()` 建好未接线；空地失败 3 个中 2 个是上色目标（CrCrCrCr / CpCpCpCp），1 个是 `no-site-large-enough`（RuRu----）。

**中（报告实测但我未复跑）**：C 说 16 个 hub 入口只有 3 个真被挡住；C 估计 pin assignment 单独能把 3/6 抬到 4–5/6——这是**估计，不是结果**，阶段 3 要当假设验证。

**弱（二手转述）**：SkillsBench 的 +16.6pp / 三模块上限、Voyager 的 3.3×/15.3×、FLE 各模型分数。A 自己标了 ⚠️。方向可信，数值别引用到决策里。

**纯推断（无直接 A/B）**：宏动作层能把真实存档从 0 抬起来。B §6.2 明说"没有『40 次 place vs 1 次 connect』的对照实验"。这是本方案的**核心赌注**，所以阶段 2 的判据必须硬。

## 6. 可反驳的预测（防止回到"加闸"惯性）

如果阶段 0–2 完成后，L4 的冷启动成功率仍是 0/5，那么"宏 + 运行时裁决"这个假设就是错的，应当停止继续投入宏库，转而回到"人在环、AI 只做 dry_run/验证"的定位（D §4 那个"资深质检员"）。**这个判据现在写下来，比事后解释便宜。**

反向预测：如果阶段 1 的 6 个宏里 `connect` 单独就能让 L4 通过，说明 C 的布线层可以再推后，阶段 3 降级为"拥挤工厂才做"。
