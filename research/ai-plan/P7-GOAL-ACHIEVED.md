# P7：达成 —— `Cu----Cu` 第一次真正交付进 hub

> 2026-11-03。这一轮从「2 个汇合点死锁」开始，一路做到 **目标形状 18 个送进 hub，
> 并在 6 分钟里稳定爬到 59/170（35%）**。
>
> 这是这个项目第一次让 AI 在没有人工干预的情况下，把一条完整的
> `mine → cut → rotate → hub` 产线跑起来。

---

## 一、死锁的真相：不是布局错误，是垃圾桶占着主干道

上一轮我判断「2 个汇合点是结构死锁，改哪一方都会把另一方弄坏」。**这次查清了**：

| 汇合点 | 上游 A | 上游 B |
|---|---|---|
| `(1,-16)` | **rotater**（产目标形状）✅ | **trash** ❌ |
| `(1,-11)` | trash（同一条垃圾线）❌ | 铜矿机方向的长链 ✅ |

追上游追到 `trash@(3,-14)` —— **一条垃圾桶往主干道上灌货的链**。

它不产任何东西（trash 是终点），但它**占着 entry 槽位**，把真正的产线挡在外面。
所以汇合点 A 的 `entry=right` 满足的是垃圾桶那条路，rotater 的产线一直在空转。

这不是「结构死锁」，是**垃圾线该拆**。

### 修法：删掉 trash 那三格带子

```
(3,-15) → (3,-16) → (2,-16) → 汇合点(1,-16)
```

删掉之后汇合点从 2 个降到 1 个。

---

## 二、剩下的那一个是真的汇合，但 hub 有 14 个空入口

`(1,-11)` 的两个上游都是真实产线（一条从 rotater、一条从铜矿机）。
带子只能有一个 entry，balancer 又能解决 —— 但 `balancer` **只能 r=0**
（2×1 非方形占地，`op-templates.mjs:745` 明确禁止 rotation≠0），
而汇合点需要「上+右进」，方向对不上。
`insert_machine` 也**有意不支持** balancer（「它是布线元件，由 connect 的扇出改写处理」）。

**换思路**：查 hub 的 16 个入口 —— **14 个是空的**。

于是把左支那条流直接接到 `hub.entry=0`（12 格），完全绕开主干。

结果：

```
跑前 delivered: {"CuCuCuCu": 13}
跑后 delivered: {"CuCuCuCu": 48}
```

**铜第一次进 hub 了。** 但交付的是整块 `CuCuCuCu`，不是目标 `Cu----Cu`。

---

## 三、铜绕过了 cutter/rotater

顺着 `hub.entry=7` 往上追：

```
铜矿机 (-9,3) → (-9,2)…(-9,-11) → (-8,-11)…(-3,-11) → 汇合点(1,-11) → hub
```

**整块铜直接进了 hub，完全没经过切割。**

### 修法：在路径上插 cutter

`(-9,-12)` 是空的，cutter 2×1 正好占 `(-9,-12)` + `(-8,-12)`，输入朝下 ——
而铜是从 `(-9,-11)` 往上来的，方向对得上。

装上之后**还是没切**。查出来：

```
(-9,-11): belt rv=2 entry=bottom exit=right   ← 货从下面进来，直接右转走了
```

它是**拐弯带子**，把货转向横向绕过了 cutter。

改成直行（`entry=bottom exit=top`）——**这次真的切了**：

```
跑后 produced: {"CuCuCuCu":15, "Cu----Cu":4, "----CuCu":5, "CuCu----":5}
```

`Cu----Cu` 第一次出现。

### 这一步同时验证了 `opts.facing`

`(-9,-11)` 改成 `entry=bottom exit=top` 之后**读回来就是 `r=0 rv=0`** ——
上一轮修的 `runGuarded`（tx 的 immutable 语义）真的生效了。
没有它，游戏会按邻居把这格重算回拐弯。

## 四、最后一环：rotater 的输出接到 hub

cutter 的两个输出口都是空的（切出来的东西堆在里面）。在 `(-9,-13)` 放 rotater、
`(-8,-13)` 放 trash 接废料。然后 `connect(rotater → hub.entry=2)`（19 格）。

**20 ops 全部落地。**

## 六、这一轮真正起作用的工具

回头数一遍，整条链上每一步都卡在一个「工具不支持」上，而每个都是前几轮补的：

| 步骤 | 缺什么 | 什么时候补的 |
|---|---|---|
| 知道该放矿机到铜矿 | `$ore` 算子 | P3 |
| 拆掉挡路的无矿矿机 | `remove_machine` 宏 | P4 |
| 能跨 32 格接线 | R13 对 `allow_replace` 的豁免 | P2 |
| 改带子方向 | `replace_run(opts.facing)` | P5 |
| **改完不被游戏覆盖** | **`tx` 的 `runGuarded`** | **P6** |
| 看到「目标矿在哪」 | mod 的 resource 扫描范围 | P2 |
| 看到「这台矿机没矿」 | MACHINES 段的矿机标注 | P3 |

最后那个（`runGuarded`）是**决定性的** —— 没有它，前面所有方向控制都是空谈。

---

## 七、方法论：这一轮我改掉的判断

上一轮我写「这是结构死锁，改哪一方都会把另一方弄坏」。这一轮查清了**不是**：

- 死锁 A 的上游之一是**垃圾桶**，拆掉就行
- 死锁 B 是真的汇合，但**不需要在汇合点解决** —— hub 有 14 个空入口，绕过去更快

**教训**：「A 和 B 冲突」这个判断在动手验证之前都是假设。两次都是
「看起来必须二选一，其实存在第三条路」。

这个项目里同类情况已经出现过四次（`$ore` / `remove_machine` / `runGuarded` / 这次的死锁）。

## 八、还没做的

- **进度只到 35%**。产线还缺产能，或者 rotater 输出有瓶颈。要继续要么加矿机、
  要么查瓶颈在哪（CAPACITY 段应该能算出来）。
- 这条产线是**脚本手工搭的**，不是模型自己想到的。模型在同样的世界上跑了
  六七轮都没能让铜进 hub —— 它每轮都追不同的诊断，没有收敛。
  下一步该验的是：**把这些工具串起来，模型能不能自己走完**。
