# M3 Gate Runner 设计评审：为什么 8 道闸会集体假绿

> 由 3 个设计方案 + 6 个独立批判（红队 × 实现者，各 3 份）交叉验证得出。
> 三个设计（线性状态机 / 声明式 spec / PRE-POST 分离）的核心结论一致：
> **按原样实现，这套闸在真实事故 A2 上会全绿。**

---

## 一、致命发现：用编译器的 oracle 验编译器

批判原文（红队 3）：

> 8 闸共享编译器的 oracle 且零反证。按现状它会在 A2 上以 **108/108、0 销毁、drift=[]** 亮绿灯，
> 与 L4 的假绿同形。

具体机制：

```
G3  dry_run           → 只报"格是否被占"，不编码方向。反向 cutter 占同一格 ⇒ 必绿
G4  逐格 (code, rv)   → rv 来自 intent，intent 来自编译器。
                        编译器 rv 自己错了两次也一致 ⇒ 绿
G5  simulateBelts     → 与 G2 用同一个模拟器、同一张 GEOMETRY 表
                        "方向反了"在这套表示里是**不动点** ⇒ drift 恒空 ⇒ 绿
```

**三层检查全部指向同一个错误源，所以三层会同时透过同一个错误。**

这和 L4 的实际情况完全吻合：我贴了 108 个实体，`dry_run` 报 0 阻断 0 销毁，
而切割机输入方向就是反的。

## 二、逐闸的独立信息量（红队 3 的结论）

| 闸 | 与谁重复 | 能否独立变红 |
|---|---|---|
| G0 目标锁定 | — | 几乎不能（goal 由本 agent 生成，无并发写者） |
| G1 选址可行 | ⊂ G3（都读 dry_run.blocked） | 不能 |
| G2 蓝图自洽 | 自证（验自己的产物） | 不能（rv 只查枚举合法，不查朝向语义） |
| G3 落点净空 | — | **能**（但只能验几何） |
| G4 落地精确 | ≈ G3 的事后版 | 弱（rv 是回显） |
| G5 拓扑闭合 | ≈ G2（同模拟器重跑） | 不能 |
| G6 行为达标 | — | **能**（唯一真行为信号） |
| G7 目标达成 | ≈ G6 的累计版 | 弱 |

**8 道闸里真正独立的信息量只有 2 个：G3（几何净空）和 G6（产量）。**

其余 6 道是同一件事的不同说法。

## 三、具体缺陷清单（按严重度）

### F1 · ~~G3 的单位错位~~ —— **批判说错了，实测推翻**

批判断言 `dry_run.would_apply` 是**格数**，会导致闸永久红。

**实测否掉了它**：空地上 29 实体 → `would_apply=29`，而按 footprint 展开是 30~31 格。
源码里 `wouldApplyCells.push({cell, kind})` 每个蓝图条目只 push 一次。
所以它是**实体数**。

差一点就按批判的结论写出一个永久红的闸 —— 这也是为什么每条批判都要实测。

### F1' · G4 在真实数据上恒红（这一轮真发现的）

比 F1 严重得多。

`obs.entities[]` 对每台建筑只报**一条**记录（origin）。
cutter 2×1 物理占两格，但 obs 里只有一条：

```
obs:        cutter@(-8,-11) uid=10036          ← 只有这一条
物理:       往 (-7,-11) 放 belt → 游戏拒绝      ← 但那一格确实被占着
```

旧 G4 用展开后的格去要求"每格都有新实体" —— 游戏永远不给，
所以**任何含 cutter/hub 的蓝图都被判死**。而且它是"假红"：
报告说"蓝图没贴全"，实际上贴得完全正确。

修法：G4 按**实体**比对；格层面的净空归 G3（问 dry_run）。

同时修正 footprint：**miner 和 rotater 都是 1 格**，不是 2 格。
实据：四台矿机在 `(2..5,-8)` 相邻共存；`op-templates.mjs` 里 miner 的
footprint 就是 `[1,1]`。

### F2 · G4 的 cells 只取原点格

cutter 2×1 的右半、hub 4×4 的外圈都不参与比对。
⇒ 净空假绿、回滚漏格。

修法：比对用 `entityCells(intent)` 展开全部占用格。

### F3 · G5 的死路判据是"有货才判"

沿用 audit R3 的 `itemsOnPath > 0`。但**断供时下游恰好是空的** ——
最该红的时候不红。

修法：改为 `boundAcceptor === null` 即死路，不看有没有货。
（我这一轮实测过的反向证据：`(1,-7)` 堆了 23 个物品时才看出来，
而 A2 那次是刚贴完，货还没流到。）

### F4' · G6 拿 window_seconds 算时长 —— 恒为 0（这一轮真发现的）

桥的 `observeProduction` 里：

```js
const windowSecs = wantSlices * sliceSecs;   // 常量：slices × 10
```

两次采样拿到的 `window_seconds` **永远相同**，所以 `dt = 0`。
旧 G6 用 `dt > 0` 当第一道检查，于是集成路径里 **100% 恒红**，
理由还是"时钟可能停了"—— 而 G-1 刚刚证明时钟在走。

修法：时长用**游戏时钟**（两次 `debug_loop.tick` 之差，单位是游戏秒）。

### F4'' · G6 的单位错位（这一轮真发现的）

旧实现比"两次**速率**之差" vs "一个**速率**阈值"。
两条稳态线（1.0 → 1.0）的差是 0 → 被判死，而它完全正常。

修法：比**后一次采样的速率**，不是增量。

另外两个 fail-open：
- 理论值 0（没矿机）→ 阈值 0 → 任何速率都 ≥ 0 → 永远绿。现在显式判红。
- G6b 的 `paths` 被桥 `slice(0,40)` 截断时，"没覆盖"不代表"没连上"。现在显式说出来。

### F4 · G6 的 upper_bound 是全厂口径（原批判）

`expectedFrom(obs).upper_bound_per_sec` 算的是**整座工厂**的理论值。
L4 全厂 delivered 4.18/s 恒过阈值，**新线全死也绿**。

修法：必须按形状算增量 —— `Δdelivered[goal.shape] / Δt ≥ 0.8 × 该线的理论值`。

### F5 · 八道闸里没有时钟闸

A1（时钟冻结）没有任何一道闸能挡。唯一间接的是 G6 的 production 停更，
但那表现为"产量为零"⇒ 假红 ⇒ 触发回滚 ⇒ **毁厂**。

修法：新增 G-1（时钟闸），在任何采样前断言：
- `debug_loop.logic_budget_ms !== null`（NaN 会变 null）
- `debug_loop.speed === "regular"`
- `tick_after - tick_before > 0`
- 不用 `step` 的返回值作数（它推进 0 tick 时历史上有过返回 ok）

### F6 · rollback 的 `destroys === addedUids` 是恒真式

粘贴完成后，region 内的实体**本来就等于** addedUids（旧实体已在 dry_run 阶段排除）。
拿它当准入校验等于没校验。

修法：真正的准入判据是 **`region 内不存在 beforeUids`**，且 region 必须
从 `addedUids` 的 cell 算出而非整块 bbox。

### F7 · G4 的 r 与 intent.rot 量纲不明

`obs.entities[].r` 是 `rotation`（0/90/180/270）；
`intent.entities[].rot` 也是角度，但粘贴时游戏存的是 `originalRotation` 还是 `rotation` 未实机钉死。
若不同，**拐角全红** —— 而 A2 正发生在拐角。

修法：先实机测一次（贴一条带拐角的线，读回 obs.r 与 intent.rot 对比）。

### F8 · mutant 夹具只改输入，不改检查代码

方案 B 的 `proveRed()` 用"只违反某闸的夹具"证明每闸会红。
但改夹具只能证明"夹具能红"，不能证明"检查函数有灵敏度"——
如果 check 写成 `return true`，换个夹具照样绿。

修法：mutant 必须**注入到 check 函数本身**（把断言改成恒真），
再看是否会因此放行一个坏夹具。两个方向都要测。

## 四、真正能防住 A2 的是什么

四份批判都指向同一个答案：

> 唯一真 oracle 是 **`debug_items.boundAcceptor`**，却被"有货才判"豁免了。

也就是说：**必须用游戏运行时的实际连接关系验证方向，而不是用编译器的模拟器。**

具体做法：
1. 贴完后跑 60 游戏秒（让货流起来）
2. 读 `debug_items.paths[]`
3. 断言：目标产线的每一段都有 `boundAcceptor`，且终点是 hub 或预期机器
4. 断言：`production.delivered_per_sec[goal.shape] > 0`

第 4 条最简单也最硬 —— **如果目标是 RuRu---- 而 delivered 里没有它，就是没通。**
不需要模拟器，不需要几何，只看游戏自己的账。

## 五、修正后的最小可行闸集

砍掉自证的，只留有独立信息量的：

| 闸 | 断言 | 为什么它不会假绿 |
|---|---|---|
| **G-1 时钟** | budget 非 null + speed=regular + Δtick>0 | 独立 oracle（游戏时钟） |
| **G3 净空** | blocked=[] ∧ destroys=[] ∧ would_apply=expectedCells | 独立 oracle（dry_run 读的是真实世界） |
| **G4 落地** | beforeUids ⊄ afterUids（无消失）∧ 逐格展开比对 | 独立 oracle（uid 是游戏分配的） |
| **G6 行为** | Δdelivered[goal.shape]/Δt ≥ 0.8×该线理论值 | 独立 oracle（游戏自己的 production） |
| **G6b 连通** | 目标线每段 boundAcceptor 非 null | 独立 oracle（运行时实际连接） |

**G0/G1/G2/G5/G7 降级为诊断信息，不作闸。**

理由：
- G0/G2 是自证
- G1 ⊂ G3
- G5 与 G2 同源
- G7 ≈ G6 的累计版

## 六、这一轮的教训

我设计 M3 时的思路是"把 8 道闸都实现出来"，但没问过每个闸的**独立信息量**。

三个设计 agent 全都照着我给的 8 闸定义去设计，没有人质疑"这 8 闸是不是真的独立"。
**是批判阶段把它挖出来的** —— 而且四份批判独立得出同一结论。

这说明：**设计阶段的多样性不够，批判阶段的价值极高**。
6 个批判 agent 花了不到 10 分钟，找出了会让整个方案失效的机制性问题。
