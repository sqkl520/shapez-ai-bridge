# L4 的两种解法：一个是必需的，一个是可选的

日期：2026-10-28
A4b agent 报告了一个反直觉结论，我核实后确认它是对的，而且暴露我原方案的一处多余动作。

---

## 事实

`live-L4-entities.json`（改造前）在 `(4,-13) (5,-13) (4,-14)` 有三条带子：

```
(4,-13) belt uid 10209
(5,-13) belt uid 10149
(4,-14) belt uid 10143
```

cutter 放在 `(4,-13)` 时：
- 输入槽在 `(4,-12)`（有带子 10208 ✓）
- 左输出槽在 `(4,-14)`
- 右输出槽在 `(5,-14)`（有带子 10150 ✓）

## 两种解法

### 解法 A（我原方案 A0）：把 `(4,-14)` 换成 trash

```
删 (4,-13) (5,-13) (4,-14)
放 cutter (4,-13)
放 trash  (4,-14)
```

净变化 +2 实体。

### 解法 B（A4b 发现的）：保留 `(4,-14)` 那条带子

```
删 (4,-13) (5,-13)
放 cutter (4,-13)
```

**只删 2 条带、只放 1 台机器。** `(4,-14)` 的既有带子 10143 自然接住左槽的废料，
继续往它原来的方向走。

净变化 **+1 实体**。

## 核实

我用 `replace_run({region:[4,-14,5,-13], building:"cutter"})` 跑：

```
✓ ok
  removed: 10209@4,-13  10149@5,-13
  placed:  cutter@4,-13
  kept:    10143@4,-14  10150@5,-14
  flow:    "top"
```

**`kept` 里有 10143 —— 它被正确保留了。**

## 结论：A4b 是对的，我的 A0 方案多此一举

`(4,-14)` 那条带子本来就是左槽的下游，把它删掉换成 trash 是**没必要的**。

不过 **A0 方案在实践中也成立** —— 而且它更「干净」：
- 解法 B 依赖 `(4,-14)` 那条既有带子继续通向某处（需要确认它不会堵）
- 解法 A 直接把废料就地销毁，不依赖下游

两种都能让 `RuRu----` 产出（实测 L4 就是用 A0 打通的）。

## 这个案例说明什么

A4b 自己说：「我之前凭直觉写了『必然 orphaned-output』的测试，跑红后逐格核对才发现错了。」

**这正是宏该做的事** —— 把「直觉判断」换成「逐格核对」，并且让错误在测试阶段暴露。

而且它证明 `replace_run` 的 `kept` 字段有意义：它明确告诉调用方
「这几格我没动，因为你的计划用不到它们」。
