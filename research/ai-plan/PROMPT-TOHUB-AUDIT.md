# prompt.mjs toHub 审计

> 审计对象：`DIAGNOSE-FACTCHECK.md` §9 / `tmp/DIAGNOSE-BASELINE.md` §4 的指控
> 「`obsWorld().toHub` 拿原点格而不是入口格找上游，58 改成 28，给 94 条带子打了错误的
> `[not reaching hub]`，而这正是第八~十二轮真 LLM 实验的依据」。
>
> 方法：读代码 + 逐行照抄两个函数到探针里跑 L4/L5 夹具 + 用两个**互相独立**的真值
> （严格前向 BFS、`loop.mjs#hubReachable`）对撞 + 回溯历史实验的 `prompt_chars`。
> 关键结论用**临时插桩**在真实代码路径上验过（改前/改后各渲染一次），做完已还原：
> `git diff -- src/agent/loop/prompt.mjs` 为空、`sha256sum` 与备份一致、
> `node --test src/agent/loop/prompt.test.mjs` → 188 通过 / 0 失败。**没有碰游戏实例。**

---

## 一句话结论

**bug 存在，但不是被指控的那个；指控给出的修法会让它更糟；「影响第八~十二轮」这句是错的。**

- `toHub` 的真 bug 是**不穿机器**（`into` 只索引带子，`prompt.mjs:832-834, 881-887`），
  不是原点格/入口格。从 hub 反向走三步就撞上 `L3` balancer 停工，L4 的 87 条带子因此被漏判。
- **「改用入口格」不是修，是挖坑**：`into` 是按 `exitCell` 索引的，相邻带子的正确查找键就是
  `origin(cur)`（145/147 对实测成立）。改成 `entryCell(cur)` 会**跳过一整节**，
  可达集合从 58 掉到 28（真值 140）、错误从 92 涨到 114。**28 比 58 错得多。**
- `[not reaching hub]` 标记**只出现在第十一、十二轮**（靠 `prompt_chars` 8735 vs 8301 反推，见 §B）。
  第八、九、十轮的 prompt 里根本没有这个标记。
- **可见的 12 条带子 100% 都带标记** ⇒ 这个标记在模型的视野里是**常量**，信息量为零；
  而且 L4 上这 12 条**全部**是真能到 hub 的（12/12 错）。
- 真正致命的一点：**这个 bug 是实验的承重墙**。`pickBeltsForGoal` 只从「到不了 hub」的集合里挑
  12 条给模型看。把它「修对」（不管是 28 还是 140），正解三条 `B69/B81/B82`
  **就一条都不在 prompt 里了**（在真实代码路径上实测 0/3）。谁按指控去修，谁就把实验直接改死。

## A. bug 核实（代码 + 实测数字）

### A.1 代码：它到底用哪个格

`src/agent/loop/prompt.mjs:881-895`（`obsWorld()` 内）：

```js
const into = new Map();          // "x,y" → 出口落在这里的带子
for (const b of view) {
    const [x, y] = exitCell(b);          // ← 索引键 = 带子的**出口格**
    ...
    into.get(k).push(b);
}
while (frontier.length) {
    const cur = frontier.pop();
    for (const b of into.get(`${cur.x},${cur.y}`) || []) {   // ← 查找键 = cur 的**原点格**
```

指控说这里该是 `entryCell(cur)`。**这个判断是错的，理由是一条几何恒等式：**

```
A 的货流进 B   ⟺   exitCell(A) == origin(B)   ⟺   origin(A) == entryCell(B)
```

`into` 的键是 `exitCell`，所以「谁指向我」的答案只能从 `origin(cur)` 出发去查
（`into[origin(cur)]` = 出口落在 cur 原点的带子 = cur 的上游）。
`entryCell(cur)` 指的是**上上游**，用它做键会把 BFS 变成「隔一节跳一节」。

**实测（`.tmpverify/tohub_link.mjs`）**，L4 上逐对枚举相邻带子：

```
相邻带子对: 两条都成立=145  只有 exit(A)==origin(B)=2  只有 origin(A)==entry(B)=0
entryCell 上有带子的 146 条；其中「并不真的喂我」的 1 条
```

（2 条例外是 `B134→B135` 与 `B85→B72`，都是**地下带/转角**那一侧，
`origin(A)==entryCell(B)` 不成立但 `exitCell(A)==origin(B)` 成立 —— 也就是说
**恰好在例外上，`origin` 口径仍然对，`entryCell` 口径会错**。）

⇒ **原点格是对的**。指控的「入口格才是对的」不成立。

### A.2 那 28/58 这个数是真的吗

是真的，而且它证明**改动方向是错的**：

`entryCell` 都不是正确的查找键（B/D 两行都比对应的 A/C 行更差）。

### A.3 真正的 bug：不穿机器

`prompt.mjs:832-834` 把 `view` 限定成带子，`881-887` 的 `into` 也只用 `view` 建表 ⇒
反向 BFS **遇到任何机器就停**。L4 的主产线是

```
矿机 M3 → 6 节带子 → L3(balancer) → 6 节 → L2 → 6 节 → L1(cutter) → 6 节 → B84/B85 → … → hub
```

第一台 balancer `L3@(4,-16)` 就把链掐断了。这就是 163 条里 87 条被漏判的全部原因。

补上「穿机器」之后（`C` 行）假阴性归零，但多出 5 条假阳（宽松穿透把 `B131..B134` 那串
方向不匹配的也当成通了）。再补上**方向校验**（货的到达方向必须等于 `OPP[输入槽 dir]`，
与 `loop.mjs:490 inputFed` 同口径）后就是 `E` 行 —— 与 `hubReachable` **完全重合**，
L4 上 140/140、**0 差集**。

剩下那 23 条不可达里，两条是地下带（`B65`、`B85`）——
`templateByBuildingVariant("underground_belt")` 返回 `undefined`，`slotsOf` 对它返回 `null`，
槽位无从得知，`prompt.mjs` 与 `loop.mjs` 都在这里断链。

### B.3 错误的方向：假阳性标记，不是漏标

- **`[not reaching hub]` 是假阳性**：标"到不了"，其实到得了。L4 的 12 条可见条目 **12/12 全错**。
- **没有假阴性**：真正到不了的 23 条里，有 18 条被标了；漏标的 5 条
  （`B131/B132/B133/B134/B85`）是 `toHub` 的**假阳性可达**（它只看格不看方向），
  这 5 条本身也到不了 hub，只是没被标出来 —— 且它们不在 prompt 里。

L5 上错误轻一些（`node .tmpverify/tohub_report.mjs`）：

```
L5 prompt BELTS: 12 条 / 标记 12 条
  逐条真值: B127:不可达  B136:不可达  B140:不可达  B144:不可达  B148:不可达  B152:不可达  B156:不可达
            B137:可达    B141:可达    B145:可达    B149:可达    B153:可达
  错误标记: B137,B141,B145,B149,B153  (5/12)
```

L5 是「标记半对」——7 条对、5 条错。因为 L5 上 `toHub` 的残缺集合恰好覆盖了 `B127/B136/B140`
那一段（它确实接不上）；L4 没有这条巧合。⚠️ 但 `B127/B136/B140` 在 L5 上**是不是正解没有验证过**
（仓库里只有 L4 有经实机验证的正解，`experiment-coldstart.mjs:78` 的 `GROUND_TRUTH` 写死在 L4），
所以 L5 的「7 条对」只能说「按可达性判据是对的」，不能说「按正解是对的」。

⚠️ 但**两关的标记覆盖率都是 100%**（12/12）。所以哪怕 L5 上有 7 条标对，
模型**依然无法从标记里区分"该改的"和"不该改的"** —— 段首那句
「Lines WITHOUT the mark already reach the hub」在可见范围内没有一行能成立。

### B.4 这个错误让模型**更容易**还是**更难**选中正确带子？

**两种机制，方向相反，而且互相抵消：**

1. **标记本身（只作用于十一、十二轮）→ 让模型更难。**
   正解三条 `B69/B81/B82` 被打上"到不了 hub"，而它们的 `desc` 同一行写着
   `下游=L3.primary`，`L3` 的 desc 写着 `输出=top:primary(→B56)` —— prompt 里
   **自带一条能走通到 `H1` 的证据链**。标记与 desc **在同一行互相矛盾**。
   一个愿意读 desc 的模型会撞上这个矛盾；一个照标记办事的模型会把这 12 条当作"要修的对象"
   而不是"要改造的产线"。这是**负向**的。

2. **`byGoal` 选择（第六轮起）→ 让模型**更可能**看到正解。**
   `pickBeltsForGoal` 只从「`toHub == false`」里挑。正因为 `toHub` 把整条主产线
   （含正解三条）都判成"到不了"，这 12 个名额才**恰好**落在 `x=4/5` 那两条并排链上。
   **正解可见率 10/10 是这个 bug 的副产品。**
   这是**正向**的，且量级远大于标记的负向。

## D. 建议（修/不修；怎么修；需要补什么测试）

### D.1 结论：**先不要动 `toHub` 的查找键**

指控建议的改动（`prompt.mjs:890` 改 `entryCell(cur)`）**必须拒绝**：
它会让可达集合 58 → 28（真值 140）、总错 92 → 114。这不是"另一个 bug"，
是**把现有行为改坏**。§A.1 的等价关系已经证明 `origin` 才是这把索引的正确键。

### D.2 要修的其实是三件独立的事，按优先级

**(1) 最高优先：`[not reaching hub]` 标记要么删掉，要么换成有区分度的信号。**

现状是「可见的 12 条 100% 带标记」——信息量为零，且 L4 的 12/12 是错的。
两个选项：

- **删掉标记与段首说明**（`prompt.mjs:998-1002`）：回到第十轮的形状，
  A/B 对照可以直接说"标记没有增益"。
- **保留但换判据**：用「这条带子的出口格上是不是空的」或「沿下游走几步撞上什么」这类
  **局部、可验证**的事实，而不是一个需要全局可达性才能算的断言。
  局部事实不需要穿机器，也就不会踩 §A.3 的坑。

**(2) 次高优先：给"该改哪 2 格"一个信号。**
这是 8/10 失败的真实原因。可用的现成事实（都已在 `obs` 里）：
- 这条链**两端**各是什么（矿机 / balancer / hub）；
- 目标形状的配方里 cutter 的**输入侧**要求（`RuRu----` 需要 `RuRuRuRu` 在 cutter 的 bottom）；
- 正解窗口在**链的中段、靠近 balancer**（`(4,-13)`），而模型反复选链头 `y=-10` 或链尾 `y=-14`。

**(3) 最低优先（技术债）：`toHub` 不穿机器 + 地下带无模板。**
如果将来要把它当成**真可达性**用（而不是现在的"选带子启发式"），
必须补 `loop.mjs:440 hubReachable` 的走法（穿机器），而不是改查找键。
但要清楚：**改成真可达性 = 正解从 prompt 里消失**，
必须先有 (2) 的替代选择判据，否则不要动。
