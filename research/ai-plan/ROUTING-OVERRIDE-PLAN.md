## 工作包

### P1 —— 契约对齐（**必须第一个**）

**目标**：决定 `connect` 用什么形态把「被覆盖的 uid」交给调用方，并把契约改对。

**碰游戏**：否（纯离线，只读代码 + 改 `contract.mjs`）

**要决定的事**：
- 放 `warnings[].replaced_belt_uids`（贴在既有 `replacing-belts` 里）
- 还是顶层 `replaces: [{uid,x,y}]`
- **两者可以都有**：顶层给人/loop 用，`warnings` 保持向后兼容

**验收**：
- 契约文档（`contract.mjs` 的 `WARNING_CODES.action`）与实现逐字一致
- 给出一条「三宏同形」的对照：`insert_machine.removed_uids` /
  `trash_unused.replaced_belt_uid` / `connect.replaced_belt_uids`
- **不写实现**，只定契约 + 写一份「实现方必须遵守的形状」

**已知约束**（F5）：`warnings[].code` 有闭集，加新码要扩闭集；顶层字段不受限。

## 我最担心的三个地方

**1. R13 一旦放宽，它就再也不是「删对了没」的检查了。**
R13 现在的价值是「模型说删 3 个，宏却删了 8 个」这种事的唯一机器拦截。
给「宏自动覆盖」开一个口子之后，这个口子会不会被别的东西利用？
P4 必须给出一个**结构性**的判据（比如「自动覆盖的 uid 必须在 `connect` 的返回值里出现，
且 `planToTxOps` 只放行这些」），而不是「给 R13 加个开关」。

**2. 覆盖的格在活链中间，会静默切断一条正在供货的线。**
`(1,-6) → hub` 这个场景覆盖的是 `(1,-7)`，它是断头链的一格（无害）。
但换成另一个世界，覆盖的可能是某条主供料链的中间格 —— 那会直接让一条产线停摆。
`trash_unused` 有 `confirm_waste` 保护这个，`connect` 的覆盖没有。
P3 必须回答：要不要引入类似的保护，还是靠 loop 的验证层事后发现。

**3.「自动降级」会让成功来得太容易，掩盖真正的失败。**
如果不设上限、只要撞了就覆盖，`connect` 会变成一个「总能成功」的宏。
那时 `connect` 失败率归零，但它的「成功」可能全是把旧工厂拆了铺新路。
P3 的验收里有一条反例就是防这个 —— 但光是测试不够，需要在**报告**里持续报告
「这次成功用了多少格覆盖」。

# ⚠️ 计划作废：根因不是「搜不出」，是 `portsOf` 把带子出口算错了

> 2026-11-01，P4 红队发现 + 主线程独立复现。**上面的方案 A 全部作废。**

## 事实

`portsOf()`（`connect.mjs:188`）对**带子**返回的 eject 端口，方向永远是 `top`：

```js
// (1,-6) 是 r=180, rv=0，真实出口是 bottom → (1,-5)
portsOf eject: [{"cell":[1,-7], "vel":"top", "face":"top"}]
真 实 出 口 :  bottom → (1,-5)
```

原因：带子走 `mk()` 这条通用路径，从 `machine-spec.json` 读静态 spec：

```json
"ejectors": [{ "tile":[0,0], "dir":"top" }]
```

**那个 `top` 是 r=0 且 rv=0 的情形**，spec 里没有「按 r/rv 变化」的表达。
带子的真实方向应该由 `beltExit(rv, r)` 算。

## 影响面（实测）

```
34 条带子里 21 条出口算错
r=0 的：全对      ← 所以既有测试全绿（它们只测 r=0）
r≠0 的：17/19 错
唯一「碰巧对」的两条是 r=90, rv=1 —— 恰好 beltExit(1,90)="top"，和 spec 写死的值一样
```

## 后果：这才是 `connect` 失败的真正原因

`connect` 以 `portsOf(from).eject` 为起点搜索路径。起点格和方向都错了，
后面 842 条候选自然全部落到错误的位置。

**用正确的出口几何重算（主线程独立验证）：**

```js
candidateShapes([1,-5], "bottom", [1,-3], vE, {maxTurns:6, maxLen:12})
→ 到 hub 入口 (1,-3) 有 123 条可行路径
→ 最短: [[1,-5],[1,-4],[1,-3]]      ← 零覆盖，正好是最初砍掉的那 3 格
```

**所以：不需要 `allow_replace`，不需要改 R13，不需要改契约。**

## 新的下一轮

1. **修 `portsOf` 对带子的出口/入口**：走 `beltExit(rv, r)` / `beltEntry(rv, r)`，
   而不是 spec 里写死的 `top` / `bottom`。
2. **修 `machine-spec.json` 的带子条目**（或在 `portsOf` 里对带子特判）。
   要注意：`r` 会变，spec 是静态的 —— 所以大概率要在 `portsOf` 里特判，而不是改 spec。
3. **补测试：r≠0 的带子端口**。这是 221 条测试里完全缺失的一类，
   也是这个 bug 能活到现在的原因。
4. **然后重跑半成品世界实验** —— 那时 `connect` 应该**零覆盖**就能成功。

## 这个 bug 为什么能活这么久

- 既有测试只覆盖 r=0 的带子（`beltExit(0,0)="top"`，与 spec 一致）
- `connect` 在真实世界里接刀大多是「机器 → 机器」，起点常是机器而不是带子
- 半成品世界这个场景第一次从**一条 r=180 的带子**起手，才暴露出来
