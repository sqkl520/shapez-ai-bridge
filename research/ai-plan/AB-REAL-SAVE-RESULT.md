# 真实存档上的第一个 A/B：抬预算有可见变化，但统计上不显著

> 2026-11-02。**这是一个弱结果，不能当作「预算修复有效」的证据。**
> 原始数据：`.tmpverify/ab-real/results.json`（30 条，0 失败）

---

## 结论

**抬预算让模型能看到的诊断点多了一些（平均触及句柄 3.73 → 4.87），
但没有任何一项指标达到统计显著。**

| 指标 | OLD（默认 9800） | NEW（16000/4600） | p |
|---|---|---|---|
| 产能动作（加 cutter） | 2/15 (13%) | 3/15 (20%) | **1.000** |
| 碰到诊断点名的句柄 | 15/15 (100%) | 14/15 (93%) | **1.000** |
| 说「看不见」 | 0/15 | 0/15 | **1.000** |
| **平均触及句柄数** | **3.73** | **4.87** | **0.125**（Mann-Whitney） |

**唯一有方向性的差异是「平均触及句柄数」，p=0.125。**

---

## 但这个实验有一个前提没成立

两臂的实际 prompt 差距比预期小：

```
OLD  chars=10519  belts=0/163   cap=NO   diag=7
NEW  chars=11217  belts=12/163  cap=YES  diag=7
```

**OLD 臂也拿到了 7 条诊断**，而诊断里本来就点明了具体句柄（`B130`/`B134`/`B129`/`M4`…）。
所以模型**不需要看到带子表也能照着诊断的句柄去改** —— 这与 `AB-PROMPT-RESULT.md`
第一轮的发现一致：

> 诊断里写了 `handles B34`，这就够了 —— 模型不需要在 BELTS 段里看到它的详细描述。

⇒ **在这个场景上，BELTS 表 + CAPACITY 的增量价值本来就有限。**
这不是预算修复没用，是**这个场景测不出它**。

---

## 那修预算到底有什么用

### 1. CAPACITY 段现在真的出现了

```
## CAPACITY
supply 2.8/s | processing 0.5/s | 18% utilized
bottleneck: cutter — 82% of supply is stuck here
options:
  · add 5 cutter (1→6) ⇒ 3/s — fills the line
```

**修复前这段在真实存档上是不存在的**（`dropped-for-budget`）。
现在模型至少**被明确告知**产能瓶颈在哪、还差多少。

但那 3/15 的产能动作说明：**看见 ≠ 去做。**

### 2. 带子表从 0 条变成 12 条

修复前模型**一条带子都看不见**，只能靠诊断里的句柄名推断几何。
现在能看见 12 条的上游/下游/货量。

**效果体现在「平均触及句柄数」上（3.73 → 4.87），但这可能只是它照着更多句柄写了计划，
不代表它理解得更好。**

### 3. `belts_shown = 0` 这件事本身就是个硬伤

不管统计显不显著，**让模型在 163 条带子的世界里一条都看不见，是明显不合理的**。
修复的价值不完全由这个 A/B 的 p 值定义。

---

## 诚实边界

1. **n=15/臂，p=0.125。** 要检出这个效应量（3.73 → 4.87）大概需要 n≈60/臂。
2. **只测一个存档**（L4-obs，163 带子 / 7 诊断）。
3. **判据「平均触及句柄数」是我自己发明的**，不是 `QUALITY-METRICS.md` 的。
   它的意义是「模型处理了几个诊断点」，但**没有验证那些句柄是不是真的被正确处理了**。
4. **两臂共享同一端点**，并发可能共享状态。
5. ~~完全没有验证「动作能不能执行」~~ → **已补，见下节。**

## 执行重放：30 条里只有 2 条能跑通（7%）

按 `B2-EXECUTION-REALITY.md` 的 E1 口径重放（`.tmpverify/ab-real/replay.mjs`）：

```
臂     n   意图加cutter  可执行  任意计划可执行
OLD   15       2 ( 13%)     0 (  0%)     1 (  7%)
NEW   15       3 ( 20%)     1 ( 33%)     1 (  7%)
```

**30 条计划里，只有 2 条能被宏吃下。而且这 2 条里只有 1 条是产能动作。**

失败分布：

| 次数 | 原因 |
|---|---|
| 8 | `replace_run:precondition_failed` |
| 6 | `connect:occupied` |
| 4 | `connect:bad_type` |
| 3 | `connect:target_already_fed` |
| 2 | `connect:ambiguous_port` |
| 2 | `connect:endpoint_not_a_port` |
| 1 | `connect:unknown_field` |
| 1 | `trash_unused:occupied` |
| 1 | `insert_machine:ambiguous_site` |

⇒ **「产能动作 13% vs 20%」这两个数字在执行层变成 0/15 vs 1/15。**
这个差别毫无意义。

**这才是这个项目真正的瓶颈：不是「模型想不想对」，是「它写出来的计划能不能被吃下」。**

## 下一步该做什么

### A. 先对这 30 条做执行重放（便宜，且是必须的）

✅ **已做**。结果见上节：30 条里只有 2 条能执行。**产能动作那两个百分比没有意义。**

### B. 换一个「诊断不说具体句柄」的场景

这个实验最根本的问题是：**诊断已经点明了 7 个句柄，模型不需要带子表**。
要测「可见性」的价值，需要一个**诊断只给宏观信号、必须靠带子表自己找**的场景。

`capacity-scenario.json` 就是这种（诊断 0 条，只有 CAPACITY）。但它在预算上
本来就够用，所以测不出预算修复的价值。

⇒ **需要一个「大存档 + 诊断不点名」的场景。** 目前没有。

### C. 别再重复测这个场景

`AB-PROMPT-RESULT.md` 第一轮已经在这个方向上得到负结果（A 臂 9/10，补上下文反而有害）。
这一轮又得到一个弱结果。**两次都指向同一件事**：

> **当诊断已经把问题说清楚时，补充上下文没有价值，甚至有害。**

## 一个方法论收获

这一轮本来可以不做：`AB-PROMPT-RESULT.md` 第一轮已经给出了同样的结论。
我做的价值在于**确认修复本身没问题**（CAPACITY 确实出现了、带子确实显示了、
system 逐字节不变）—— 但**没确认修复有价值**。

⇒ **「修好一个真实缺陷」和「修好之后效果变好」是两件事。**
前者可以靠单元测试证明（`prompt_budget.test.mjs` 的 6 条），
后者需要在这个缺陷**真正造成伤害的场景**上测。

**这个场景不是。**
