## 0. 一句话结论

**关键的杠杆不是"让 LLM 更聪明"，而是"让 AI 拥有一个确定性的、可离线计算的世界模型"——
把聪明转移到代码上，把 LLM 留给它真正擅长的：**选择与修复**。**

本次研究实测证明了这条路的**可行性**（此前只是推测）：

| 已实测打通的能力 | 证据 |
|---|---|
| 从 `map.seed` 离线算出**整张资源图** | 与实机 **3002/3002 格逐格一致**（`facts/offline-map-reproduction.md`） |
| **离线复刻全部形状运算** | 与第三方公开求解器 **48,433/48,433 一致**（`facts/solver-cross-validation.md`）。⚠️ **范围要说清**：公开表是**拓扑表**（每层哪些象限非空，4 层 nibble），全码比对已覆盖多层；但它**不含 subshape 种类与颜色** —— 那部分靠 shape-ops.mjs 逐行对照游戏源码 + `CgScScCg` 端到端复放验证 |
| **零观测**在 2099 格外盲建 | 26ms，预测类型逐字节准确（`facts/offline-map-EXPERIMENTS.md` H3） |
| 2855 格外未生成区域的**物流真的在流动** | 离线解码存档看到 20 个预测物品（H5b） |
| **蓝图一次性实例化子工厂** | 2404 格外，1 次调用建成 49 个实体（H6）。⚠️ 只证明"**建成了**"，未证明这 49 个实体的**加工逻辑在工作**（§5.2） |
| 从目标反推**完整生产配方** | `CgScScCg`（level-11 真目标）端到端复放；solver 也能自动解出（`proto/solver-README.md`） |
| **cutter 槽位语义**（AI 最易错处） | 实机验证：槽0=左列、槽1=右列，与源码预测逐字符一致 |
| **蓝图粘贴的拐角确定性** | 两轮修复：`placeOne` 尊重 rv（v1）+ 粘贴包 `performImmutableOperation`（v2）；反例实验证明受扰邻居下拐角仍保 `code=3`（`facts/RV-FIX-verified.md`） |

**这意味着 AI 的工作方式应当是**：
```
离线求解（免费、全局、可反复试错）
    → 生成蓝图（一次调用）
    → 在最优位置粘贴（可在任何位置，包括未探索区域）
    → 用游戏自身的 hash 验证（免费真值）
    → 只用 LLM 处理"求解器失败"与"策略选择"
```

而不是：

```
观察 → 让 LLM 决定下一个动作 → 执行 → 再观察 …（O(动作数) 次 LLM 调用，长时程必然漂移）
```

**后者是当前 `src/agent/play.mjs` 的路子，也是前期研究（`04-ai-planning-research.md` §9.1/§9.2）
明确否决的路子。前者是本次研究实测打通的路子。**

## 1. 三层架构（去重、合并、排序后的结果）

```
┌───────────────────────────────────────────────────────────────────────┐
│ L3  策略层（LLM，每次尝试 1 次调用）                                  │
│     输入：目标形状 + 可用原料摘要 + 求解器/布局器的失败报告             │
│     输出：一个 DSL 程序（选择哪条产线、什么拓扑、在哪建）              │
│     禁止：坐标、旋转值、建筑 id —— 一律由下层推导                     │
│     何时才用：求解器/布局器给出多个候选需要取舍，或全部失败需要修复     │
├───────────────────────────────────────────────────────────────────────┤
│ L2  编译与验证层（纯确定性代码，零 LLM）           ← ★ 本次研究的重心  │
│     · 配方求解器：形状代数反向搜索（shape-ops.mjs 已验证）             │
│     · 地图模型：seed → 资源图（gen-resources.mjs 已验证）              │
│     · 布局编译器：配方 DAG + 机器几何 → 建筑放置 + 传送带路由          │
│     · 蓝图生成器：布局 → SZBP1 字符串（可一次粘贴整个子工厂）          │
│     · 三级验证器：形状 hash / 几何合法性 / 实机模拟（await 交付）      │
│     失败时输出**结构化批评**（错误码 + 首个差异 + 占用者），喂给 L3     │
├───────────────────────────────────────────────────────────────────────┤
│ L1  执行层（现有工具链，已实机验证）                                   │
│     place / place_path / paste_blueprint / bulk_delete                │
│     step / await（确定性快进）/ obs（可触发 chunk 生成）/ snapshot     │
└───────────────────────────────────────────────────────────────────────┘
```

**层间契约（可立即实现）**：
- L2 的布局编译器**只输出** `paste_blueprint` 或 `place_path` 动作列表，绝不输出坐标给 L3 看。
- L2 的三个验证器返回**机器可读的失败结构**（不是自然语言），L3 拿到它才能有效修复。
- L1 的每个写动作都返回 uid（需要先修 `place_path` 只返回 `first_uid` 的问题，见 §4）。

## 3. 设计取舍（哪些方案合并、哪些否决）

### ✅ 采纳并合并

| 来源方向 | 处理 |
|---|---|
| **观测升级**（2 个方案） | 合并为 2.3 + 2.4。**关键判断**：观测**不该**由 mod 端做复杂派生（会拖慢渲染线程），
应拆成"mod 端只加原始字段（堵塞/占用）+ agent 端做派生视图" |
| **规划与求解**（2 个方案） | 合并为 1.3 + 2.1。**求解**（形状代数）与**布局**（空间）是**两个不同问题**，
必须分层——公开生态里它们从来是分开的（`doomeer/factorio` 只做配方计量；MIP-Router 只做路由） |
| **LLM 接入**（2 个方案） | 合并为 1.5 + 3.5。**关键判断**：LLM 不该"驱动游戏"，只该"在确定性层失败时介入" |
| **蓝图与知识库**（2 个方案） | 合并为 3.1。**关键判断**：模块库要**小且经检查器过滤**（前期研究 §9.6 的明确警告），
≤3 条进上下文 |
| **基础设施**（2 个方案） | 合并为 1.4 + 3.4 + §4 的工具缺陷修复 |
| **宏观策略**（2 个方案） | 拆入 3.2 + 3.3 |

### ❌ 否决（明确不做，附理由）

| 否决项 | 理由 |
|---|---|
| **让 LLM 逐动作驱动游戏**（当前 `play.mjs` 的隐含方向） | O(动作数) 次 LLM 调用；长时程必然漂移；前期研究 §9.1/§9.2 有强证据（PlanBench、FLE）。**且本次研究已给出更好的替代** |
| **深度 RL / 世界模型（Dreamer/MuZero 类）** | 真模拟器就是世界模型，学一个近似的毫无意义；NetHack/FLE 的证据是"符号方法远胜" |
| **视觉输入（截图喂 LLM）** | BALROG 实测：给视觉表示**反而更差**；且我们有结构化 obs |
| **多 LLM agent 辩论/协调** | 2026 年协调层论文：多 agent 生产失败率 41–87%；小项目里 1 次调用胜过 4 个 agent 吵架 |
| **通用配方求解器从零重写** | **别人已经做完了**（TomasSirgedas 表已验证 100% 正确；nedsociety 的 BFS 枚举；cpcp1998 的完备枚举）。**复用 + 交叉验证**，把力气花在布局与迭代 |
| **照搬竞品 `Songxwn/shapez-auto` 的"每关清空重建"** | 官方 tips 反复强调"别拆旧厂，所有图形后面升级都要用"；清空重建会在高等级时**反复丢失已积累的产能**。这是它的**设计缺陷，不是我们该学的** |
| **Gurobi/MILP 求解布局** | 依赖专有软件（生态调研明确标为"坑"）；CP-SAT（OR-Tools）是免费替代，但仍是 npm 依赖——违背项目零依赖铁律。**先用确定性启发式 + 局部搜索**，不够再议 |
| **`eval_code` 式的逃生舱**（让 LLM 直接执行代码） | 生态调研列为"避免清单"；不可验证、不可回滚 |

## 4. ⚠️ 工具层必须修的问题（本次研究暴露）

这五条是**实际踩到的坑**，不是理论风险。**第一条是最关键的**：

| # | 问题 | 证据 | 建议 |
|---|---|---|---|
| **4.0** | **`placeOne` 丢弃调用方指定的 `rotationVariant`** —— 传送带的弯道变体**永远**由游戏的自动定向重算，蓝图里存的 rv 不被使用。这是"布局落不了地"的**根本原因** | `src/mod/shapez-ai-bridge.js:782`（签名无 rv 参数）+ `:866`（`place` 只收 `{building,x,y,r,variant}`）；M4 连续 5 次失败均由拐角 rv 不可控导致（`facts/ROOT-CAUSE-rotationVariant-override.md`） | 给 `placeOne` 加可选 `rotationVariant`；`paste_blueprint` 从 code 反推并传入（**约 10 行**） |
| 4.1 | **`bulk_delete` 会静默删掉真实工厂** | 主 Agent 实验时误删 **42 个真实实体**（`facts/INCIDENT-bulk-delete.md`）；后续又发生 3 次"边界差 1~2 格"的残留 | ✅ **已修**：加 `dry_run:true`（返回 `{would_delete, by_type, items[]}` 不执行），实机验证通过（`beba23a`） |
| 4.2 | **`place_path` 只返回 `first_uid`** | 无法精确回滚（AI 建错了只能靠大范围删除，危险） | 返回全部 uid，或加 `return_uids:true` |
| 4.3 | **`obs` 看不到传送带上的物品** | 带内物品是诊断堵塞的唯一直接证据，当前只能靠存档解码（可行但绕） | 加 `include_belt_items`；或把 §2.4 的存档路径封装成工具 |
| 4.4 | **`place_path` 的退化段（from==to）报 2001** | 每次布局实验都会踩（本次踩了 4 次） | 要么允许（=place 一格），要么在文档里显著标注 |
| **4.5** | **粘贴不检查建筑解锁等级** —— `tryPlaceBuilding` 只查碰撞/可放置（`logic.js:117`），**不查 `getIsUnlocked`**；我们也没查。于是 level 2 就能放 stacker，产出的配方"合法但游戏进程里没有" | 审查 F2 + 我核实 `logic.js:117-133`（无解锁判断）；`getIsUnlocked` 只在 UI 层（`buildings/*.js`） | 在 `place`/`place_path`/`paste` 前加一道 `meta.getIsUnlocked?.(root)` 校验，或至少在 obs 里回报"该建筑当前是否已解锁" |
| **4.6** | **SZBP1 没存 `originalRotation`** —— 邻居重算以 `originalRotation` 为基准（`belt.js:160`），存档 schema 有这字段（`static_map_entity.js`），但我们 stride=4 只存 rotation | 审查 F1(c) + 我核实 `blueprint.mjs`/§6 协议 + 上游 schema | SZBP1 扩到 stride=5 补 `originalRotation`；否则"贴到既有工厂旁"仍会走样 |
| **4.7** | **蓝图功能本身 level 12 才解锁** —— 但 mod 的 `paste_blueprint` 是特权路径（`charge:false`），level ≤11 用它"作弊"。这不是 bug 但**必须写进文档**，否则"AI 在 level 11 用蓝图"会让人误以为游戏那时就能蓝图 | 审查 F2 + `levels.js:241` reward_blueprints @ L12 | 文档标注"AI 用蓝图属 mod 特权，不代表游戏内已解锁"；若要"忠实模拟玩家"则 ≤L11 禁用 paste |

**另附两条观察（不是缺陷，但需文档化）**：
- `obs` 的 region 查询会**触发 chunk 生成**（副作用，已实测）。对 AI 是**有用**的（可当侦察用），但文档里应说明。
- **`place_path` 的水平/竖直段方向由参数顺序决定**（`from→to`），
  传参写反会让物流反向（本次踩过）。布局编译器必须按其**流动顺序**传参。

## 7. 如果只能做一件事

**做 `2.1 布局编译器`（配方 DAG → 空间布局 → 蓝图）。**

理由：
- 配方求解**已经有现成的正确答案**（公开表已验证 100%）——不是瓶颈。
- 世界模型**已经打通**（离线资源图 + 离线代数）——不是瓶颈。
- LLM 接入**已有清晰的学术结论**（LLM-Modulo）——不是瓶颈。
- 布局仍然是**我们要自己建的部分**——但注意（对抗审查 F3，竞品源码已核实）：
  **"布局没人解决"这个说法是错的**。竞品 `Songxwn/shapez-auto` 有**真的布局编译器**
  （`internal/plan/layout.go` 685 行：每 Op 占地模板 + 螺旋候选位 + **A\* 带路由** + hub 四边回退），
  更早的 `TomasSirgedas/Shapez-solver`（2022）也已输出**带拐角模块**的蓝图。
- 所以做布局的理由是**工程性的**（我们的 L2 落地链需要它，且要与蓝图/离线地图整合），
  不是"没人做过"。**差异化必须重述**（§0 已改）：
  **① 地图先验（seed→全图离线复现，竞品没有）② 确定性时间控制（step/await）
  ③ 存档解码的物流观测通道 ④ 通用可编程接口（MCP/协议契约/只读模式）。**

**但注意**：布局编译器**依赖第一批的地基**（求解器 + 形状代数 + 验证器）。
所以严格说"只能做一件事"的话，是**第一批的 1.1–1.4**——它们是布局编译器的前置。
