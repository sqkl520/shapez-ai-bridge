> 以及主 Agent 亲自完成并实测的若干关键突破。

## 0. 一句话结论

**关键的杠杆不是"让 LLM 更聪明"，而是"让 AI 拥有一个确定性的、可离线计算的世界模型"——
把聪明转移到代码上，把 LLM 留给它真正擅长的：**选择与修复**。**

本次研究实测证明了这条路的**可行性**（此前只是推测）：

| 已实测打通的能力 | 证据 |
|---|---|
| 从 `map.seed` 离线算出**整张资源图** | 与实机 **3002/3002 格逐格一致**（`facts/offline-map-reproduction.md`） |
| **离线复刻全部形状运算** | 与第三方公开求解器 **48,433/48,433 形状 100% 一致**（`facts/solver-cross-validation.md`） |
| **零观测**在 2099 格外盲建 | 26ms，预测类型逐字节准确（`facts/offline-map-EXPERIMENTS.md` H3） |
| 2855 格外未生成区域的**物流真的在流动** | 离线解码存档看到 20 个预测物品（H5b） |
| **蓝图一次性实例化子工厂** | 2404 格外，1 次调用建成 49 个实体（H6） |
| 从目标反推**完整生产配方** | `CgScScCg`（level-11 真目标）7 步链，端到端验证（`facts/ops-semantics-VERIFIED.md`） |
| **cutter 槽位语义**（AI 最易错处） | 实机验证：槽0=左列、槽1=右列，与源码预测逐字符一致 |

**这意味着 AI 的工作方式应当是**：
```
离线求解（免费、全局、可反复试错）
    → 生成蓝图（一次调用）
    → 在最优位置粘贴（可在任何位置，包括未探索区域）
    → 用游戏自身的 hash 验证（免费真值）
    → 只用 LLM 处理"求解器失败"与"策略选择"
```

而不是：

```
观察 → 让 LLM 决定下一个动作 → 执行 → 再观察 …（O(动作数) 次 LLM 调用，长时程必然漂移）
```

**后者是当前 `src/agent/play.mjs` 的路子，也是前期研究（`04-ai-planning-research.md` §9.1/§9.2）
明确否决的路子。前者是本次研究实测打通的路子。**

## 1. 三层架构（去重、合并、排序后的结果）

```
┌───────────────────────────────────────────────────────────────────────┐
│ L3  策略层（LLM，每次尝试 1 次调用）                                  │
│     输入：目标形状 + 可用原料摘要 + 求解器/布局器的失败报告             │
│     输出：一个 DSL 程序（选择哪条产线、什么拓扑、在哪建）              │
│     禁止：坐标、旋转值、建筑 id —— 一律由下层推导                     │
│     何时才用：求解器/布局器给出多个候选需要取舍，或全部失败需要修复     │
├───────────────────────────────────────────────────────────────────────┤
│ L2  编译与验证层（纯确定性代码，零 LLM）           ← ★ 本次研究的重心  │
│     · 配方求解器：形状代数反向搜索（shape-ops.mjs 已验证）             │
│     · 地图模型：seed → 资源图（gen-resources.mjs 已验证）              │
│     · 布局编译器：配方 DAG + 机器几何 → 建筑放置 + 传送带路由          │
│     · 蓝图生成器：布局 → SZBP1 字符串（可一次粘贴整个子工厂）          │
│     · 三级验证器：形状 hash / 几何合法性 / 实机模拟（await 交付）      │
│     失败时输出**结构化批评**（错误码 + 首个差异 + 占用者），喂给 L3     │
├───────────────────────────────────────────────────────────────────────┤
│ L1  执行层（现有工具链，已实机验证）                                   │
│     place / place_path / paste_blueprint / bulk_delete                │
│     step / await（确定性快进）/ obs（可触发 chunk 生成）/ snapshot     │
└───────────────────────────────────────────────────────────────────────┘
```

**层间契约（可立即实现）**：
- L2 的布局编译器**只输出** `paste_blueprint` 或 `place_path` 动作列表，绝不输出坐标给 L3 看。
- L2 的三个验证器返回**机器可读的失败结构**（不是自然语言），L3 拿到它才能有效修复。
- L1 的每个写动作都返回 uid（需要先修 `place_path` 只返回 `first_uid` 的问题，见 §4）。

## 2. 推荐路线图（按批次，每批独立可验收）

### 🥇 第一批：地基（**必须最先做，其余全依赖它**）

**目标：把本次研究已验证的三块能力，固化成仓库里的一等公民。**

| # | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|
| 1.1 | `src/ai/shape-ops.mjs`（从 `proto/` 提升为正式模块）+ 回归测试 | 无 | `node test/shape_ops_selftest.mjs` 全绿；含与公开配方表的抽查对拍 |
| 1.2 | `src/ai/world.mjs`（seed → 资源图；从 `proto/gen-resources.mjs` 提升） | 无 | 对 level-11 存档的 seed 复现 **3002/3002** 一致（已有测试可搬） |
| 1.3 | `src/ai/solver.mjs`（配方求解器，见 `designs/solver-*.md`） | 1.1 | `CgScScCg`、`CrCrCrCr`、`----CuCu`、及一个多层形状全部解出；与公开表一致率 ≥95% |
| 1.4 | `src/ai/verify.mjs`（形状/几何验证器） | 1.1 | 能对任意 SZBP1 蓝图做形状合法性检查；错误结构化 |
| 1.5 | `docs/AGENT-PROMPT.md` + `play.mjs --llm` 骨架（接口先行，可 mock） | 无 | 定义了 L3 的输入/输出契约与 DSL 语法；用脚本 mock 可端到端跑通 |

**为什么这批必须先做**：L2 是"聪明"的所在地。没有它，LLM 只能做笨事。
**工作量估计**：1.1/1.2 是把已验证的原型搬进 `src/`（小时级）；1.3 是主要工作量（天级）；1.4/1.5 中等。

### 🥈 第二批：闭环（让 AI 真的能"自己玩"）

| # | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|
| 2.1 | **布局编译器** `src/ai/layout.mjs`：配方 DAG → 机器+传送带几何 → SZBP1 | 1.1–1.4 | 能对 `----CuCu`（1 切割机 + 2 矿机 + 带）自动生成蓝图并在实机粘贴成功、`await` 到交付增加 |
| 2.2 | **一键建线** `play.mjs build <target>`：求解 → 布局 → 粘贴 → 验证 | 2.1 | 全自动完成 level-2 目标（`----CuCu`，40 个） |
| 2.3 | **战场感知** `obs` 增强：拥堵/死端/供给缺口 | 无（mod 端加字段） | 见 `facts/observation-gaps.md` 的优先级清单；至少实现"传送带是否堵塞" |
| 2.4 | **存档物流观测**：`save_now` + 离线解码 `beltPaths` 封装成 `play.mjs traffic` | 无 | 能打印真实工厂的带内物品分布（本已实测可行，只是封装） |

**为什么第二批是闭环**：2.1+2.2 打通"从目标到建成"的完整链路——这就是"AI 能玩"的定义。
2.3/2.4 是让 AI **看得见自己建的东西跑得怎么样**（当前 obs 看不到带内物品，这是最大观测盲区）。

### 🥉 第三批：规模化与自适应（"越玩越好"）

| # | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|
| 3.1 | **模块库**：参数化子工厂模板（feeder / 切割模块 / 上色模块） | 2.1 | ≥3 个模块，每个可参数化生成蓝图并独立验证 |
| 3.2 | **选址优化**：基于离线资源图的物流成本最小化 | 1.2 | 对当前地图给出"每个资源簇到 hub 的最优连接方案"，含成本对比 |
| 3.3 | **改造/扩张**：按等级目标 re-plan（保留旧产线） | 2.2 | 从 level-N 到 N+1 的自动扩张（不拆已有产线）——**注意官方 tips 反复强调"别拆旧厂"** |
| 3.4 | **能力分（benchmark）**：量化"AI 变聪明了" | 2.2 | 定义并实现一个分数（如：达到 level N 的动作数/墙钟/LLM 调用数） |
| 3.5 | **LLM 修复循环**：求解器/布局器失败时调 LLM | 1.5 + 2.1 | 构造人为失败案例，验证 LLM 能在 ≤3 次尝试内修复 |

## 3. 设计取舍（哪些方案合并、哪些否决）

### ✅ 采纳并合并

| 来源方向 | 处理 |
|---|---|
| **观测升级**（2 个方案） | 合并为 2.3 + 2.4。**关键判断**：观测**不该**由 mod 端做复杂派生（会拖慢渲染线程），
应拆成"mod 端只加原始字段（堵塞/占用）+ agent 端做派生视图" |
| **规划与求解**（2 个方案） | 合并为 1.3 + 2.1。**求解**（形状代数）与**布局**（空间）是**两个不同问题**，
必须分层——公开生态里它们从来是分开的（`doomeer/factorio` 只做配方计量；MIP-Router 只做路由） |
| **LLM 接入**（2 个方案） | 合并为 1.5 + 3.5。**关键判断**：LLM 不该"驱动游戏"，只该"在确定性层失败时介入" |
| **蓝图与知识库**（2 个方案） | 合并为 3.1。**关键判断**：模块库要**小且经检查器过滤**（前期研究 §9.6 的明确警告），
≤3 条进上下文 |
| **基础设施**（2 个方案） | 合并为 1.4 + 3.4 + §4 的工具缺陷修复 |
| **宏观策略**（2 个方案） | 拆入 3.2 + 3.3 |

### ❌ 否决（明确不做，附理由）

| 否决项 | 理由 |
|---|---|
| **让 LLM 逐动作驱动游戏**（当前 `play.mjs` 的隐含方向） | O(动作数) 次 LLM 调用；长时程必然漂移；前期研究 §9.1/§9.2 有强证据（PlanBench、FLE）。**且本次研究已给出更好的替代** |
| **深度 RL / 世界模型（Dreamer/MuZero 类）** | 真模拟器就是世界模型，学一个近似的毫无意义；NetHack/FLE 的证据是"符号方法远胜" |
| **视觉输入（截图喂 LLM）** | BALROG 实测：给视觉表示**反而更差**；且我们有结构化 obs |
| **多 LLM agent 辩论/协调** | 2026 年协调层论文：多 agent 生产失败率 41–87%；小项目里 1 次调用胜过 4 个 agent 吵架 |
| **通用配方求解器从零重写** | **别人已经做完了**（TomasSirgedas 表已验证 100% 正确；nedsociety 的 BFS 枚举；cpcp1998 的完备枚举）。**复用 + 交叉验证**，把力气花在布局与迭代 |
| **照搬竞品 `Songxwn/shapez-auto` 的"每关清空重建"** | 官方 tips 反复强调"别拆旧厂，所有图形后面升级都要用"；清空重建会在高等级时**反复丢失已积累的产能**。这是它的**设计缺陷，不是我们该学的** |
| **Gurobi/MILP 求解布局** | 依赖专有软件（生态调研明确标为"坑"）；CP-SAT（OR-Tools）是免费替代，但仍是 npm 依赖——违背项目零依赖铁律。**先用确定性启发式 + 局部搜索**，不够再议 |
| **`eval_code` 式的逃生舱**（让 LLM 直接执行代码） | 生态调研列为"避免清单"；不可验证、不可回滚 |

## 4. ⚠️ 工具层必须修的问题（本次研究暴露）

这四条是**实际踩到的坑**，不是理论风险：

| # | 问题 | 证据 | 建议 |
|---|---|---|---|
| 4.1 | **`bulk_delete` 会静默删掉真实工厂** | 主 Agent 实验时误删 **42 个真实实体**（`facts/INCIDENT-bulk-delete.md`）。靠实验前 snapshot 才恢复 | 加 `dry_run:true`（返回将删清单）或 `only_uids:[...]` 白名单 |
| 4.2 | **`place_path` 只返回 `first_uid`** | 无法精确回滚（AI 建错了只能靠大范围删除，危险） | 返回全部 uid，或加 `return_uids:true` |
| 4.3 | **`obs` 看不到传送带上的物品** | 带内物品是诊断堵塞的唯一直接证据，当前只能靠存档解码（可行但绕） | 加 `include_belt_items`；或把 §2.4 的存档路径封装成工具 |
| 4.4 | **`place_path` 的拐角语义** | 开发期踩过；`bench_b3.mjs` 的 `placeLane()` 是逐格显式版 | 在 `place_path` 内做正确的拐角处理，或文档明确"多段请用 placeLane 模式" |

**另附一条观察（不是缺陷，但需文档化）**：`obs` 的 region 查询会**触发 chunk 生成**（副作用）。
已实测（H2）。这对 AI 是**有用**的（可当侦察用），但文档里应说明。

## 6. 与前期研究（`04-ai-planning-research.md`）的关系

| 前期结论 | 本次研究的处理 |
|---|---|
| LLM 不做规划主体，确定性求解器做主 | ✅ **被本次实测强化**：我们把"确定性"从"应该"变成了"已验证可离线复刻整个游戏代数" |
| 不让 LLM 碰坐标/旋转/建筑 id，输出 DSL 程序 | ✅ 维持，且**竞品也这么做**（`Songxwn/shapez-auto` 的 LLM 只输出加工树） |
| 自评不可靠，必须执行式验证 | ✅ 维持；补充：**游戏自身的 shape hash 是免费真值**，且 `await` 提供端到端验证 |
| 不要世界模型 / 深 RL / 视觉 / 多 agent | ✅ 维持，本次未发现需要推翻的证据 |
| 技能库要小且经检查器过滤（≤3 条） | ✅ 维持 |
| 4 层架构（L0 模拟器 / L1 布局搜索 / L2 编译器+验证 / L3 LLM） | ✅ **采纳但重新分层**：本次的 L1 = 执行（工具链，已存在），L2 = 编译+验证（**本次重心**），L3 = 策略。原方案的"L1 布局搜索"被并入 L2，因为本次发现**布局与配方必须一起编译**（几何约束来自机器槽位） |
| 未做：落到真实 API、源码核证、可运行原型 | ✅ **本次补齐了**：3 个可运行原型 + 11 份带证据的事实文件 + 6 个实机实验 |
| 它没提到"离线世界模型" | ⭐ **本次的最大增量**：整张地图 + 全部形状代数可离线计算，已实测 |

## 7. 如果只能做一件事

**做 `2.1 布局编译器`（配方 DAG → 空间布局 → 蓝图）。**

理由：
- 配方求解**已经有现成的正确答案**（公开表已验证 100%）——不是瓶颈。
- 世界模型**已经打通**（离线资源图 + 离线代数）——不是瓶颈。
- LLM 接入**已有清晰的学术结论**（LLM-Modulo）——不是瓶颈。
- **唯独"把生产 DAG 摆成不交叉、不堵塞、能运转的工厂"没有任何现成方案**——
  这才是真问题，也是竞品 `shapexw/shapez-auto` 用"每关清空重建 + 简单摆法"**绕开**的问题。
- 谁解决了布局，谁就解决了"AI 玩工厂游戏"的核心。

**但注意**：布局编译器**依赖第一批的地基**（求解器 + 形状代数 + 验证器）。
所以严格说"只能做一件事"的话，是**第一批的 1.1–1.4**——它们是布局编译器的前置。
