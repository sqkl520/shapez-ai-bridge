## 关键发现（布局编译器必读）

**1. stacker 的输入槽 → 层 的映射（实测）**
```
输入槽 0（左格 (0,0) 的 bottom）→ 成为**下层**（layer 0）
输入槽 1（右格 (1,0) 的 bottom）→ 成为**上层**（layer 1）

实测：槽0 收 CuCuSuSu、槽1 收 RuRuCuCu → 输出 CuCuSuSu:RuRuCuCu
      （冒号前 = 下层 = 槽0 的料）
```
这与源码 `shapeActionStack(lowerDefinition, upperDefinition)` 的调用顺序一致
（`item_processor.js` 的 process_STACKER 用 `items.get(0)` 作 lower）。

**2. stacker 是布线最难的一个（也解释了它为什么是 MAM 瓶颈）**
```
   ┌─ 输出（朝上）
   │
 [stacker]   ← 两个输入**都从下方**进
   ↑     ↑
 带A    带B    ← 两条平行的、都朝上的带子
```
→ **两条输入带必须平行且都朝上**，而输出带从 stacker 正上方朝天走 ——
**输出带与两条输入带在同一竖直平面内会冲突**（输出在左格上方，输入带 A 也在左格下方）。
所以 stacker 的输入必须来自**不同行**（或使用隧道），这是布局编译器必须专门处理的模式。

**3. 本次用的绕行方案（可复用模板）**
```
矿B 的料：先竖直上到比 stacker 输入行**高一格**的"横向车道"，再水平搬运，最后拐回
→ 即：把第二条输入"抬高一行再横向搬运"，避开输出带
```

## 对布局编译器的最终结论

**它必须内置的几何规则表**（全部已实测）：
1. 矿机输出**恒为 top**（朝上）—— 所以矿机的料总要"先往上走"。
2. cutter/stacker/mixer/rotater 都是**下进上出**（沿 +y 流动）。
3. painter 是**左进（形状）、上进（颜料）、右出**（沿 +x 流动）。
4. **cutter 的两条输出带都要朝上**；**stacker 的两条输入带都要朝上**且要**避开输出带**。
5. hub 四边都能进 —— 布局不必挤在一个方向。

→ **结论**：布局就是"**处理这些方向冲突**"。行式布局（每层一条水平轨道、竖直连接）
天然匹配"下进上出"的机器；painter 需要单独的横向通道；stacker 需要"抬高一行绕行"的模式（本文验证过）。
