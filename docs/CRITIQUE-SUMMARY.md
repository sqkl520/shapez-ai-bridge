# 锐评汇总（4 个独立 Agent 交叉批判）

> 2026-10-20/21 由 4 个独立 Agent 完成（其中红队因 API 超时中断后按规则**原样重跑**）。
> 每份锐评独立分析、互不可见。本文件汇总冲突与共识，并给出裁决。

## 一、四份锐评的核心结论

### A. 产品定位（工具还是 mod？）
**结论：都不是——它是「以 mod 形态分发的游戏控制面（control plane）」。**
- mod 只是**安装器形态**（单文件 .js 进 mods 目录）；产品本体是游戏外的工具链（MCP/HTTP/基准）。
- 类比最接近 **obs-websocket**：游戏内插件，向外部工具暴露 WS 控制 API。
- 抓出 2 个**真 bug**（已核实并修复）：
  - `METADATA.website` 是占位符 `https://github.com/`——游戏 mods 菜单/存档对话框会渲染成可点链接。
  - `doesNotAffectSavegame:false` 与注释自相矛盾——**实测证据**：真实存档里确实写入了 `{"id":"shapez-ai-bridge","website":"https://github.com/",...}`，卸载后读档会弹"missing mods"警告。
- 命名建议：`shapez-mcp`（吃 MCP 生态搜索红利）> `shapez-control` > `shapez-agent-harness`。

### B. 技术红队（5 次实证实验）
**8 个高/中严重度缺陷，其中 3 个已实证可触发：**

| 严重度 | 发现 | 证据 |
|---|---|---|
| 高 | **任意网页可控制游戏**：无 Origin 校验 + `text/plain` 绕过预检（实测 `Origin: evil.example.com` 连 `/mod` 返回 101） | 实证 |
| 高 | **快照路径穿越可任意读写文件**：`snapshot_load` 的 `name` 未过滤 `..\`（实测在快照目录外成功写入文件） | 实证 |
| 高 | `/mod` 槽位可被冒充/踢占（任何新 WS 连接直接替换旧 mod） | 实证 |
| 高 | 并发 `load_save`/`new_game` 返回假成功（mod 侧无 RPC 队列） | 推理 |
| 高 | 超时≠未执行（桥接删 pending，游戏侧动作已生效，AI 重试=重复动作） | 推理 |
| 高 | MCP 超时 120s < 桥接 180s → 长 await 被误报"桥接不可达" | 实证（口径） |
| 高 | `.pre-restore` 单槽位——连续 restore 会覆盖含原始档的备份 | 实证（代码路径） |
| 高 | `gv` 校验形同虚设（硬编码常量，从不读真实游戏版本） | 推理 |
| 中 | `step` 的 `ticks_run` 是调用次数不是真实 tick 数 | 推理 |
| 中 | 文档称 2005 为超时码但实现从不发出（全用 2004） | 实证 |
| 低 | `read_only` 是软闸（同权限可改配置重启）；`WRITE_OPS` 是死代码 | 推理 |
| — | **MCP stdout 纪律：该面未发现重大问题** | 实证 |

**最可能导致一天内卸载的三问题**：① 按 README 启用 token → mod 连不上（全链路 1005）② MCP 120s 掐断长 await 并谎报"桥接不可达"③ 连续 load/new_game 假成功 / 超时重试重复执行。

### C. 新用户旅程（真实执行）
**宣称 3 步，实测约 9 步**。四个 README 完全没写的步骤：下载 ZIP（无 URL 无 clone 命令）、解压、装 Node、在正确目录开终端。
- **成就警告顺序错了**：安装在**完成之后**才告知（应在决定之前）。
- 桥接是阻塞进程，README 没说"要开第二个终端"。
- 卸载后 `.bak-*` 与 `modsettings_*.json` 残留（"删一个文件就干净"不再严格成立）。
- 尖锐论点：**"跑桥接、配 MCP JSON 的用户本就活在命令行，GUI 是镀金"**——但它同时承认真正的断点是"拿不到仓库"。
- 建议：发 Release ZIP + 快速开始改 6 行带序号清单 + 把 `play.mjs observe` 提为"不接 AI 也能看"的演示。

### D. 生态对比（GitHub API 实测星数）
**重大发现：存在一个同游戏同架构的竞品** `QXIKmIJ/shapez-ai`（0★，比我们早 4 天发布）。
- 坐标图位置：我们是"单游戏专用 × 开发者向"象限里**安装成本最高**的（clone + 手动常驻 + 填绝对路径）。
- 同类最佳实践：`minecraft-mcp-server` 789★ 用 `npx -y github:...` 一行进配置；`NagiBridge` 108★（星露谷）发含编译产物的 Release zip。
- 我们的**真实差异点**（竞品未见等价物）：① 确定性 `step(ticks)`+`await` 原语 ② 结构性原语复刻游戏成本模型 ③ 2001/2002/2003 错误语义 + hint。
- 五个盲区（按威胁排序）：分发方式、无玩家通道、版本硬锁 1.5.6、benchmark 名不副实、"1.x 社区确无蓝图字符串标准"（SZBP1 不算重复造轮子，经源码核验）。
- **抄袭清单**：① 抄 `npx` 一行分发 ② 抄 civ6-mcp 的 step 差分摘要 ③ 抄 NagiBridge 双轨 Release zip。

## 二、四份锐评的交叉验证与冲突裁决

### 共识（≥2 份锐评独立发现）
1. **"30 秒快速开始"是假的**（A + C 独立发现，C 给出 9 步核账）。
2. **普通用户拿不到仓库**（A + C + D：无 Release、无 clone 命令、无 zip）。
3. **分发是最大瓶颈**（A + C + D 一致）。
4. **存档类操作有真实缺陷**（A 发现 mods 列表污染【实证】；B 发现 `.pre-restore` 覆盖 + gv 校验失效【推理/实证】）。

### 冲突与裁决

**冲突 1：GUI 是镀金还是必需？**
- C 说："GUI 是镀金，真正的断点是拿不到仓库"。
- 用户明确要求 GUI，D 的坐标图显示我们安装成本最高。
- **裁决：C 的批评校正了 GUI 的定位——GUI 服务"不碰命令行"的新画像（shapez 玩家/MCP 折腾者），而不是替代 CLI 用户。** C 指出的问题（成就警告顺序、阻塞进程、目录搞错）恰恰是 GUI 天然解决的——GUI 把 9 步压到"下载 → 双击 → 点安装"。C 的核心论据"拿不到仓库"由 Release ZIP 解决，GUI 与 ZIP 是配套关系。

**冲突 2：卸载残留（C 说问题，A 说 bug）**
- **裁决：都是真的，方向一致**——A 的 `doesNotAffectSavegame` 修复（已做）会止住新增污染；C 的 `.bak-*` 残留应由 GUI 的卸载功能顺带清理。
