# 「实验 9/10、真机 0/1」不是 labs-vs-live 差距 —— 实验量错了指标

2026-11-21。

## 结论先说

1. **之前那条「诊断在 prompt 75% 处所以模型看不见」的假说是错的。** 实验装置与真机
   用的是**同一份 11358 字符的 prompt**，`## DIAGNOSIS` 在两边都从第 8573 字符（75.5%）
   开始，逐字节相同。位置不是变量。
2. **「9/10 vs 0/1」是采样噪声，不是效应。** 同一份世界快照、同一个仓库基线上，
   实验室基线（E 组，当前仓库原样 hint）是 **6/10**；真机那一次 0/1 的 p ≈ 0.4。
3. **真正的差距在另一个维度，而且比原来以为的严重得多：**
   模型「选中根因」9/10，**能真正落地只有 1/10**。实验的判据从来只测选择，没测落地。

## 一、位置假说怎么被推翻的

`tools/probe-live-prompt.mjs` 用**真机那一轮的完整参数**重建 prompt
（`exp-chain-hint.mjs` 只传 8 个参数，`loop.mjs:4063` 实际传了 16 个 ——
这是最初怀疑的来源），结果：

```
真机同参数重建   system 4725 + user 11358 = 16083
实验同参数重建   system 4725 + user 11358 = 16083
user 长度差 0 字符
DIAGNOSIS 位置：真机 8573 (75.5%)   实验 8573 (75.5%)
```

多传的那些参数（`itemsOnBelts` / `priorAttempts` / `runLog` / `stickyGoal`）
在这个场景里**都是空的**（首轮、无历史），所以整段被 `filter` 掉了。
`prompt_chars` 在真机是 16045、这里是 16083 —— 差 38，来自真机第二轮
比第一轮多了 671 字符的 `LAST ROUND`，以及重建时用的是最新 obs（多 1 条带子）。

⇒ **实验装置复现的就是真机条件，一点没差。**

## 二、那为什么是 9/10 vs 0/1

因为 0/1 就是 1 个样本。

| | 命中根因 | 落地 |
|---|---|---|
| 实验 E（当前仓库基线，同一快照） | 6/10 | **2/10** |
| 实验 F6（完整链+句柄） | 9/10 | **1/10** |
| 实验 D6 | 6/10 | **2/10** |
| 真机 `r-20261121100232-d10f` | 0/1 | 0/1 |

E 组 6/10 与真机 0/1 的 Fisher 单尾 p ≈ 0.4。**没有证据说明真机更差。**

但请注意最右列：**无论哪一组，「命中根因」和「能落地」之间都差着 5 倍。**

## 三、真正的差距：能选中，但落不了地

新工具 `tools/replay-plan.mjs` 把实验里采集的每个计划**原样重放**给
`buildTxPlan`。`connect.mjs` 等宏零游戏写操作，只读 `ctx.entities` 并规划，
所以整条链路可以在离线快照上跑，**拒绝原因与真机逐字相同**
（已用真机那两个计划验证：重放出 `connect:occupied` + `connect:port_already_bound`，
与真机 `plan-last.json` 一字不差）。

F6 组（9/10 选中根因）的落地情况：

| 样本 | 选中 | 落地 | 拒绝原因 |
|---|---|---|---|
| F-01 | ✓ | ✗ | PLAN_REJECTED：可交付带子 390→180（-54%） |
| F-02 | ✓ | ✗ | PLAN_REJECTED：-40% |
| F-03 | ✓ | ✗ | PLAN_REJECTED：-74% |
| F-04 | ✓ | ✗ | port_already_bound ×2 / occupied |
| F-05 | ✓ | ✗ | occupied ×3 |
| F-06 | ✗ | ✗ | port_already_bound / occupied / ambiguous_port |
| F-07 | ✓ | ✗ | LLM_COORD：$ref 多带了 to/from 键 |
| F-08 | ✓ | ✗ | PLAN_REJECTED：-49% |
| F-09 | ✓ | ✗ | PLAN_REJECTED：-49% |
| **F-10** | ✓ | **✓** | —— |

**「预演闸门」是最大的单一拒绝源**（5/10），不是 `occupied`。

## 四、预演闸门没有算错 —— 代价是真的

这是本节最要紧的一条：**不要因为它拦住了「正确的修法」就去放宽它。**

模型要修的是 `painter C3` 的 color 槽。给这个槽供料**必须**从一台
**阴性矿（blue/green）**拉线。而这份世界里，矿机位置是这样的：

```
uid=17644 (-10,9)  ore=CuCuCuCu  到 C3 = 10    ← 最近，但是形状矿，供不了色料
uid=15113 (5,5)    ore=red       到 C3 = 19
uid=17120 (-10,-6) ore=green     到 C3 = 25    ← 最近的色料源
uid=16586 (37,-10) ore=blue      到 C3 = 66    ← 模型选的 M7
uid=16614 (89,-39) ore=blue      到 C3 = 147
```

**所有蓝色矿机都在 60 格开外，且中间是密度很高的既有带子网。**
`connect M7 → C3.color` 实测要铺 **70 格**（Z 形），
`replace-would-disconnect` 警告成真：覆盖掉 288 条正在工作的带子。

```
B 的候选路径：
  choice.shape = "Z", turns = 2
  legs = right 1, bottom 25, left 43
  warnings = [replacing-belts, replace-would-disconnect, hub-entry-chosen]
```

所以「-288 可交付带子 / 74%」是**准确的物理代价**，闸门拦得对。
问题在更上游：**这个工厂的色料源在远端，而模型没有便宜的路可走。**

## 五、把这条链写下来

```
真正的阻塞（按发现顺序）
  ① 诊断：painter C3 的 color 槽空                     ← MACHINE_STARVED 已经看得见
  ② 模型：选中它（9/10）                               ← hint 改造已经解决
  ③ prompt：没有距离信息，模型挑了 66 格外的矿机        ← 信息缺口，尚未解决
  ④ 宏：那条路要 70 格、覆盖 288 条在跑的带子           ← 物理事实
  ⑤ 闸门：拦住它（对）                                 ← 工作正常
  ⑥ 没有任何机制告诉模型「换一台近的」或「先挪矿机」    ← 真正的缺口
```

第 ⑥ 条是本轮新发现的、也是接下来该做的。

## 六、顺带修正的两条错误

**① `tools/replay-plan.mjs` 第一版把每个失败都读成 `null (null)`。**
`buildTxPlan` 失败返回的是 `{ok:false, code, diagnosis:{…}}`，
而第一版按 `{rejected:{code,layer}}` 去读 —— 照臆想的 schema 写的。
这条在 `never-write-code-against-imagined-schema` 里记过一次，这是第二次。

**② 重放时必须用 `partial: true`。** 真机 `PARTIAL_APPLY` 默认开，
语义是「失败的跳过、成功的提交」。用全有或全无去重放会低估落地率。

## 七、下一步

不再改 hint 措辞 —— 那已经到头了（9/10）。要动的是第 ③ 和第 ⑥：

1. **把距离/矿种送进 MACHINES 段。** 现在矿机那行只有 `hub 东北 47 格`，
   既没写它在挖什么，也没写它离哪台机器近。模型只能瞎挑。
   一条 `M7 miner blue · 到 C3 66 格 输出=right:out(→无)` 就把 ③ 补上了。
2. **给「换台近的」一个可执行形态。** 最近的色料源 `M13/M14`（green，到 C8 很近）
   连不上 C3，但可以先接 C8 的 mixer，让 mixer 的产物走既有 B96 到 C3 ——
   这条路几乎不铺新格子。**模型不知道 B96 已经在跑**，因为它不在 BELTS 的 7 条里。

第 2 条尤其值得做：它把「-74% 的大工程」换成「接一格」。
