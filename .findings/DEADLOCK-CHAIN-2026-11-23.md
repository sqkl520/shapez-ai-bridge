### upper 那一路背后是什么

⇒ 它朝**上**，出口格 `(-1,5)` = stacker 的 upper 槽。**接对了**。

（`debug_items` 的 `boundAcceptor` 对这条路径返回字符串 `"yes"` 而不是坐标 ——

## 二·六、货是「顶死的」还是「陆续停下的」—— 这决定了因果方向

有人会问：259 件堵住会不会是**零产出的结果**，而不是原因？

实测否定了这个反向因果。看货之间的间距（`items.belts[].pos` 的差分）：

```
path 8   259 件   间距全部 0.63（258 个间隙，无一例外）   ← 顶死
path 4     8 件   间距全部 0.63                          ← 顶死
path19     3 件   间距全部 0.63                          ← 顶死
path20    87 件   间距全部 0.63                          ← 顶死
path 0     4 件   间距 2.36                              ← 松散，在流动
path15     4 件   间距 2.36                              ← 松散，在流动
```

`0.63` 正是游戏的最小间距 `itemSpacingOnBelts`。间距恰好等于它 ⇒ 货被**顶住**了。
间距 2.36 = 3.7 倍 ⇒ 还在淌（`path0`/`path15` 的终点是垃圾桶，在慢慢吃）。

跨全部 517 个死亡快照：

```
带上的货总数          258385 件
其中挤在 0.63 间距带上  254168 件（98.4%）
```

⇒ **堵住是因，零产出是果。** 97% 以上的货在物理上被顶死，不是「因为停了所以堆在那」。

⚠️ 这条判据（间距是否恰为 0.63）比「路径满载率」更硬 —— 它直接读物理，
不依赖 `capacity = cells / 0.63` 这个我自己的估算公式。

## 七、更正：259 件是**果**，不是因

批判 Agent（`.findings/CRITIQUE-DEAD-WORLD-2026-11-23.md`）用 path8 的时间轨迹
推翻了本文最初的因果结构。核实无误：

```
死亡那一刻   r-20261115121951-39ea  tick 556784（2026-11-15 12:19:51）
             path8 = 102 格 / 162 件
             produced_total = {}           ← 世界已经死了

path8 首次到 259 件  r-20261116154241-6124  tick 660986（2026-11-16 15:42）
             → 比死亡晚 28.9 游戏小时
```

**259 件出现在死亡之后 28 小时。** 它不可能是死因；它是死后的堆积，
而且其中一部分是**我们后来的动作**把 path8 从 102 格拉长到 165 格攒出来的。

更关键的一条：死亡之前（11-15 11:13，世界还在正常产出 10 个形状键）：

```
path8 = 162 件 / 102 格 = 每格 1.59 件
标称容量 1/0.63 = 1.587 件/格
⇒ 那时 path8 **已经是 100% 满载**
```

**满载状态和「世界在产出」同时存在。** 所以「满载」既不是死因，也不是死亡的标志。

### 真正的死因（另一个 Agent 独立查到的同一个动作）

`.findings/ROOTCAUSE-COLOR-SLOT-2026-11-23.md` 与批判报告指向同一个事件：

```
2026-11-15 12:14:35   r-20261115121125-264d  r3
                      insert_machine(trash) @(-3,-8)
                      tx_plan 只声明 destroys:[15021] + placements:1
                      但游戏重算邻居：
                        belt#14953@(-3,-7)  rv 2 → 0   （左→下转角 变成 左→右直带）
                        belt#15019@(-2,-7)  方向也翻转
2026-11-15 12:19:51   produced_total 从 10 个键变成 {}（dt = 5 分钟）
```

**一个「放垃圾桶」的动作，通过游戏的邻居重算，静默地把 painter 的供料主链改道了。**

### 这一节保留下来有什么用

几何部分（§一）仍然准确：painter color 槽空、stacker lower 没料、path8 末端接
upper —— 这些是**当前状态**的正确描述，只是它们**不是**死亡的原因。

对 `WORLD_FROZEN` 的影响：
- 判据（零产出 + 某条路径满载）描述的是**结果状态**，不是根因。
- 它给的「先通开」建议，作用对象是**后果**，不是原因。
- 真正该修的是喂 painter 的 color 槽 —— 那是**另一个方向**。
- 真调 LLM 实验也印证了：`remove_run` 那 12/12 落地的动作，判词全是 `churn`
  （259 件只是从矿机那端断开，世界仍然零产出）。

⇒ **`WORLD_FROZEN` 的定位应该是「世界已经停转」的警报，不是「怎么修」的处方。**
它的 hint 应该说清这一点，或者干脆把处方交给别的诊断。
