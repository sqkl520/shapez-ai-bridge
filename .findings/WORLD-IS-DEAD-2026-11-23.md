# 这个世界已经不产出了 —— 所有 prompt 层的努力都建在一条死链上

2026-11-23。全部数字来自 `research/ai-plan/runs/` 里 567 个已保存的快照，
只读，没有碰游戏。

---

## 一句话

**从 2026-11-16 起，实验存档里的工厂一件货都不产了。**
不是"产出很少"，是 `produced_total = {}` —— 整张图 60 秒零产出。

而 `hips_belts` 上还有 365 件货、18 个机器输出口**全部**满着（`progress = 1`）。
这是**满载冻结**：原料进不来，成品出不去，整条链焊死。

## 二、不是"没载入"，是"载入了但不转"

那个最容易被误读的形态，这次专门排除了：

```
567 个快照中，91.0%（516 个）同时满足：
  · produced_total = {}          （零产出）
  · items.belts 非空             （货带子在，世界是载入的）
```

也就是说：**带子上躺着货，但没有任何一台机器在动。**

## 三、死法：满载冻结，不是断路

`r-20261123151728-52a3` 这一轮的 `items-last.json`：

```
18 个 machine ejector，progress >= 1 的有 18 个（100%）
```

ejector 的 `progress = 1` 意思是**机器已经做好了下一件，但吐不出去**。
全部 18 个都这样，而它们要吐的东西是：

```
----SuSu ×1   SuSu---- ×1   red ×3   blue ×7
RuRuRuRu ×1   green ×3      CuCuCuCu ×1   CuCu---- ×1
```

上游 17 台矿机脚下都是矿（red / blue / green / RuRuRuRu / CuCuCuCu），
但它们的输出口全满 —— 因为下游的带子也全满 —— 因为再下游的加工机器也全满。

**这是一条从 hub 一路堵到矿机的反向淤积。**

跨全部 566 个含 ejector 的快照：

```
全部输出口堵死：443 个（78.3%）
部分堵死：      123 个
每个快照的堵塞比例中位数：1.00（= 100% 堵死）
```

## 四、为什么这推翻了此前所有结论

`## LEFTOVER LINES`、`PROGRESS` 读数、`feed_sources`、`role@dir`、`cheapest`、
`belts_dead_dangling`、`WRONG_SHAPE_PRODUCED` —— 这一整轮工作都在假设
**"模型选对了动作，世界就会往前走"**。

而在一个 100% 满载冻结的工厂里：

- 接一根新带子进去 → 它立刻也被堵满，`produced_total` 仍然是 `{}`
- 拆掉一条残线 → 腾出一点空间，但 hub 入口那边不通，货还是不走
- 诊断说 `MACHINE_STARVED`（缺料）→ 实际上**不缺料，是堵料**

`MACHINE_STARVED` 报的是 `slotsOf` 里没有带子接着的输入槽。
而在满载冻结的世界里，**真正缺的不是"接上"，是"通开"** —— 这是两个方向相反的动作。

## 六、这对"300 轮"算术意味着什么

`.findings/GOAL-IS-OUT-OF-BUDGET.md` 算的是：单台 stacker 12 机器秒/件
⇒ 1000 件需 300 个满额轮次。

那个算术**本身没错**，但它假设链条是通的。现在链条是焊死的：

```
每轮推进 40 游戏秒 × 300 轮 = 12000 游戏秒 = 3.3 小时
而实测每秒只推进 1.05~1.61 游戏秒（见 §七）
⇒ 300 轮实际需要 2~3 小时的真实游戏时间，而每轮之间还隔着 LLM 的往返
```

## 七、顺带修正一个一直读错的单位

`obs.tick` 来自 `root.time.now()`，而 `game_time.js:152` 的 `now()` 返回的是
**`this.timeSeconds`** —— 是**游戏秒**，不是 tick。

实测（359 个 tx 成功的 run，第 1 轮 observe → 第 2 轮 observe）：

```
间隔中位数 37.0 游戏秒
```

而 `step(2400)` 在 60 tick/s 下 = **40 游戏秒**。两者对得上 ——
**步进是真的在跑，预算算术没有错**。

不带 tx 的 186 个 run 中位数只有 17.9 秒，正是「没落地就不推进」的设计。

⇒ 之前 `.findings/GOAL-IS-OUT-OF-BUDGET.md` 里「只推进 26 tick」那句话是把
游戏秒当成了 tick 读。26 游戏秒 ≈ 1560 tick，不是 26 tick。结论不变，单位要改。

## 八、这不是存档坏了 —— 是 L12 这一关独有的

按关卡分组（同一批 567 个快照）：

```

level  9   snapshots  58   silent  16  ( 28%)   ← 正常（四分之一的窗口只是恰好没产出）
level 12   snapshots 508   silent 500  ( 98%)   ← 异常
```

同一个存档、同一个桥、同一套代码：**L9 上工厂是活的，L12 上是死的。**

而且 L9 时代造得出东西（`Cu----Cu` / `CuCu----` / `CrCrCrCr` / `RbRb----`），
L12 从进关起就没造出过任何一件本关目标。

⇒ 这不是"存档文件损坏"或"桥读错了"，是**这一关的世界在结构上已经堵死**。

## 九、一个反证：满载 ≠ 死亡

不能简单说"输出口全堵就是死了"：

```
50 个还在产出的快照里，30 个（60%）也是 18 个出口全堵
413 个沉默快照同样全堵
```

满载是这套工厂的**常态**，不是死因。

真正的区分是：**产出窗口是空的**。即使在满载状态下，只要链条里
**任何一段**还在动，`produced_total` 就会有键。

⇒ 判据必须是「产出为零」，不是「出口堵满」。写代码时要按前者。

---

## 十、结论

**在把这个世界从满载冻结里解开之前，任何提示词改动都无法被证伪，也无法被证实。**

模型修的方向对不对、`LEFTOVER LINES` 它读不读、`PROGRESS` 它理不理 ——
这些问题的答案全部被一个更基础的事实盖住了：**世界不转，所以什么都不会发生。**

更糟的是，现有诊断会**主动误导**：

- `MACHINE_STARVED` 说「这台机器缺料，接上它」→ 实际上不缺料，是下游堵死
- `NO_PRODUCTION` 说「没有产线在造目标」→ 模型于是去**新建**，
  在一个已经 100% 堵死的世界里再铺一条线，只会让它更堵
- `feed_sources` 推荐"从 C4 接它的缺料口"→ 接上去之后那件货也出不来

**正确的第一条动作是"通开"，不是"接上"。** 而这三个字从来没有出现在 prompt 里。

⇒ 下一步：把「世界产出为零 + N 个出口全堵」这个事实做成一条诊断，
并给出**能解堵的句柄**（堵在出口的机器、它下游的带子）。
这是在继续调 prompt 之前唯一值得做的事。
