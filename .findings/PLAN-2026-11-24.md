## 一、一句话：真正的问题是什么

**真正的问题不是「某条诊断写错了」，而是三件地基性的事：
① 世界被改的方式（游戏按邻居重算带子方向）没有被代码约束，只被事后报告；
② 没有任何机制能证明「算出来的东西真的到了模型眼前」；
③ 真机上跑的不是仓库里的代码。**

其中 ①，本轮找到了一个**有对照组、可证伪、且还没人修**的机制：
`opTx` 的 immutable 保护**只覆盖第一条 op** —— 因为 `performImmutableOperation` 是同步的，
而 tx 的执行体是 `async`，第一个 `await` 一挂起，标志就在 `finally` 里被复位。
事故那次 `ops = [delete, place(trash)]`：delete 被保护，place 没有 —— 于是邻居带子被重算。

`FIX-NEIGHBOR-RECOMPUTE` 的 agent 独立读源码得出了同一个机制，但**明确选择只做可见化、不修根因**
（它写：「这个泄漏应当单独立项修」）。本计划把这个「单独立项」立起来。

### T3｜根因：让 immutable 覆盖**每一条** op（改 mod）

- **角色**：mod 修复（本计划唯一允许改 `src/mod/` 的任务）
- **唯一问题（可证伪）**：`opTx` 里 `runGuarded(root, async () => { for (… await this.performAction(op)) })`
  **是否只保护第一条 op**？若是，把每条 op 各自包进同步 immutable 之后，
  「delete 后 place 挨着带子」这个组合**是否不再产生 `diff.modified`**？
- **判据**：
  1. **先证伪/证实机制**，不靠读注释：写一个离线 harness（`.tmp-T3/guard-sim.mjs`），用**同一段代码形状**
     复刻 `performImmutableOperation = (fn) => {flag=true; try{fn()}finally{flag=false}}` 与
     `async () => { for (…) await syncOp() }`，断言「第一条 op 期间 flag=true，第二条起 flag=false」。
     这段 harness 必须能**在旧形状下失败**（把它作为变异验证）。**注意**：这是仿真，不能替代真机证据；
     真机证据在 T7。

     不许改 `runGuarded` 的语义（它被 `paste_blueprint` 共用），不许改 `opPlace`/`opDelete`。
     **必须**在 `opTx` 返回里加一个可观测字段 `immutable_coverage: {ops, covered}`，让真机能读回。
  3. `rollbackToSnapshot` 也走 `entityAdded`，同样只在 immutable 外 —— 检查它是否也受影响，
     若受影响**只报告不修**（回滚这条链是 T7 的验证对象，改动面太大）。
