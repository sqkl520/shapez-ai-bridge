# 这一关在当前预算下到底能不能完成

2026-11-21。这是一个**算术问题**，不是提示词问题。

## 结论

**单台 stacker、每轮 40 游戏秒的推进量，这条目标需要约 300 个「推进满额」的轮次。**
而实测这个 run 只推进了 26 tick、tx_count = 0。

这不是"模型还不够聪明"，是**预算与目标的量级差了几十倍**。

## 一、单件成品的机器时间

按验证 agent 给的配方（我用 `shape-ops.mjs` 复核过代数部分）：

| 工序 | 次数 | 速率 | 机器秒/件 |
|---|---|---|---|
| cutter | 5 | 0.500/s | 10.00 |
| rotater | 2 | 2.000/s | 1.00 |
| **stacker** | **3** | **0.250/s** | **12.00** ← 最窄 |
| painter | 2 | 0.333/s | 6.00 |
| mixer（白 = 2 台串联） | 2 | 0.400/s | 5.00 |

串联链的最窄段决定产能：**stacker 12 机器秒/件**。
1000 件 ⇒ 单台 **200 分钟 = 3.3 小时**纯 stacker 时间。

这是**并联**能改善的部分（加工机器没有并联上限），但每多一台性价比递减，
而且要多铺一条进料线 —— 在已经 699 条带子的世界里，那条线本身就要穿过拥堵。

## 二、agent 每轮能推进多少游戏时间

`loop.mjs` 里游戏时间**只在 tx 成功落盘之后才推进**，且每轮最多一次：

```js
// loop.mjs:4912 —— 在 ⑥ verify 里，apply 成功之后
behavior: mode === "live"
    ? { ticks: Math.min(2400, Math.max(0, budget.TICKS_MAX - st.ticks)) }
```

- 上限是 **2400 tick**，不是 `TICKS_MAX` 的 24000
- 2400 tick / 60 tick/s = **40 游戏秒**
- tx 失败 / plan 被拒 / dry_run ⇒ **一秒都不推进**

实测 `r-20261121100232-d10f`：`tx_count = 0`，两次 observe 之间只差 **26 tick**（那是不受控的实时流逝）。

## 三、除法

```
1000 件 × 12 机器秒/件 = 12000 机器秒
÷ 40 游戏秒/轮        = 300 个「推进满额」的轮次
```

而且这 300 轮还得**每一轮都 tx 成功**。这个 run 是 **0/2**。

## 四、这意味着什么

**继续优化「模型选不选对」是次线性收益。** 即使把落地率从 10% 提到 50%，
300 轮 × 50% 仍然是 600 轮的需求量 —— 而一次会话能给的轮次在个位数。

不是提示词不够好。是**这个目标与这套预算不在同一个量级上**。

## 五、可选项（按代价排序）

**① 提高每轮推进量（最便宜）。**
`Math.min(2400, …)` 改成 20000（mod 的 `MAX_STEP_TICKS` 上限，已核实：
`shapez-ai-bridge.js:78` `MAX_STEP_TICKS = 20000`，`:4092` 校验 `[1, 20000]`）——
单轮推进量 ×8.3，300 轮变 36 轮。

**② `fast_forward` 这条路是死的（已核实，不要再试）。**
`shapez-ai-bridge.js:4046-4070` 有完整记录：1.5.6 的发布包里
`globalConfig.fastForwardSpeed` **从未被定义**，`getTimeMultiplier()` 返回 `undefined`，
`budget += deltaMs * multiplier` 把逻辑时钟污染成 NaN，
之后 `while (budget >= deltaMs)` 永远为假 —— **整个游戏时钟永久停摆**，
切回 regular 也救不回来。mod 现在会在应用前先验乘数，不合法直接拒。
所以「快进」只能靠 `step`，上限就是 ① 里那个 20000。

**③ 并联 stacker。**
加工机器无并联上限。4 台 ⇒ 12 秒/件变 3 秒/件，300 轮变 75 轮。
但要新增进料线，而现有世界已经 699 条带子、532 条通到 hub。

**④ 接受它需要多轮。**
用户之前明确说过「能看『完成这条需要 N 轮』的进度感感觉没有必要」，
所以**不做进度条**。但「这一关一个 run 物理上做不完」是个**约束事实**，
不是进度感 —— 它该进 prompt 的理由是让模型别在「这轮就要做完」上打转，
而不是给用户看进度。这两件事要分开。

## 六、我没有做的那件事

没有去改 `Math.min(2400, …)`。那会让每轮的世界变化量变成 8 倍，
而**当前落地率是 10%**（`replay-plan.mjs` 实测 30 个样本里只有 3 个能落地）。
一次坏的计划被 8 倍放大，比现在危险得多。

先确认落地率，再放开推进量。顺序不能反。
