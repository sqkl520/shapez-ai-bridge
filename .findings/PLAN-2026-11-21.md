# 长期计划（2026-11-21 起）

## 这份计划的根据：一组不撒谎的数字

最近 12 个 run 的结局：

```
halt BUDGET_ROUNDS  rounds=2  tx=1  delta=0
halt BUDGET_ROUNDS  rounds=2  tx=0  delta=0
halt BUDGET_ROUNDS  rounds=2  tx=0  delta=0
halt BUDGET_ROUNDS  rounds=2  tx=1  delta=0
halt BUDGET_ROUNDS  rounds=2  tx=2  delta=0
halt DRY_RUN        rounds=1  tx=0  delta=0   ×7
```

**12 个 run，`goal_delta` 全是 0。**

而今天做的所有修复（`feed_sources`、`role@dir`、`cheapest`、纯闭环、
`WRONG_SHAPE_PRODUCED`、L4 窗口、`OUTPUT_STRANDED`）——
**每一个都让模型单轮表现变好，但没有一个改变了 `delta=0` 这件事**。

这说明：**单轮质量不是当前的瓶颈。**

三个已量化的事实：

1. **一个 run 只跑 2 轮就 `BUDGET_ROUNDS` 停**（`ROUNDS_MAX = 3`，实测用不满）
2. **一关需要约 300 个「满额推进」的轮次**（单台 stacker 3.3 小时，
   每轮最多推进 2400 tick = 40 游戏秒）—— `.findings/GOAL-IS-OUT-OF-BUDGET.md`
3. **落地率刚刚从 0/10 提到 10/10**（`feed_sources` + `role@dir`，n=10，p=0.000），
   但那是在**离线快照**上，真机只跑过 1 次（`r-20261121190439-6190`，
   tx 成功、产出 9 件——但是上一关的形状）

⇒ **2 轮 vs 300 轮，差 150 倍。** 在此之前优化任何单轮指标都是噪声。

## 计划的四条主线，按性价比排

### 主线 A：让「一轮有用」变成「一轮可累积」（最高优先）

**问题**：每轮都从零开始看世界，做完一个动作就结束。300 轮需要的是
「记住自己做到第几步」，而不是「每轮重新推理一遍」。

**要做的**：

A1. **跨轮进度台账**（已有 `attempts.json` 的骨架，但只记「试过什么」，
    不记「做到哪一步」）。加一个 `worlds[worldKey].plan`：
    `{goal, steps_done:[...], steps_todo:[...], last_good_state}`。
    每轮 prompt 带一句「你已经做到第 N 步，下一步是 X」。

A2. **验证台账在真机上真的能跨轮**。现在 `runLog` / `stickyGoal` 存在，
    但真机上没见过它们起作用（12 个 run 全是 2 轮）。

**验收**：连续 5 个 run，第 2 个 run 的 prompt 里出现第 1 个 run 的进度。

### 主线 B：把「300 轮」压到可完成的量级（第二优先）

**问题**：单台 stacker 0.25/s，一个 run 只推进 40 游戏秒。

**要做的**（按顺序，每步都要先量代价）：

B1. **提高每轮推进量**：`Math.min(2400, …)` → 更大。
    上限是 mod 的 `MAX_STEP_TICKS = 20000`。2400 → 20000 是 8.3 倍，
    300 轮变 36 轮。
    ⚠️ **前置条件**：落地率必须先在真机上验证。现在真机只跑通过 1 次。
    坏计划被放大 8 倍比现在危险。

B2. **并联 stacker**：加工机器无并联上限。4 台 ⇒ 3 秒/件，300 轮变 75 轮。
    但要新增进料线，而世界已经 699 条带子。

B3. **确认 fast_forward 确实不可用**（已查过一次：1.5.6 没有
    `globalConfig.fastForwardSpeed`，会让时钟变 NaN 永久停摆）。
    这条路死了，不要再试。

### 主线 C：真机验证闭环（与 A/B 并行）

**问题**：今天所有结论都来自离线快照。真机只跑过 1 次。

**要做的**：

C1. **把真机 loop 跑成常规范式**。现在跑一次要手工拼命令行，
    而且踩过 `ANTHROPIC_BASE_URL` 被占用的坑。做成 `tools/live-run.sh`：
    显式参数、自动备份、自动回滚。

C2. **建一个「真机回归」**：固定目标形状 + 固定轮数，跑完比对
    `delivered` / `produced_total`。现在判断「改得好不好」完全靠人读 transcript。

C3. **把离线验证与真机验证的差距做成常驻监控**。今天已经踩过一次：
    离线 A/B 说 10/10 落地，真机跑出来产出的是错误形状（颜色不对）。
    离线看不见「颜色对不对」这个维度。

### 主线 D：清掉结构性欠账（随时可做，不阻塞主线）

D1. **诊断码三处登记的自动校验**。新码要登记 `DIAG_CODES` / `RETRIEVAL_TABLE` /
    `RANK` 三处，缺一处静默失效。今天第四次踩（`OUTPUT_STRANDED`）。
    做成测试：某码在 `DIAG_CODES` 但不在 `RANK` ⇒ 红。
    ⚠️ 但现在 76 个码里 45 个不在 RANK，多数是 LLM/TX 层的码（本身不参与跨层排序）。
    所以校验要先区分「会进 diagnose() 输出的码」和「只在 loop 内部流转的码」。

D2. **`DIAGNOSE_CODES`（loop.mjs:147）是死码**——只声明、从没被引用。
    要么删掉，要么让它成为真正的校验源。

D3. **`findObsoleteLines` 只在换关那轮报**。真机证明那个前提不成立：
    没换关也会在造错的东西（`WRONG_SHAPE_PRODUCED` 已补上这个缺口，
    但残线拆除的授权链还是断的）。

## 风险

**最大的风险是我把主线 A 做成了「又一个 prompt 字段」。**

今天一整天的教训是：加字段 ≠ 加能力。`feed_sources` 加了但推荐错颜色、
`cheapest` 加了但被早收敛架空、`WRONG_SHAPE_PRODUCED` 加了但忘了登记 RANK。
每一次都是「我以为做完了，真机一跑发现没生效」。

所以主线 A 的每一步都必须先问：**这个台账字段，真机上怎么证明它起作用了？**
答不上来就先别写。
