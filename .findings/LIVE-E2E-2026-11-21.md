## 6. 但产出的是 L11 的形状，不是 L12 的目标

`produced_total` 的三个码全部落在同一条链上：

```
green + ----CuCu  →  painter 喷漆  →  ----CgCg  (4)
                    + ScSc----     →  ScScCgCg  (9)
                    rotater(CW)    →  CgScScCg  (9)  ← L11 的目标形状
```

`.findings/SHAPE-verdict.md:161` 已经实证：`CgScScCg` **正是第 11 关的目标形状**
（`levels.js:242`），hub 里躺着 2071 件（上一关已达成）。

### 根因：`feed_sources` 只保证「能喂颜料」，不保证「喂对颜色」

目标 `CbCbCbRb:CwCwCwCw` 的第三/四象限是 `CwCwCwCw`，需要 **white**。
而 white 在这张图上**没有矿**（实测 47 种矿，无 `white`）；recipe 给出的路径是
`blue+green→cyan`、`cyan+red→white`，即**必须走 mixer 级联**。

`feed_sources` 的实现（`semantic.mjs:3647-3653`）用的是：

```js
const wantsColor = /color/i.test(missRole);
// ...
const producesPigment = (e.type === "mixer" || e.type === "painter" || … )
    || (e.type === "miner" && isPigmentOre(minerOre(e)));
```

**它判的是「这台机器产不产颜料」，不是「产的颜色对不对」。**
于是踩绿矿的 `M13` 与踩蓝矿的机器在这个判据下完全等价 ——
它推荐 M13，模型选了 M13，货通了，颜色错了。

**这不是模型的错，也不是 role@dir 的错。** 缺的那一维是
「目标需要什么颜色」→「哪台源头产这个颜色」。

### 顺带发现的既有缺陷（与本次修复无关，但同一坑）

`MACHINE_STARVED` 的诊断文本里，整份 prompt **一次都没提到需要什么颜色**：
第 1 轮的诊断渲染里 `green` / `white` / `Cw` / `color` 出现次数**全是 0**。
模型只能看到「C3 缺 color 槽」，看不到「缺的是白色」。它选了最近的绿矿，完全合理。

### 另一条真缺陷：C2 的右输出是死路，堵死了它的左输出

`C2`（cutter#13544）有两个输出槽，但**右输出格的下一格 `(-6,10)` 是空地**：

```
C2 cutter @(-5,9) r=180
  out left @bottom cell=(-5,10) -> belt 14835   ✔ 有去处
  out right@bottom cell=(-6,10) -> EMPTY        ✘ 死路
```

cutter 每切一刀产出两半，一半走左、一半永远出不去 ⇒ **cutter 两个槽位迟早都堵死**。
实测 `ejectors` 一直是 `----CuCu@progress=1 + CuCu----@progress=1`（两个都卡在 1），
在最近 **10 个历史 run 里全部如此** —— 这是**先于本轮就存在的结构缺陷**，
不是这次 tx 造成的（本轮 tx 只碰 x∈[-9,-3] 的 29 格，没碰 x=-5 那条线）。

后果：**L12 那条 C2→C3 的 shape 供料线本身就已经是死的**。
本轮把绿色颜料接进去之后，painter 只吃到那一半 `CuCu----`，另一半永远等不到。
所以接完 color 之后只出了一小批（9 件），然后就**自己停了** ——
不是回滚导致的，是 C2 的堵死把上游又掐住了。

```
回滚后 90 秒，连采 3 次：
  C2 in=2  outL=0  C3.shape=0  C3.color=0   ejector=CuCu----@1（纹丝不动）
```

**这条线现在需要两处修：C2 右输出的死路 + painter 需要的白颜料。**
只接颜色不够 —— 模型下一轮如果只做 color，仍然会卡在 C2。

## 7. 两处指标失真（值得单独记）

### 7.1 `belts_dead` 把「喂机器」当成「死」

新铺 29 条带子终点是机器，按定义到不了 hub。指标 +23 里 29 条全是这个。
`health.mjs:381` 有一条「新铺的带子还没接完 ≠ 破坏」的豁免，条件是
`dead.delta < belts.delta`；本轮 23 < 23 **为假**（因为它删了 6 条、加了 29 条），
于是判 regressive。**结论碰巧对（确实没达成目标），理由不对（不是「改坏了」）。**

### 7.2 `flowReachable` 与 `accepts` 判据不一致 —— 真 bug，但**影响量我之前算错了**

`flowReachable` 建边用 `at()`（footprint 索引）；`accepts()` 对「槽位本体格在
footprint 外」有 `viaSlotBody` 兜底，`at()` 没有。而 2×1 机器旋转 90°/270° 后，
`slotsOf` 的 slot 本体格会**落到 footprint 之外**（`footprintCells` 不旋转，
只把 `assumed` 置 true，没有修正）。

> **纠错**：我第一版写「修了能多救 81 条、`belts_deliverable` 偏低 81」—— **错了**。
> 那个 81 是 `sourceless`（cycle 剔除）开关造成的，我把它和 `viaSlotBody` 混在一次模拟里了。
> 分开测的结果：
>
> ```
> 默认 (sourceless:true) : reaching=309  dead=390
> sourceless:false       : reaching=390  dead=309   ← 差的 81 条是这个开关
> ```
>
> 而**真正受 viaSlotBody 影响的带子，全图只有 1 条**：`17586`（出口 `(30,-50)` 是
> mixer 17319 的槽本体格）。它所属的 mixer 本身不在 reach 里，所以**修了之后 dead 计数不变**。

所以：**这是一个判据不一致的真缺陷，但它不改变当前的 `belts_deliverable=309`。**
保留这一条是因为 `connect` 与预演闸门都依赖同一份几何；一旦哪条链真的走到这个位置，
`flowReachable` 会漏边。但**它不是你在这份世界上看到的任何数字的原因**，别拿它当解释。
历史注释（`topology.mjs:205`）记的「painter r=270 的 color 槽不在 footprint 里，
81 件货堆在那里进不去」是**另一个实例**（L10 的 `B13243`），与这里的量级不可混用。

## 9. 结论

### 修复有效

1. **`feed_sources`**：模型 1/1 选中第 1 名推荐源，`M13(27格, 安全)`。
2. **`role@dir`**：`to.port` 写 `"color"`，**没有**再出现把方位当端口名的错。
3. **纯闭环闸门**：390→309 与离线一致。
4. **整条链通了**：从矿机到 hub，`produced_total` 从 `{}` 变成 9 件真交付，
   hub 入库 +9。**painter 冻死这个 L12 死结在本轮被真机证实可以解开。**

**任务书要问的「修复后的 prompt 能不能驱动出真实产出」—— 答案是能。**
tx 落地约 1 秒后货就开始淌，run 结束后累计交付 9 件。

### 但产出不对，而且线上还有两处更硬的阻塞

产的是 `CgScScCg`（L11 遗留），不是 `CbCbCbRb:CwCwCwCw`。三处缺口，按硬度排：

1. **`feed_sources` 只保证「能喂颜料」，不保证「喂对颜色」**。
   L12 需要 white，图上无白矿，只能 mixer 级联出白色。
   推荐了绿矿 ⇒ 货通了、颜色错了。
2. **C2 右输出是死路**（`(-6,10)` 空地），cutter 迟早堵死，shape 供料线本身已死。
   这是**先于本轮就存在的**结构缺陷（最近 10 个 run 全部如此）。
3. **L4 的 60 秒窗口测晚了**：run 自己判「没产出」，实测 9 件全在窗口后。
   后续读 verify 记录的人会误判修法无效。

### 建议（按性价比）

1. **`feed_sources` 加颜色匹配**：`wantsColor` 时，从 goal 形状解出所需色码
   （`CwCwCwCw` ⇒ white），只推荐产该色的源头；white 无矿 ⇒ 直接推 **mixer** 而不是矿机。
   L12 的正确答案是「先修 mixer 级联」，不是「拉一根最近的颜色线」。
2. **诊断要说出缺什么颜色**。现在 `MACHINE_STARVED` 的渲染里颜色信息出现 0 次。
   一行「C3 的 color 槽需要 white（地图无白矿，须 mixer 合成）」就能让模型不去拉绿矿。
3. **`L4` 的观测窗口要按链条延迟放宽**，或改成「观测到第一次产出为止，最多等 N 分钟」。
   60 秒对 painter→stacker→rotater 三层链太短，会把「慢但在跑」判成「没跑」。
4. **C2 右输出的死路要进诊断**。现在没有任何一条诊断说「这台 cutter 有一半产物没有去处」。
5. **修 `flowReachable` 的建边**：`at()` 加 `viaSlotBody` 兜底（与 `accepts` 同判据）。
   注意：**它不改变当前的 309**（实测只影响 1 条、且那条的机器本身不可达），
   属于「判据一致性」修复，不要指望它能改善分数。
4. **`belts_dead` 不该把「喂机器的新带子」算成退化**。豁免条件要从
   `dead.delta < belts.delta` 放宽到「新增带子有多少条能让某个槽 `inputFed` 变 true」。
