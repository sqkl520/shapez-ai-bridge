## 先说三个会改变排序的实测

三条都**不在**候选清单里，但都会改变 R1–R5 的结论。

### ① 修好这条死锁链，产出的也不是目标形状

`.findings/CONCLUSION.md` 把 painter#13552 缺色定为**唯一断点**。这个事实对，
但没人问过下一句：**这条链通了以后产出什么？** 逐格追出来的两路进料是：

```
stacker#14684 上路 (-1,6) = ScSc----       ← path8 顶上来的（星形半片）
stacker#14684 下路 (-2,6) = ----CuCu       ← painter#13552 的 shape 来料（铜圆半片）
painter 把它喷蓝            → ----CbCb
stacker 叠起来              → ScSc----:----CbCb
L12 目标                    → CbCbCbRb:CwCwCwCw     ✗ 不一致
```

全图 376 件在流货物的成分（按目标需要的 `Cb / Rb / Cw` 逐格比对）：

| 货物 | 件数 | 目标需要吗 |
|---|---|---|
| `blue`（颜料） | 217 | ★ 需要（目标色 b） |
| `ScSc----` | 139 | ✗ |
| `CuCuCuCu` | 13 | ✗ |
| `----CuCu` | 8 | ✗ |
| `green` / `red` | 15 | ✗ |
| `SuSu----` / `CuCu----` / `RuRuRuRu` / `----SuSu` | 4 | ✗ |

**含 `Cb` / `Rb` / `Cw` 的货物件数 = 0。** 那 217 件蓝颜料是唯一相关的材料，
而它们物理上出不来：87 件在 `path20`（55 格，`boundAcceptor: null`，末端悬空在 `(37,-40)`），
120 件压在 `path8` 的 `ScSc----` 后面。

⇒ **R1/R2/R3 无论多准确，解开的是一条通向错误形状的链。** 这是本评估最重要的结论。

### ② 模型在 L12 那一次 run 里选得不算离谱，是**动不了手**

## 逐条评估

### R1：让 `MACHINE_STARVED` 指明哪一台是根

**⚠️ 已在评估期间由另一个 agent 落地（`24ce607`）。以下是落地后的实测，不当作待办。**

- **能解决多少：修掉一个真实错误，但推进 L12 = 0。**
  旧 hint 同时说两句互相矛盾的话（「最典型的是 painter」+「先修最下游那一台」），
  而在这台世界上 painter 恰恰是**上游**。这是**主动误导**，必须改。
  但改完仍然：成因排第 6（R0 未修）、解开的链产出 `ScSc----:----CbCb`（问题①）。
- **代价**：已沉没，88 行 + 1 条测试。回归风险低（`semantic.test.mjs` 62 pass / 2 fail，
  与基线一致；两条 fail 在 T7 / 一条 shape 断言，与本次改动无关）。
- **可验证性：这是本路线最弱的一环。**
  只能证明「`subject` 从 C4 变回 C3」「hint 里出现『根』字」——
  这属于 `when-line-no-effect` / `model-was-right-i-was-wrong` 记过的那类**选择侧指标**。
  不能证明「世界更接近目标」。
- **依赖**：无。但与 R0 同做才有意义 —— 排在末位的正确答案，模型读不到。

### R2：把死锁链完整画进 prompt

- **能解决多少：几乎为零，且原因不止一个。**
  (a) **被 180 字符闸门结构性挡死。** `prompt.mjs:2476`
  只给 `HUB_FED_BY_COLOR` / `HUB_INLET_THIN` 放 400，其余一律 180。
  实测一条 262 字符的 R2 文案，180 截断后**恰好把可执行的那半句切掉**：

  ```
  到达：… → 上游 259 件货塞满 165 格带 → 19 个 ejector 卡死 → 整图零产出。**
  丢弃：**先修 painter#13552 的 color 槽**：`connect {from:…, to:{ref:"C3",port:"color"}}`。
  ```

  即「模型看懂了病因，却动不了手」—— 和 `HUB_FED_BY_COLOR` 当初一模一样的病。
  (b) **预算饱和。** 实测 `system 4725 + user 11329 = 16054`，`targetChars = 4600×3.5 = 16100`
  ⇒ **余量 46 字符**。探针实测（把 hint 放宽到 400）：
  `belts_shown 6 → 5`，`trimmed_belts 10 → 11`。**每一句链文案都从带子表里抢名额**，
  而带子表正好是模型唯一能就地改造的东西。
  (c) 画的链通往错误形状（问题①）。
- **代价**：中等。要动 `prompt.mjs`（wide 白名单）+ `semantic.mjs`（文案），
  且必须绕开 180 闸门（挪进 `observed` 或加白名单）。回归风险**高**：
  `prompt_diag_hint.test.mjs` 有两条测试专门钉「其它诊断仍截 180」，改白名单会当场打红；
  且 prompt 已饱和，任何加长都会改变 `belts_shown`，而 `prompt_belt_visibility.test.mjs`
  的回归 E 对带子可见性是硬断言。
- **可验证性**：能验证「文案到达模型」（渲染后 grep），但不能验证「模型因此更接近目标」。
  交付本身可断言，效果不可断言。
- **依赖**：必须先修 R0（否则它排第 6，链画给谁都白画）+ 必须先解决 180 闸门。

### R3：新增「世界冻结」诊断

- **能解决多少：能新增一个客观信号，但它比 MACHINE_STARVED 更宏观、更不可执行。**
  数据完全可得且没人用过：`items.ejectors` 19 条，**19/19 `progress = 1`**（实测）。
  `grep -rn "\.ejectors" src/agent/loop/*.mjs` **零命中** —— 这条数据一次都没进过任何判据，
  属实是空白。但「整座工厂已死锁」是**症状的汇总**，而 MACHINE_STARVED 已经说了**成因**。
  在诊断表**恰好满 8 条、0 条被压掉**（实测）的情况下，加一条高排位码 = 挤掉一条。
- **代价**：中高。新 semantic 块 + 新 `RANK` 条目 + 阈值（`N%` 取多少？在只有 1 个样本的
  世界上调阈值正是本项目反复吃亏的地方）+ 正负例测试。回归风险中。
- **可验证性：本清单里最强。** `19/19 progress=1` 是布尔事实，
  可以拿 `r-20261121072433-521e` 的 `items-last.json` 做**离线夹具**逐项断言，
  不需要 LLM、不需要真机。这是 R1–R5 里唯一能写出「客观、可复现、不依赖模型」验收的路线。
- **依赖**：无技术上依赖，但**业务上必须在 R0 之后** —— 否则两条宏观信号抢同一个 slot。

### R4：改动作粒度（宏观动作而非宏调用）

- **能解决多少：前提已被自家实验证伪一半，全量版解不了问题①。**
  便宜的那一半**已经做过了**：`3ad63d4` 的 `--force-one-call` 把每轮宏数从 3.45 压到 1.00，
  成因选中率 0% → 20%，**Fisher 单尾 p = 0.106，未达显著**。也就是说
  「逼模型只做一个动作」这个**弱版本已经测过，不够**。
  强版本（新的动作抽象，如「接通这条链」）代价极大：新宏 + 契约条目 + `planToTxOps` 分支 +
  验证器 + `MACRO_NAMES` 白名单，且 `build_line` 被明确拒绝（`constants.mjs:700-704`：
  前置条件是 site-not-empty，本世界 749 实体必然拒）。
  更关键：世界差异的瓶颈**不在动作粒度**。问题①说解开的链产出错形状，
  问题②说单 run 执行率才是短板 —— 宏观动作既不能改形状，也不改连接被占的现实。
- **代价：本清单最高。** 属于「新能力」而非「修缺陷」，且要动的都是硬契约。
- **可验证性**：可以测（复用 `exp-force-one.mjs` 的分类器），但**该分类器已经修过一次**
  （第一版 `/stacker|painter/` 太松，把 50% vs 88% 的假结论报出来；收紧后 0% vs 20%）。
  再放松口径就会重犯。
- **依赖**：R1 + R2 + R3 全部做完才轮得到它，而且做完仍不解决形状问题。

### R5：接受现状

- **能解决多少：把它当「方向」是错的，但当「判据」是对的。**
  算术上 L12 **不可能在一次 run 内突破**：

  ```
  stacker 速率 = belt 2 × processors(0 级 ⇒ 1.0) × 1/8 = 0.25 件/s
  1000 件需要 4000 游戏秒 = 66.7 分钟
  TICKS_MAX = 24000 tick ÷ 60 tick/s = 400 游戏秒
  ⇒ 一次完美 run 理论最多交付 100 件，需 ≥10 次完美 run
  ```

  再叠加 6 条叠加原因里**有 5 条不在 agent 的 6 个宏的动作词汇内**
  （② 218 件颜料进不了 `filter:"shape"` 的 hub；③ 从未造出过任何 2 层形状；
  ④ 主带已压到 98.9%/99.7% 容量；⑥ 载货带都不通 hub）。
- **代价**：零代码。机会成本是「本来能拿去修 R0」。
- **可验证性**：不需要 —— 这正是问题。
- **依赖**：无。
- **它错在哪**：`63% 的 run 有 apply`、`单 run 最多 5 次 apply` 说明 agent **并非无用**；
  放弃等于把「跨 run 复利」这条路一起放弃（`memory.mjs` 的跨 run 记忆已经落地，
  `worldUpdate` / `attemptsForGoal` 都在）。不该放弃，该**换判据**。

## 如果只能做一条

**做 R0：在 `src/agent/loop.mjs` 的跨层 `RANK` 表里加一行 `MACHINE_STARVED: 3`。**

理由（按强度排序）：

1. **它是唯一「零成本 + 确定生效」的改动。** 一行表项，0 字符预算
   （实测 `16054 / 16100`，一个字都不能加）、0 新逻辑、0 新测试夹具。
   生效可当场验证：渲染后成因从第 6 行变到第 1 行。
2. **它修的是本项目第三次犯的同一个错。** 该文件自己在 `:1247-1263` 和 `:1273-1285`
   两次记录了「忘了登记跨层表 ⇒ 整批消失」，并明确写了「这条注释是防止下一个人再走一遍」。
   `MACHINE_STARVED` 是第三次。
3. **它让 R1/R2/R3 从「做了也白做」变成「值得做」。** R1 已经把 hint 改对了
   （「从 painter#13552 开始…是这条链的根」），但那句话躺在**第 6 行**——
   而真机证据是模型只读到第 1–3 行就选了。**排序是让内容生效的前提。**

**但必须把话说清楚**：R0 + R1 合起来也**不能**让 L12 推进，因为
问题①（链产出错形状）和问题②（执行率）都还在。它们唯一的作用是把
「模型没看到成因」这一项从失败原因里**排除掉**，让下一步能测真正的东西。

**真正该做的第二件事（不在这 5 条里）**：把成功判据从
「`delivered` 涨了」换成「**目标可用**的材料/带子数涨了」——
即 `CONCLUSION.md` §「如果要改，改什么」提的那条三判据度量。
理由：`delivered` 在一次 run 内结构性为 0（≤100/1000），拿它当判据，
R1–R5 的**任何**改进都会被读成「无效」。本项目已有 `one-belt-drop-ate-the-memory`
（判据错导致把正确动作记成坏动作 57 次）和 `when-line-no-effect`（指标错导致结论虚高
一倍多）两次前鉴 —— **判据不先修，测什么都是假的。**
